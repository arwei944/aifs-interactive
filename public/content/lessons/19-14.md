# 顶点14 -推测解码推理服务器

> EAGLE-3在vllm0.7中的实际吞吐量为2.5-3倍。P-EAGLE （AWS 2026）进一步推动了类似的猜测。SGLang的SpecForge大规模训练了草稿头。红帽的投机者中心发布了通用开放模型的一致草案。TensorRT-LLM在NVIDIA上实现了一流的推测解码。2026年的生产服务堆栈是vLLM或SGLang，具有EAGLE-family草稿，FP8或INT4量化，以及队列等待的HPA。这个顶点是为两个开放模型提供2.5倍以上的基线吞吐量，并提供完整的尾部延迟报告。

**Type:** Capstone
**Languages:** Python (serving), C++ / CUDA (kernel inspection), YAML (configs)
**Prerequisites:** Phase 3 (deep learning), Phase 7 (transformers), Phase 10 (LLMs from scratch), Phase 17 (infrastructure)
**实施阶段：** P3·P7·P10·P17
**Time:** 30 hours

## 问题

投机解码在2026年成为一种商品。EAGLE-3草案头训练目标模型的隐藏状态并提前预测N个令牌；目标模型在单个步骤中进行验证。60-80%的接受率转化为2-3倍的端到端吞吐量。vLLM 0.7本地集成了这一点。SGLang + SpecForge为您提供培训管道。红帽的投机者发布了Llama 3.3 70B, Qwen3-Coder-30B MoE， GPT-OSS-120B的一致草案。

工艺在于服务操作，而不是模型。接受率随流量分布（ShareGPT vs代码vs域数据）而变化。拒绝下的尾部延迟比没有猜测时更糟糕——你必须在多个批处理大小下报告p99，而不仅仅是稳态令牌/秒。每百万代币的成本vs Anthropic / OpenAI API是可信度杠杆。

## 概念

推测解码有两层。一个草案模型（EAGLE-3头部，ngram或更小的目标对齐模型）每一步提出k个候选令牌。**目标**模型一次验证所有k；任何被接受的前缀都将替换贪心路径。验收率取决于草案与目标的一致性和输入分布。

EAGLE-3在大多数流量上都胜过ngram草稿。P-EAGLE对更深的吃水树进行了类似的推测。权衡：拒绝时的P99延迟更高，因为验证传递更大。服务配置必须报告批处理大小的桶延迟以显示此问题。

部署是Kubernetes。vLLM 0.7在每个GPU或张量并行分片上运行一个副本。HPA在队列等待而不是CPU上自动扩展。FP8 （Marlin）和INT4 （AWQ）量化将GPU内存保持在H100 / H200的范围内。端到端报告是吞吐量、接受率、批次1/8/32时的p50/p99和$/1M令牌。

## 体系结构

```
request ingress
    |
    v
vLLM server (0.7) or SGLang (0.4)
    |
    +-- draft: EAGLE-3 heads | P-EAGLE parallel | ngram fallback
    +-- target: Llama 3.3 70B | Qwen3-Coder-30B | GPT-OSS-120B
    |     quantized FP8-Marlin or INT4-AWQ
    |
    v
verify pass: batch k draft tokens through target
    |
    v (accept prefix; resample for rejected suffix)
    v
token stream back to client
    |
    v
Prometheus metrics: throughput, acceptance rate, queue wait, latency p50/p99
    |
    v
HPA on queue-wait metric
```

## 堆栈

- 上菜：vLLM 0.7或SGLang 0.4
- 投机方法：EAGLE-3 draft heads， P-EAGLE parallel投机，ngram fallback
- 草案培训：SpecForge （SGLang）或Red Hat speculator
- 目标型号：羊驼3.3 70B, Qwen3-Coder-30B MoE, GPT-OSS-120B
- 量化：FP8 (Marlin), INT4 AWQ
- 部署：Kubernetes + NVIDIA设备插件；队列等待度量的HPA
- Eval: ShareGPT, MT-Bench-v2, GSM8K， HumanEval用于域扩展验收测量
- 参考：TensorRT-LLM推测解码的供应商基线

## 构建它

1. **选择羊驼3.3 70B。量化到FP8通过马林。在1xH100（或2x张量并行）上部署在vLLM 0.7下。

2. * *源草案。**从红帽投机者拉对齐EAGLE-3草案头（或通过SpecForge训练一个）。加载到vLLM的推测解码配置中。

3. * *基线数据。**猜测之前：代币/秒在1/8/32批次，p50/p99延迟，GPU利用率。发布。

4. * *启用EAGLE-3。**翻转配置；重新运行相同的基准测试。报告加速，接受率，p99尾部延迟增量。

5. * * P-EAGLE。**允许并行推测；与EAGLE-3系列相比测量更深的吃水树。报告P-EAGLE帮助和伤害的变化。

6. * *域交通。**通过同一服务器运行ShareGPT vs HumanEval vs特定于域的流量。衡量每次分发的接受率。确定气流何时漂移。

7. **第二个目标模型。**在Qwen3-Coder-30B MoE上运行相同的管道。草案是棘手的（MoE路由噪声）。报告。

8. * * k8 HPA。**部署在k8下与HPA跟踪演示负载为三倍时的横向扩展。

9. * *成本比较。**在相同的eval上计算$/1M token与Anthropic Claude Sonnet 4.7和OpenAI GPT-5.4。发布。

## 练习

1. 当草案比目标版本落后一个版本时（例如，Llama 3.3 -> 3.4漂移），测量接受率下降。构建监视警报。

2. 实现ngram-fallback：如果EAGLE-3接受度低于阈值，则切换到ngram草稿。报告可靠性改进。

3. 运行一个受控的MoE实验：同样的Qwen3-Coder-30B注入了路由噪声和没有。测量草案验收灵敏度。

4. 扩展到H200 （141gb）。报告获得的每个副本的模型大小净空以及您是否可以提供未量化的Llama 3.3 70B。

5. 在相同的H100硬件上测试TensorRT-LLM推测解码。报告它与vLLM在哪里获胜。

## 关键术语

| Term | What people say | What it actually means |
|------|-----------------|------------------------|
| Draft model | "Speculator" | Small model that proposes N tokens for the target to verify |
| EAGLE-3 | "2026 draft architecture" | Draft head trained on target hidden states; ~75% acceptance |
| P-EAGLE | "Parallel speculation" | Tree of draft branches verified in one target pass |
| Acceptance rate | "Hit rate" | Fraction of drafted tokens accepted without resampling |
| Quantization | "FP8 / INT4" | Lower-precision weights to fit more model in GPU memory |
| Queue wait | "HPA metric" | Time a request waits in the pending queue before inference starts |
| Speculators hub | "Aligned drafts" | Red Hat Neural Magic hub of EAGLE drafts for common open models |
