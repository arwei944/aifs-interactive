# 自托管服务选择- llam .cpp, Ollama， TGI, vLLM, SGLang

> 2026年，自托管推理将由四大引擎主导。根据硬件、规模和生态系统进行选择。**llama.cpp**是最快的CPU -最宽的模型支持，完全控制量化和线程。**Ollama**是dev-laptop一命令安装，比llama.cpp （Go + CGo + HTTP序列化）慢15-30%，在prod-like负载下的吞吐量差距是3倍。**TGI于2025年12月11日进入维护模式** -仅修复了错误，原始吞吐量比vLLM慢10%，但历史上最高的可观察性和hf生态系统集成。这种维护状态使其成为一个高风险的长期赌注——对于新项目来说，SGLang或vLLM是更安全的违约。**vLLM**是通用的生产默认- v0.15.1（2026年2月）添加PyTorch 2.10, RTX Blackwell SM120， H200优化。**SGLang**是真正的多回合/重前缀专家-生产40万+ gpu （xAI, LinkedIn, Cursor, Oracle， GCP, Azure， AWS）。硬件约束：仅cpu→仅llama.cpp。AMD /非nvidia→仅支持vLLM （TRT-LLM是nvidia锁定的）。2026管道模式：dev = Ollama, staging = lama.cpp, prod = vLLM或SGLang。相同的GGUF/HF权重。

**Type:** Learn

## 学习目标

- 在给定硬件（CPU / AMD / NVIDIA Hopper / Blackwell）、规模（1个用户/ 100个/ 10,000个）和工作负载（一般聊天/代理/长上下文）的情况下选择一个引擎。

- 使用相同的GGUF或HF权重描述dev/staging/prod管道。
- 解释为什么“CPU only”强制llama.cpp和“AMD”排除TRT-LLM。

## 这个问题

您的团队启动了一个新的自托管LLM项目。一个工程师说是Ollama，另一个说是vLLM，第三个说“TGI不是开箱即用吗？”这三种方法适用于不同的环境。没有人适合所有人。

在2026年，选择树很重要：硬件第一，规模第二，工作负载第三。2025年的一个具体事件——TGI在12月11日进入维护模式——改变了新项目的默认值。

## 这个概念

### 五大引擎

| Engine | Best for | Notes |
|--------|----------|-------|
| **llama.cpp** | CPU / edge / minimal deps / widest model support | Fastest on CPU, full control |
| **Ollama** | Dev laptops, single user, one-command install | 15-30% slower than llama.cpp; 3x prod throughput gap |
| **TGI** | HF ecosystem, regulated industries | **Maintenance mode Dec 11, 2025** |
| **vLLM** | General-purpose production, 100+ users | Broad production default; v0.15.1 Feb 2026 |
| **SGLang** | Agentic multi-turn, prefix-heavy workloads | 400,000+ GPUs in production |

### Hardware-first决定

**CPU专用**→llama.cpp。奥拉玛也能工作，但速度较慢。没有其他引擎在CPU上有竞争力。

**AMD GPU**→vLLM （AMD ROCm支持）。SGLang也可以工作。TRT-LLM是nvidia锁定的，所以它不在。

**NVIDIA Hopper (H100 / H200)**→vLLM或SGLang或TRT-LLM。三个都是顶级的。

**NVIDIA Blackwell (B200 / GB200)**→TRT-LLM是吞吐量领先者（第17.07期）。vLLM和SGLang紧随其后。

**苹果硅（m系列）**→lama.cpp（金属）奥拉玛把这个包起来。

### Scale-second决定

**1用户/本地开发者**→Ollama。一个命令，第一个令牌，以秒为单位。

**10-100用户/小团队**→vLLM单gpu。

**100-10k用户/生产**→vLLM生产堆栈（第17·18阶段）或SGLang。

**10k+用户/企业**→vLLM生产堆栈+分解（阶段17.17）+ LMCache（阶段17.18）。

### Workload-third决定

**一般聊天/问答**→vLLM赢得广泛的默认。

**代理多回合（工具、规划、记忆）**→SGLang的RadixAttention（第17·06阶段）占主导地位。

**重前缀复用的RAG **→SGLang。

**代码生成**→vLLM fine；SGLang在缓存上稍微好一些。

**长上下文(128K+)**→vLLM +块预填充；SGLang +分级KV。

### TGI维护陷阱

2025年12月11日，TGI进入维护模式，只修复bug。历史上：顶级的可观察性，一流的hf生态系统集成（模型卡，安全工具），在原始吞吐量方面略落后于vLLM。

对于2026年的新项目：远离TGI。现有的TGI部署可以继续，但最终应该迁移。SGLang和vLLM是更安全的默认值。

### 管道模式

Dev （Ollama）→staging （lama.cpp）→prod （vLLM）。相同的GGUF或HF权重贯穿始终。工程师们在笔记本电脑上快速迭代；分期反映生产量化；产品是服务对象。

### Ollama caveat

Ollama很适合开发，但不适合共享生产：Go HTTP序列化增加了开销，并发管理比vLLM更简单，OpenTelemetry支持滞后。在Ollama发挥作用的地方使用它——一个用户，一个命令——然后切换到vLLM进行共享。

### 自托管vs托管是一个单独的决定

第17.01阶段（托管超大规模）、第02阶段（推理平台）涵盖托管。本课假设您已经决定使用自托管。自托管的原因：数据驻留、自定义微调、大规模的总成本所有权、托管上不可用的域模型。

### 你应该记住的数字

- TGI维护模式：2025年12月11日。
- vLLM v0.15.1: 2026年2月；PyTorch 2.10;Blackwell SM120支持。
- SGLang生产足迹：400,000+ gpu。
- Ollama吞吐量差距vs llama.cpp：慢15-30%；在推力载荷下3x。
