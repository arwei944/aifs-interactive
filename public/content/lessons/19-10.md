# 顶点10 -多代理软件工程团队

> sw - af的工厂架构、MetaGPT的基于角色的提示、AutoGen 0.4的类型角色图、Cognition的Devin和factory的Droids都汇聚在2026年的相同形状上：架构师规划，N个编码人员并行工作树，审查员进行审核，测试人员进行验证。并行工作树将挂钟转换为吞吐量。共享状态和切换协议成为故障面。最重要的是建立团队，在sw -bench Pro上进行评估，并报告哪些交接中断以及多久一次。

**Type:** Capstone
**Languages:** Python / TypeScript (agents), Shell (worktree scripts)
**Prerequisites:** Phase 11 (LLM engineering), Phase 13 (tools), Phase 14 (agents), Phase 15 (autonomous), Phase 16 (multi-agent), Phase 17 (infrastructure)
**运行阶段：** P11·P13·P14·P15·P16·P17
**Time:** 40 hours

## 问题

单代理编码控制在大型任务中遇到了瓶颈。这不是因为任何单个代理都很弱，而是因为一个200k令牌上下文不能容纳架构计划加上四个并行代码库切片，加上审稿人评论和测试输出。多代理工厂将问题分开：架构师拥有计划，编码人员在并行工作树中拥有实现，审稿人进行审核，测试人员进行验证。sw - af的“工厂”架构，MetaGPT的角色，AutoGen的类型角色图——这三种框架都描述了相同的形状。

故障面是切换。架构师计划一些程序员无法实现的东西。编码员产生冲突的差异。审稿人批准了一个幻觉修复。测试员与仍在写作的程序员赛跑。您将构建其中一个团队，在50个sw -bench Pro问题上运行它，跟踪每一次移交，并发布事后分析。

## 概念

角色是类型代理。**Architect** (Claude Opus 4.7)读取问题，编写计划，并将其分解为具有显式接口的子任务。**编码器**(克劳德十四行诗4.7，N个并行实例，每个在一个**Reviewer** (GPT-5.4)读取合并的差异并批准或请求特定的更改。**Tester** (Gemini 2.5 Pro)孤立地运行测试套件，并报告通过/失败的工件。

交流是通过一个共享的任务板（文件备份或Redis）。每个角色使用它被允许处理的任务。切换是a2a协议类型的消息。协调关注：合并冲突解决（协调者角色或自动三方合并），共享状态同步（一旦编码人员开始，计划就会冻结；重新计划是单独的事件），以及审稿人守门人（审稿人不能批准其自己的更改或其提出的更改）。

代币放大是隐性成本。每个角色边界都添加了摘要提示和交接上下文。40回合的单代理运行变成了四个角色总共160回合。这个标题特别权衡了代币效率与单代理基准的关系，因为问题不是“多代理是否有效”，而是“它是否能赢得每美元”。

## 堆栈

- 编排：具有共享状态的LangGraph +每个代理子图
- 消息传递：用于类型化代理间消息的A2A协议（谷歌2025）
- 型号：Opus 4.7（架构师），Sonnet 4.7（编码器），GPT-5.4（审稿人），Gemini 2.5 Pro（测试人员）
- 工作树隔离：
- 合并协调器：自def 三向合并+ llm介导的冲突解决
- Eval: sw -bench Pro（50个问题），sw - af场景，用于单元测试的HumanEval++
- 可观察性：使用角色标记的范围，每个代理令牌记帐
- 部署：k8，每个角色作为一个单独的部署+待办事项的HPA

## 构建它

1. **任务。**不是JSONL输入信息:代理订阅标签。

2. **建筑师。**读取GitHub问题，运行Opus 4.7与计划模板需要显式的子任务接口（文件触摸，公共函数，测试影响）。释放一

3. **程序员。** N个并行工人，每个工人从棋盘上申请一个子任务。每个都会生成一个新的实现子任务。发射

4. **合并协调员。**在all-coders-done的情况下，以三种方式将N个分支合并为一个staging分支。只有当文件级重叠存在时，llm介导的冲突解决。

5. **评论家。** GPT-5.4读取合并的差异，不能批准它所创建的差异。发射

6. **测试人员。** Gemini 2.5 Pro在一个干净的沙箱中运行测试套件。捕捉构件。发射失败的测试循环回拥有失败子任务的编码器。

7. **切换会计。**在Langfuse中，每个跨越角色边界的消息都有一个包含有效负载大小和使用的模型的跨度。计算每个子任务的token放大（coder_token + reviewer_token + test_token + architect_share / coder_token）。

8. ** Eval。**运行50个sw -bench Pro问题。将pass@1和$-per- resolved -issue与单个代理基线（单个工作树中的一个Sonnet 4.7）进行比较。

9. **死后。**对于每个失败的问题，确定失败的移交（计划太模糊，合并冲突，审稿人错误批准，测试人员错误）。生成切换失败直方图。

## 练习

1. 将一个明显的bug注入到一个困难的中期运行（额外的）度量审稿人的错误批准率。调整审稿人提示，直到错误批准低于5%。

2. 减少到两个编码人员（架构师+编码人员+审查人员+测试人员，编码人员按顺序运行两个子任务）。比较挂钟和通过率。

3. 将合并协调器替换为单个写入器约束（子任务触及不相交的文件集）。衡量架构师的规划负担。

4. 从GPT-5.4切换到Claude Opus 4.7。测量错误批准率和令牌成本增量。

5. 添加第五个角色：文档管理员（俳句4.5）。审查之后，它会生成一个变更日志条目。衡量文档质量是否证明额外的令牌花费是合理的。

## 关键术语

| Term | What people say | What it actually means |
|------|-----------------|------------------------|
| Parallel worktree | "Isolated branch" | `git worktree add` producing a fresh working tree per coder |
| Task board | "Shared message bus" | File or Redis store of typed messages agents subscribe to |
| Handoff | "Role boundary" | Any message crossing from one role's context to another's |
| Token amplification | "Multi-agent overhead" | Total tokens across roles / single-agent tokens for the same task |
| A2A protocol | "Agent-to-agent" | Google's 2025 spec for typed inter-agent messages |
| Merge coordinator | "Integrator" | Component that runs three-way merge and mediates conflicts |
| False approval | "Reviewer hallucination" | Reviewer approves a diff with known bugs |
