# 自主编码代理前景（2026）

> 在不到三年的时间里，sw -bench验证从4%上升到80.9%。同样的Claude Sonnet 4.5在SWE-agent v1上得分43.2%，在Cline autonomous上得分59.8%——现在模型周围的脚手架和模型本身一样重要。OpenHands（以前的OpenDevin）是最活跃的麻省理工学院许可平台，它的CodeAct循环直接在沙盒中执行Python动作，而不是JSON工具调用。标题数字隐藏了一个方法上的问题：500个经过SWE-bench验证的任务中有161个只需要1-2行更改，而对于相同的前沿模型，SWE-bench Pro（10+行任务）的比例为23-59%。

## 这个问题

“哪种编码代理是最好的”是一个错误的问题。正确的问题是：在与我的工作相匹配的任务分布上，以及我将在生产环境中运行的脚手架，我能得到什么样的端到端可靠性？

在2022年至2026年期间，该领域了解到脚手架-检索层，规划器，沙盒，编辑-验证循环，反馈格式-是承重的。Claude Sonnet 4.5在SWE-agent v1上得分43.2%克莱恩自主支架内的同一模型得分为59.8%。16.6绝对差值，相同权重。基本模型是一个组件；这个循环就是产物。

伴随的问题是基准饱和隐藏了回归。SWE-bench Verified接近饱和，而easy-task tail（500个任务中需要≤2行代码的有161个）将得分拉高。真实世界的质量在像sw -bench Pro（10+线变化）这样的发行版上得到了更好的衡量，其中同样的领导者仍然保持在23-59%。

## 这个概念

### 瑞典板凳，一段

SWE-bench （Jimenez et al.）采用真实的GitHub问题和真实的补丁，并要求代理生成一个补丁，使测试套件通过。sw -bench Verified （OpenAI, 2024）是一个人工管理的500个任务子集，删除了模糊和破碎的任务。sw -bench Pro是更困难的继任者——需要10条以上的变更线，目前前沿代理占23% - 59%。

### 2022→2026年的曲线到底显示了什么

- **2022**：研究模型在原始sw -bench上约为4%。
- **2024**: GPT-4 +德文式脚手架~14%；swe -剂在~12%。
- **2025**：克劳德3.5/3.7十四行诗内线Aider和SWE-agent推至40-55%范围。
- **2026**: Claude Sonnet 4.5和前沿竞争对手在SWE-bench验证70-80%以上。Epoch AI的排行榜实时跟踪这一点。

斜率来自三个复合来源：更好的基础模型、更好的脚手架（CodeAct、反射、验证器循环）和更好的基准测试（经过验证的去除噪声）。

### CodeAct vs JSON工具调用

OpenHands （All-Hands-AI, arXiv:2407.16741，前身为OpenDevin）采取了一个特定的架构赌注：模型不是发出由主机解码和执行的JSON工具调用，而是发出Python代码，并在沙盒中运行jupyter风格的内核。代理可以循环遍历文件、链接工具，并在一个操作中捕获自己的异常。

权衡:

- **JSON工具调用**：每个动作是一个回合；易于审核；有限的组合性;默认情况下是安全的，因为每个调用都要经过显式验证器。
- **CodeAct**：一个动作可以是一个完整的程序；成分;需要一个加固的沙箱（OpenHands使用Docker隔离）；故障模式包括沙盒运行时允许的任何故障模式。

这两种体系结构都在生产中。CodeAct在开放平台（OpenHands, smolagents）中占主导地位。JSON工具调用在托管服务（Anthropic managed Agents, OpenAI Assistants）中仍然占主导地位，在这些服务中，提供者控制执行者。

### 为什么脚手架占主导地位

编码运行是一个长期的视界轨迹（第1课）。可靠性贯穿各个步骤。脚手架买积分的三个地方：

1. **检索**：找到正确的文件来读取是无声的瓶颈。SWE-agent的ACI、OpenHands的文件索引和Aider的repo-map都攻击了这一点。
2. **验证器循环**：运行测试，读取堆栈跟踪，并重新尝试在sw -bench上是一个10+点的增量。
3. **故障遏制**：一个沙盒，回滚错误，防止复合损害。同样的模型，有和没有验证器循环看起来像两个不同的产品。

### 基准饱和度和真实分布

OpenHands的作者和Epoch AI都指出，SWE-bench Verified有一个简单的尾部：500个任务中有161个只需要1-2行更改。高分部分是由这条尾巴驱动的。sw -bench Pro限制10+线的变化和返回得分在23-59%的范围内，即使是前沿系统。您的产品分布几乎肯定更接近于Pro而不是Verified。

选择代理的含义：运行您自己的bug backlog的一个类似pro的子集。真正重要的是你所交付的任务的得分。

## 使用它


1. 一个JSON工具调用框架，每回合执行一个操作。
2. 一个**CodeAct**脚手架，可以在每个操作中发出一小段Python代码。

两者都使用一个存根“模型”（确定性规则），因此比较将脚手架与模型质量隔离开来。输出显示，CodeAct脚手架在更少的回合内解决了更多的任务，但代价是每个动作的爆炸半径更大。

## 练习

1. 运行每个脚手架在相同的任务集中进行多少次？每一枚的爆炸半径是多少？

2. 请阅读OpenHands论文（arXiv:2407.16741）。这篇论文认为，在复杂的任务中，CodeAct优于JSON工具调用。找出论文承认的一种故障模式，并用一句话说明这种模式何时会在生产中占主导地位。

3. 从bug backlog中选择一个需要在两个文件中进行10行以上更改的任务。在(a) JSON工具调用和(b) CodeAct下估计前沿模型的端到端成功概率。证明差距是合理的。

4. SWE-bench Verified有161个单文件，1-2行任务。构建一个排除它们的分数。排行榜是如何洗牌的？

5. 阅读“介绍sw -bench验证”（OpenAI）。解释用于删除模棱两可任务的具体方法，并说出一个策展人会错过的类别。

## 关键术语

| Term | What people say | What it actually means |
|---|---|---|
| SWE-bench | "Coding benchmark" | Real GitHub issues with ground-truth patches and test suites |
| SWE-bench Verified | "Cleaned subset" | 500 human-curated tasks, easier-tail present |
| SWE-bench Pro | "Harder subset" | 10+ line changes; frontier sits at 23–59% |
| CodeAct | "Code-as-action" | Agent emits Python; Jupyter-style kernel executes in sandbox |
| JSON tool call | "Function calling" | Each action is a structured JSON payload validated before execution |
| Scaffold | "Agent framework" | Retrieval + planner + executor + verifier loop around the base model |
| ACI (Agent-Computer Interface) | "SWE-agent's format" | Command set designed for LLM ergonomics, not human shells |
| Verifier loop | "Test-and-retry" | Run tests, read output, revise patch; biggest non-model reliability gain |
