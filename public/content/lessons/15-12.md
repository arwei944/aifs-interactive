# 长时间运行的后台代理：持久执行

> 生产长线代理不运行每个LLM调用都成为具有检查点、重试和重放的活动。Temporal的OpenAI Agents SDK集成于2026年3月发布。Claude Code例程（Anthropic）在没有持久本地进程的情况下运行计划的Claude Code调用。会话在人工输入时暂停，在部署中幸存下来，并从最近键入的检查点恢复在新的人体工程学背后是一个旧的模式——工作流编排——一个新的输入：LLM调用作为不确定的活动，必须在恢复时确定地重播。

**Type:** Learn
**Languages:** Python (stdlib, minimal durable-execution state machine)
**Prerequisites:** Phase 15 · 10 (Permission modes), Phase 15 · 01 (Long-horizon agents)
**Time:** ~60 minutes

## 这个问题

考虑一个运行4小时的代理。它调用三个工具，提示用户两次，并调用40个LLM。中途，它所运行的主机重新启动。会发生什么呢?

- 在一个天真的运行将从头开始。这三个工具调用（具有实际的副作用）再次执行。系统会再次提示用户输入他们已经批准的内容。40个LLM电话被重新计费。
- 持久执行：从最近的检查点恢复运行。已经完成的活动不会重新执行；他们的结果从持久的日志中重播。用户不会重新批准他们已经批准的事情。已经拨打的法学硕士电话不会重新计费。

这是十年来工作流引擎的相同模式（Temporal, Cadence， Uber的Cherami）。新的是，LLM调用现在是一种活动——不确定的、昂贵的、有副作用的——它们完全符合这种模式。

这堂课的主题是：长视界可靠性衰减（METR观察到一个“35分钟衰减”——成功率随着视界近似呈二次下降）。持久执行可以使运行时间超过可靠性配置文件所支持的时间，这是一种新的方法，如果设计正确，则安全失败，如果设计错误，则不安全。

## 这个概念

### 活动、工作流和重播

- **工作流**：确定性编排代码。定义活动、分支和等待的顺序。必须是确定性的，以便可以从事件日志中重播，而不会出现意外的分歧。
- **活动**：一个不确定的、可能失败的工作单元。LLM调用，工具调用，文件写入，HTTP请求。每个活动都记录了它的输入和输出（一旦完成）。
- 事件日志：持久的后备存储。每个活动的开始、完成、失败、重试以及每个工作流决策都被记录下来。
- **重放**：在恢复时，工作流代码从开始重新运行；每个已经完成的活动返回其记录的结果，而无需重新执行。只有尚未完成的活动才会实际运行。

这与React对虚拟DOM的重新渲染或Git从提交中重建工作树的形状相同。编排器中的决定论使持久性变得廉价。

### 为什么LLM调用符合这种模式

LLM调用是：
- 不确定（温度>；甚至温度0在模型版本之间漂移）。
- 昂贵（金钱和延迟）。
- 可能失败（速率限制、超时）。
- 副作用（如果它们调用了工具）。

这就是活动概况。将每个LLM调用包装为一个活动，为您提供了具有指数回退的重试，重新启动时的检查点，以及用于调试的可重复播放的跟踪。

### 由

LangGraph、Microsoft代理框架、Cloudflare持久对象和Claude代码例程都汇聚在相同的API形状上每个状态转换都保留到后端（PostgreSQL默认，SQLite用于开发，Redis用于缓存）；Resume读取最近的检查点。

后端选择很重要：

- **PostgreSQL**：持久的，可查询的，可存活的部署。默认为LangGraph。
- **SQLite**: local-dev；跨主机丢失数据。
- **Redis**：快速但短暂，除非配置了AOF/快照。
- **Cloudflare持久对象**：透明分布；由唯一键限定范围；存活数小时到数周。

### 人力投入达到一流状态

提议-然后提交（第15课）需要一个持久的“等待人类”状态。工作流暂停，外部队列保存挂起的请求，审批从该点重新开始。没有持久性，这是最好的努力；有了它，一夜之间的批准就会到来，工作流程在早上就会开始。

### 35分钟的退化

METR观察到，在连续运行约35分钟后，所测量的每个代理类别都显示出可靠性衰减。任务持续时间增加一倍，故障率就会增加四倍。持久执行不能解决这个问题；它允许您运行比可靠性配置文件支持的时间更长。安全的模式是将持久性与重新进入时需要新的HITL的检查点结合起来，并使用预算终止开关（第13课）来限制总计算，而不考虑时钟时间。

### 当持久执行是错误的答案时

- 在没有人工输入的情况下运行不到几分钟。开销>收益。
- 严格的只读信息检索。
- 正确性要求在一个上下文窗口内端到端完成的任务（一些推理任务；一些一次性生成）。

## 练习

1. 运行观察幼稚重试和重放之间活动执行计数的差异。更改崩溃点并显示相应的重放计数变化。

2. 转换玩具引擎使用模拟两个共享引擎的并发会话，并确认它们的事件日志没有冲突。

3. 以玩具引擎中的一个活动为例。引入非确定性（工作流决策中的挂钟时间戳）。在回放中展示分歧。解释一下真正的引擎是如何处理这种（副作用登记）的。

4. 阅读LangChain的文章“生产深度代理背后的运行时”。列出运行时持久化的每个状态，并列出每个状态所涵盖的故障模式。

5. 为6小时的自主编码任务设计检查点策略。你们在哪里检查站？崩溃后的恢复是什么样的？什么需要新的HITL？

## 关键术语

| Term | What people say | What it actually means |
|---|---|---|
| Workflow | "Agent's script" | Deterministic orchestration code; replayable from event log |
| Activity | "A step" | Non-deterministic unit (LLM call, tool call); logged before and after |
| Event log | "The backing store" | Durable record of every state transition |
| Replay | "Resume" | Re-run workflow; completed activities return logged results without re-execution |
| Checkpoint | "Save point" | Persisted state keyed by thread_id; latest-wins on resume |
| thread_id | "Session key" | Identifier that scopes durable state |
| 35-minute degradation | "Reliability decay" | METR: success rate drops ~quadratically with horizon |
| Non-determinism | "Drift on replay" | Wall clock, random, LLM output; must be registered as side effect |
