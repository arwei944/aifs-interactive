# 并行工具调用和工具流

> 三个独立的天气查询序列化为三个往返。并行运行它们，总时间将缩减为最慢的单个调用。每个前沿供应商现在在一个回合内发出多个工具调用。回报是真实的；管道很微妙。本课程涉及两个部分：平行扇出和流参数重组，重点是id相关陷阱。

## 这个问题

在没有平行呼叫的情况下，回答“班加罗尔、东京和苏黎世的天气如何”的座席会这样做：

```
user -> LLM
LLM -> call get_weather(Bengaluru)
host -> run executor, reply with result
LLM -> call get_weather(Tokyo)
host -> run executor, reply with result
LLM -> call get_weather(Zurich)
host -> run executor, reply with result
LLM -> final text answer
```

三次LLM往返，每次也支付执行器延迟。大约是理想时间的4倍。

使用并行调用：

```
user -> LLM
LLM -> call get_weather(Bengaluru); call get_weather(Tokyo); call get_weather(Zurich)
host -> run all three executors concurrently, reply with three results
LLM -> final text answer
```

一个LLM往返。执行者时间是三者的最大值，而不是总和。OpenAI、Anthropic和Gemini的生产基准测试显示，扇形输出工作负载的挂钟减少了60%到70%。

代价是相关性的复杂性。当三个呼叫顺序错误时，您的结果必须匹配当结果流时，必须在执行之前将部分参数片段组装成完整的JSON。Gemini 3添加唯一id的部分原因是为了解决对同一工具的两个并行调用无法区分的现实问题。

- ** OpenAI。**
- **人择。**

### 并发运行调用

主机在自己的线程、协程或远程工作者上运行每个调用的执行器。最简单的线束使用线程池；生产环境使用asyncio with完成的顺序是不可预测的- id是标识符。

一个常见的错误：以调用列表顺序而不是完成顺序回复结果。这通常是有效的，因为模型只关心更倾向于使用显式id按完成顺序回复。

### 流式工具调用

当模型流时，用于三个并行调用的三个独立的块流在线路上交错。每个id需要一个累加器。

供应商形状：

- ** OpenAI。**每个块是块携带对每个索引进行累加
- **人择。**流事件`content_block_delta` events carry `input_json_delta` chunks. `content_block_stop` closes each block.
- **双子座。**在双子座3号之前，流媒体一次返回一个完整的呼叫。

### 部分JSON和parse-early陷阱

你无法解析部分JSON，例如正确的门是提供商的呼叫结束信号：OpenAI的只有这样才能尝试更健壮的方法是使用增量JSON解析器，在结构完成时生成事件；OpenAI的流指南建议用户体验显示一个实时的“思考”指标。大括号计数作为完整性测试是不可靠的（引号内的字符串或转义内容会导致误报），应该只用作非正式的调试启发式。

### 无序的完成

```
call_A: fast API, returns first
call_B: slow API, returns second
call_C: median API, returns third
```

主机回复仍然必须引用id：

```
[{role: "tool", tool_call_id: "call_A", content: ...},
 {role: "tool", tool_call_id: "call_B", content: ...},
 {role: "tool", tool_call_id: "call_C", content: ...}]
```

回复中的顺序对于OpenAI或Anthropic的正确性并不重要。双子座接受任何订单，只要id匹配。

### 基准测试：顺序vs并行

系上挽具顺序运行它总共需要1800毫秒。并行运行的时间为max(400,600,800) = 800毫秒。差异是恒定的，而不是成比例的，因此节省的成本随着工具数量的增加而增加。

现实世界的警告：并行调用会给下游api带来压力。到速率限制服务的10路扇出将失败。阶段13·17涵盖网关级背压；重试语义计划在未来的阶段进行。

### 流扇形挂钟

如果模型本身是流的，您可以在一个调用的参数完成后立即开始执行，而不是等待所有调用完成。这是一个优化OpenAI文档，但不是所有sdk公开。本课中的控制程序做到了这一点：一旦模拟流产生一个完整的参数对象，宿主程序就启动该调用。

## 使用它

Z0第一个运行三个模拟天气呼叫顺序和并行使用后半部分重播了一个虚假的流媒体响应——大块的没有LLM，没有网络，只有重组逻辑。

看点：

- 顺序计时器达到1.8秒。在相同的假延迟上，并行计时器达到0.8秒。
- 累加器通过缓冲每个id并仅在每个调用的JSON完成时进行解析来处理无序到达的块。
- 执行器在id的参数完成后立即启动，而不是在所有流结束后启动。

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Parallel tool calls | "Fan-out in one turn" | Model emits multiple tool calls in a single assistant message |
| `parallel_tool_calls` | "OpenAI's flag" | Enable or disable multi-call emission |
| `disable_parallel_tool_use` | "Anthropic's inverse" | Opt-out flag; default is parallel enabled |
| Tool call id | "Correlation handle" | Per-call identifier the result message must echo |
| Accumulator | "Stream buffer" | Per-id string buffer for partial `arguments` chunks |
| Out-of-order completion | "Fastest first" | Parallel calls finish in unpredictable order; ids are the glue |
| Dependency graph | "Ordering constraints" | Tools whose outputs feed into inputs of other tools; cannot parallelize |
| Parse-early trap | "JSON.parse exploded" | Attempting to parse an incomplete `arguments` string |
| `streamFunctionCallArguments` | "Gemini 3 feature" | Streamed argument chunks with unique id per call |
| Completion-order reply | "Don't wait for all" | Reply with results as they arrive, keyed by id |
