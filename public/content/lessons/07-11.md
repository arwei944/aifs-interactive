# 专家组合（MoE）

> 密集的70BTransformer激活每个令牌的每个参数。671B MoE每个令牌只激活37B，并且在每个基准测试中都超过它。稀疏性是近十年来最重要的扩展思想。

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 7 · 05 (Full Transformer), Phase 7 · 07 (GPT)
**Time:** ~45 minutes

## 这个问题

密集Transformer在推理时的FLOPs等于它的参数计数（正向通过时乘以2）。按比例扩大密集模型，每个代币都要支付全部费用。到2024年，前沿领域遇到了计算瓶颈：为了变得更智能，每个令牌需要指数级地增加FLOPs。

混合专家打破了这种联系。将每个FFN替换为总参数=每个令牌的活动参数=2026年的典型配置：存储规模为

2026年的前沿几乎完全是MoE: DeepSeek-V3（总671B /活跃37B）、Mixtral 8×22B、Qwen2.5-MoE、Llama 4、Kimi K2、gpx -oss。在人工分析的独立排行榜上，排名前十的开源模型都是MoE。

## 这个概念


### FFN交换

密集Transformer块：

```
h = x + attn(norm(x))
h = h + FFN(norm(h))
```

MoE块:

```
h = x + attn(norm(x))
scores = router(norm(h))              # (N_tokens, E)
top_k = argmax_k(scores)              # pick k of E per token
h = h + sum_{e in top_k}(
        gate(scores[e]) * Expert_e(norm(h))
    )
```

每个专家都是独立的FFN（通常是SwiGLU）。路由器是一个单线性层。每个令牌都有自己的选择

### 负载平衡问题

如果路由器将90%的令牌通过专家3，其他专家就会挨饿。已经尝试了三种修复方法：

1. **辅助负载平衡损耗**（开关Transformer，混合式）。在专家使用中添加与差异成比例的惩罚。工作，但增加了一个超参数和第二个梯度信号。
2. **专家容量+令牌掉落**（早期交换机）。每个专家最多处理一次溢出令牌跳过该层。伤害了质量。
3. **辅助无损耗平衡** (DeepSeek-V3)。添加一个学习到的专家偏差，它会改变路由器的top-k选择。偏差是在训练损失之外更新的。主要目标没有罚球。2024年的大开锁。

DeepSeek-V3的方法是：在每个训练步骤之后，对于每个专家，检查其使用率是高于还是低于目标。将偏差推到选择用途用于门控的专家概率是原始的从表达式中解耦路由。

### 共享专家

DeepSeek-V2/V3还将专家分为“共享”和“路由”。每个令牌都要经过所有共享的专家。路由专家是通过top-k选择的。共享专家获取共同知识；路由专家是专门的。V3运行1个共享专家加上256个路由中的top-8。

### 细粒度的专家

经典MoE (GShard, Switch)：每个专家都像一个完整的FFN一样宽。`E` is small (8–64), `k` is small (1–2).

现代细粒度MoE (DeepSeek-V3, Qwen-MoE)：每个专家更窄（1/8 FFN大小）。`E` is large (256+), `k` is larger (8+). 相同的总参数，但组合扩展得更快。`C(256, 8) = 400 trillion` possible "experts" per token. 质量提高，延迟保持不变。

### 成本概况

每个令牌，每层：

| Config | Active params / token | Total params |
|--------|-----------------------|--------------|
| Mixtral 8×22B | ~39B | 141B |
| Llama 3 70B (dense) | 70B | 70B |
| DeepSeek-V3 | 37B | 671B |
| Kimi K2 (MoE) | ~32B | 1T |

DeepSeek-V3几乎在每个基准测试中都击败了Llama 370b（密集），同时每个令牌的活跃FLOPs更少。更多的参数=更多的知识。更多的活动FLOPs =每个令牌更多的计算。运动使它们解耦。

### 问题是：内存

所有的专家都依赖GPU，不管哪个着火。671B型号的fp16重量需要1.3 TB的VRAM。Frontier MoE部署需要专家的并行性——跨gpu的分片专家，跨网络的路由令牌。延迟主要是由全对全通信决定的，而不是由matmul决定的。

Bias affects selection, not gate weight. That is the DeepSeek-V3 trick — bias corrects load imbalance without steering the model's predictions.

### Step 2: run 100 tokens through the router

Track which experts fire how often. Without the bias, usage is skewed. With a bias update loop (`-γ` for over-used experts, `+γ` for under-used), usage converges to a uniform distribution over a few iterations.

### Step 3: param count comparison

Print the "dense equivalent" of an MoE config. DeepSeek-V3-shaped: 256 routed + 1 shared, 8 active, d_model=7168. The total parameter count is eye-watering. The active count is a seventh of a dense Llama 3 70B.

## Use It

HuggingFace loading:

model = AutoModelForCausalLM.from_pretrained("mistralai/Mixtral-8x22B-v0.1")
```

2026生产推断：vLLM本地支持MoE路由。SGLang拥有最快的专家并行路径。两者都自动处理top-k选择和专家并行。

**何时选择MoE:**
- 你想在每个令牌的较低推理成本下获得边界质量。
- 您拥有VRAM /专家并行基础设施。
- 您的工作负载是令牌繁重（聊天、代码），而不是上下文繁重（长文档）。

**何时不能选择MoE:**
- 边缘部署-您为任何活动的FLOP支付全部存储。
- 延迟关键的单用户服务-专家路由增加了开销。
- 小模型(<7B) - MoE的质量优势仅在计算阈值（~6B活动参数）以上出现。

## 练习

1. **容易。**运行观察辅助无损耗偏差更新如何在50次迭代中平衡专家使用。
2. **介质。**将学习到的路由器替换为基于哈希的路由器（确定性，无学习）。比较质量和平衡。为什么学过的路由器更好？
3. **难。**实现grpo风格的“rollout-matched routing”（DeepSeek-V3.2技巧）：专家在推理期间触发的日志，在梯度计算期间强制相同的路由。测量对玩具策略梯度设置的影响。

## 关键术语

| Term | What people say | What it actually means |
|------|-----------------|-----------------------|
| Expert | "One FFN among many" | An independent feed-forward network; parameters dedicated to a sparse slice of the FFN computation. |
| Router | "The gate" | A tiny linear layer that scores each token against each expert; top-k selection. |
| Top-k routing | "k active experts per token" | Each token's FFN computation goes through exactly k experts, weighted by gate. |
| Auxiliary loss | "Load-balance penalty" | Extra loss term that penalizes skewed expert usage. |
| Auxiliary-loss-free | "DeepSeek-V3's trick" | Balance via per-expert bias on the router's selection only; no extra gradient. |
| Shared expert | "Always on" | Extra expert through which every token passes; captures common knowledge. |
| Expert parallelism | "Shard by expert" | Distribute different experts to different GPUs; route tokens across the network. |
| Sparsity | "Active params < total params" | The ratio `k × expert_size / (E × expert_size)`; 37/671 ≈ 5.5% for DeepSeek-V3. |
