# 推理度量- TTFT， TPOT， ITL, Goodput, P99

> 有四个指标决定推理部署是否正常工作。TTFT是预填充+队列+网络。TPOT（相当于ITL）是每个令牌的内存绑定解码成本。端到端延迟是TTFT加上TPOT乘以输出长度。吞吐量是指在整个船队中聚合的每秒令牌。但是对产品来说最重要的是good - put——同时满足每个SLO的请求的比例。低goodput下的高吞吐量意味着您正在处理的令牌永远不会及时到达用户。llama -3.1- 8b -指令在2026年TRT-LLM上的参考数字：平均TTFT 162 ms，平均TPOT 7.33 ms，平均E2E 1,093 ms。总是报告P50， P90， P99 -绝不是故意的。注意测量陷阱：GenAI-Perf将TTFT从ITL计算中排除，LLMPerf将其包含；对于同一运行，两个工具在TPOT上存在分歧。

## 这个问题

“我们的吞吐量是每秒15000个代币。”那又怎样?如果40%的端到端请求超过2秒，用户就会放弃会话。吞吐量本身并不能告诉你产品是否有效。

推理有多个延迟轴，每个轴的失败都不同。预填充是受计算限制的，并根据提示长度进行缩放。Decode受内存限制，并随批处理大小缩放。排队延迟是一个操作问题。网络是一个物理距离问题。你需要不同的指标，你需要百分位数，你需要一个单一的组合来说明“用户是否得到了他们所期望的”——这很好。

## 这个概念

### TTFT -到第一个令牌的时间


当提示很长时，预填充占主导地位。在H100上的lama-3.3- 70b FP8上，32k提示需要~800 ms的纯预填充。队列时间是调度程序在负载下的行为。网络请求是包括TLS在内的连线时间。TTFT是用户看到任何流返回之前的延迟时间。

### TPOT / ITL -令牌间延迟

一个数量有许多名称。`TPOT` (time per output token), `ITL` (inter-token latency), `decode latency per token` — all the same. 它是第一个流令牌之后连续流令牌之间的时间间隔。


在相同的lama-3.3- 70b H100堆栈上，使用分块预填充，TPOT平均为~7 ms。如果没有分块预填充，在相邻序列的长预填充期间，TPOT可以达到50ms。看P99，不要吝啬。

### E2E延迟


对于长输出（bbb500个令牌），E2E是tpot主导的。对于具有长提示的短输出，E2E是ttft主导的。报告输出长度条件的E2E。

### 吞吐量


聚合度规。告诉你车队的效率。不告诉你个人要求健康。

### 你真正关心的度规


SLO是一个多约束。只有当所有约束条件都满足时，请求才是“好的”。好东西就是份额。高吞吐量在60%的货物是失败的。较低的吞吐量达到99%是目标。

到2026年，goodput将成为MLPerf Inference v6.0提交和AI平台提供商内部SLA跟踪中使用的指标。

### 为什么平均值是错误的统计

LLM延迟分布是右倾斜的。具有一个长预填充邻居的解码批可以以TPOT ~7 ms发送500个令牌，以TPOT ~60 ms发送20个令牌。平均TPOT为9 ms。P99 TPOT为65 ms。用户经常点击P99——这就是他们离开的原因。

总是报告三重（P50, P90, P99）。对于用户体验，P99是需要优化的。

### 参考编号-羊驼-3.1- 8b -指导TRT-LLM， 2026

- 平均TTFT: 162 ms
- 平均TPOT: 7.33 ms
- 平均端到端时间：1093毫秒
- P99 TPOT：根据分块预填充配置变化10-25毫秒。

这些是公布的NVIDIA参考点。它们随着模型大小（70B将显示3-5倍）、硬件（H100 vs B200 ~3倍）和负载而变化。

### 测量陷阱

两个最常用的2026基准测试工具在相同运行的TPOT上存在分歧：

- **NVIDIA GenAI-Perf**：将TTFT排除在ITL计算之外。ITL从令牌2开始。
- **LLMPerf**：包括TTFT。ITL从令牌1开始。

对于TTFT 500毫秒的请求，在700毫秒的总解码中有100个输出令牌，GenAI-Perf报告选择工具会改变数字。

总是说明是哪个工具。总是发布定义。

### 构建SLO

2026年70B聊天模式面向消费者的合理SLO：

- TTFT P99 <= 800 ms。
- TPOT P99 <= 25 ms。
- 对于<300个令牌的输出，E2E P99 <= 3 s。
- Goodput目标>= 99%。

企业slo收紧TTFT (200- 400ms)，放松E2E。关键是将它们写下来，测量所有三个，并将goodput作为单个组合来跟踪。

### 如何测量

- 运行真实的流量或现实合成(LLMPerf与
- 为基准测试运行设定2倍的峰值并发性目标。
- 运行30-50次迭代，取组合样本的百分位数。
- 发布工具名称，工具版本，模型，硬件，并发，提示分发。

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| TTFT | "time to first token" | Queue + network + prefill; dominated by prefill at long prompts |
| TPOT | "time per output token" | Memory-bound decode cost per token after first |
| ITL | "inter-token latency" | Same as TPOT in most tools (not all — see GenAI-Perf) |
| E2E | "end to end" | TTFT + TPOT * output_len; response-side network on top |
| Throughput | "tok/s" | Fleet efficiency; useless without latency percentiles |
| Goodput | "SLO-met rate" | Fraction of requests meeting every SLO constraint simultaneously |
| P99 | "tail" | 1-in-100 worst-case latency; the user experience metric |
| SLO multi-constraint | "the joint" | AND of all three latency bounds; a request fails if any one is violated |
| GenAI-Perf vs LLMPerf | "the tool trap" | Tools disagree on whether ITL includes TTFT |
