# 法学硕士的FinOps——单位经济学和多租户属性

> 传统FinOps在LLM支出上有所突破。成本是代币交易，而不是资源正常运行时间。标签不映射——API调用是一个事务，而不是一个资产。工程决策（提示设计、上下文窗口、输出长度）是财务决策。2026年的剧本在第一天就有三个属性维度：每用户(四个令牌层-提示，工具，内存，响应-一个桶隐藏花费。多租户产品的执行阶梯：每个租户的费率限制（预期峰值的2-3倍，明确429 +重试）；每日消费上限（1.5-3倍合同上限，触发利率收紧+警报）；杀死开关花费z-score b> 4（自动暂停+页面呼叫）。归因模式：标记-聚合、遥测-合并（跟踪- id→计费；最高精度）、抽样-外推、基于模型的分配、事件源、实时流。单位度量：每个解析查询的成本，每个生成工件的成本——而不是$/M令牌。追溯标签总是遗漏；请求创建时的仪器。

**Type:** Learn
**Languages:** Python (stdlib, toy cost-attribution simulator with kill switch)
**Prerequisites:** Phase 17 · 13 (Observability), Phase 17 · 14 (Caching)
**Time:** ~60 minutes

## 学习目标

- 解释为什么传统的FinOps（标签+层级）会破坏LLM支出，并说出三个新的归因维度。
- 列举四个令牌层（提示、工具、内存、响应），以及为什么单桶计费隐藏了成本。
- 为多租户产品设计一个执行阶梯（费率→支出上限→终止开关）。
- 选择一个单位度量（每个解析查询/工件的成本），而不是$/M令牌。

## 这个问题

你的账单上写着4万美元。你不知道：
- 哪个租客花掉了这笔钱。
- 是哪个产品特性驱动了它。
- 是否有个人用户滥用。
- 无论是提示膨胀、工具调用还是内存放大都是罪魁祸首。

提供者端的标记和聚合适用于云资源（EC2、S3），其中标记传播到行项。LLM API调用不会自动标记——您必须在调用现场标记用户/任务/租户，然后进行调用。追溯归因总是漏掉一些边缘情况。

## 这个概念

### 三个归因维度

**每用户** (推动座位定价，扩展对话，识别高级用户。

**每任务** (驱动功能优先级，删除昂贵功能的决策。

**每租户** (驱动单位经济，续订价格，等级门槛。

第一天在呼叫地点通知所有三个人。追溯总是更糟。

### 四个令牌层

| Layer | Example | Typical % of total |
|-------|---------|---------------------|
| Prompt | system + user input | 40-60% |
| Tool | tool-call results fed back | 20-40% (agent workloads) |
| Memory | prior conversation / retrieved docs | 10-30% |
| Response | model output | 10-30% |

将这四种方法放在一起会使优化变得盲目。在你的归因图式中分解它们。

### 执行阶梯

1. **每个租户的费率限制**。预期峰值的2-3倍。返回429房客看到摩擦；没什么好惊讶的。

2. **每个租户的每日消费上限**。1.5-3倍收缩天花板。触发：收紧速率限制+提醒客户成功。

3. **终止开关**花费z-score > 4相对于租户基线。Auto-pause租户;页面随叫随到;升级到ops + CS。

### 归因模式

- **标记和聚合**：邮票元数据头；聚合后。简单的;粗糙。
- **遥测joiner**：通过跟踪id连接跟踪到计费。最高的精度。成熟的团队会做什么。
- **抽样+外推**：抽样5-10%，乘以。对于粗糙的花费具有成本效益；了尾巴。
- **基于模型的分配**：回归推断成本驱动因素。对于没有标记的遗留数据。
- 事件源：成本作为流中的事件（Kafka / Kinesis）。实时的。
- **实时流**：仪表板更新亚秒。

### 每X的成本是单位度量

$/M代币是供应商的语言。产品指标:

- 每个已解决的支持票的成本。
- 每篇生成文章的成本。
- 每个成功代理任务的成本。
- 每用户会话分钟的成本。

将成本与产品结果联系起来。否则优化是不锚定的。

### 成本归因轨迹形状

```
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

每次呼叫都发出声音。存储在数据湖中。每个维度的汇总。第17·13阶段的可观测性堆栈就是它所在的地方。

### 复合储蓄组合

栈：缓存+批处理+路由+网关。四个都有：
- 缓存L2（阶段17·14）：~10倍便宜的输入。
- 批次（第17·15期）：5折。
- 走向廉价模式（第17·16阶段）：成本降低60%。
- 网关效率（阶段17·19）：冗余+重试。

最佳情况：初始基线的5-10%。大多数团队都有2-3个杠杆；很少有人把四个都叠起来。

### 你应该记住的数字

- 归因维度：每个用户、每个任务、每个租户。
- 四个令牌层：提示、工具、内存、响应。
- 死亡开关：花费z-score b> 4。
- 单位度量：每个解析查询的成本，而不是$/M令牌。
- 堆叠优化：可能是基线的5-10%。

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Per-user attribution | "user-level cost" | `user_id` stamped on every call |
| Per-task attribution | "feature cost" | `task_id` + `route` identify product surface |
| Per-tenant attribution | "customer cost" | `tenant_id`; drives unit economics |
| Four token layers | "cost layers" | prompt + tool + memory + response |
| Rate limit | "429 guard" | Per-tenant ceiling enforced at gateway |
| Daily spend cap | "daily ceiling" | Tenant-scoped budget with alert |
| Kill switch | "auto-pause" | Spend z-score > 4 triggers auto-suspension |
| Cost per resolved | "product unit metric" | Cost tied to product outcome, not tokens |
| Telemetry joiner | "trace-to-billing" | Highest-accuracy attribution pattern |
| Stacked optimization | "cache+batch+route+gateway" | Compounding savings to ~5-10% baseline |
