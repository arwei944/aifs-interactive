# Human-in-the-Loop: Propose-Then-Commit

> 2026年关于HITL的共识是具体的。它不是“代理询问，用户点击批准”。它是提议-然后提交：提议的操作被持久化到一个具有幂等键的持久存储；将意图、数据沿袭、触及的权限、爆炸半径和回滚计划提交给审核人员；确认后才承诺的；执行后验证，确认副作用确实发生。LangGraph的典型的失败模式是橡皮图章式的批准：单击“批准？”而不进行审查。文档化的缓解是带有明确检查表的挑战-响应。

**Type:** Learn
**Languages:** Python (stdlib, propose-then-commit state machine with idempotency)
**Prerequisites:** Phase 15 · 12 (Durable execution), Phase 15 · 14 (Tripwires)
**Time:** ~60 minutes

## 这个问题

代理执行一个操作。用户必须决定：批准还是不批准。如果决定是即时的，它可能不是审查。如果决策是结构化的，它是缓慢的，但值得信赖的。工程学上的问题是如何使结构化审查成为阻力最小的途径。

2023年的HITL模式是一个同步提示：“代理想要发送邮件给X，正文是Y -批准吗？”用户单击“审批”。每个人都觉得这个系统是安全的。在实践中，这种表面上的东西都是橡皮图章：用户审批得很快，审批预测得很少，当代理出错时，审计跟踪显示了用户无法回忆起的一长段审批历史。

2026模式——提议-提交——将HITL移动到持久的基板上，附加结构化元数据，并需要积极提交。每个托管代理SDK都有一个版本：LangGraphAPI名称不同；形状不会。

## 这个概念

### 提议-然后提交状态机

1. **建议。** Agent产生一个建议的操作。持久化到持久存储（PostgreSQL, Redis, durable Object）。包括:
   - 意图（为什么代理要这样做）
   - 数据沿袭（是什么来源导致了这个提议）
   - 涉及的权限（哪些范围/文件/端点）
   - 爆炸半径（最坏的情况是什么）
   - 回滚计划（如果提交了，我们如何撤消它）
   - 幂等键（每个提案唯一；重新提交返回相同的记录）
2. **表面。**审稿人看到具有所有元数据的提案。审稿人是一个人（不是审稿人本身）。
3. **提交。**积极肯定。执行该操作。
4. **核实。**执行后，回读并确认副作用。如果验证步骤失败，则系统处于已知的坏状态，并启动警报。

### 幂等键

如果没有幂等键，则在短暂失败后的重试可以重复执行已批准的操作。具体示例：用户批准“将100美元从A转到b”。网络信号。工作流重试。用户已经批准了一次，但是传输执行了两次。幂等键将批准与一个单一的、独特的副作用联系起来；第二次执行是无操作。

这是Stripe和AWS api使用的相同的等幂模式。在Microsoft代理框架文档中明确地将其用于代理审批。

### 持久性：为什么批准比流程更持久

审批等候室是代理商不拥有的一块土地。工作流程暂停（第12课）。当批准到达时，工作流从那个点开始恢复。这就是LangGraph配对的原因

### 橡皮图章式的批准和应对挑战的减缓

HITL的默认UI（“批准”/“拒绝”按钮）产生快速审批，没有真正的审查。文档化缓解：在启用Approve按钮之前，要求对特定问题给出肯定答案的挑战和响应检查表。具体的形状:

- “你知道这涉及到什么资源吗？”[]”
- “你证实爆炸半径是可以接受的吗？”[]”
- “如果失败，您有回滚计划吗？”[]”

不是为了官僚主义本身而官僚主义，而是一种强制功能。不能勾选复选框的审稿人要么要求澄清（升级），要么拒绝（安全默认）。Anthropic代理安全研究明确引用了清单驱动的HITL作为橡皮图章批准模式的缓解措施。

### 什么是重要的

并不是每一个行动都需要先提议后提交。2026年指南：

- **后续操作**（总是HITL）：不可逆转的写入、金融交易、出站通信、生产数据库更改、破坏性文件系统操作。
- **可逆操作**（有时是HITL）：对本地文件的编辑，暂存环境的更改，可逆写与明确的回滚。
- **读取和检查**（绝不是HITL）：读取文件，列出资源，调用只读API。

### post操作验证

“提交运行了”和“副作用发生了”是不一样的。网络分区和竞争条件可以产生一个工作流，认为它成功，而后端没有持久。verify步骤在提交后重新读取目标资源以进行确认。这与数据库事务的模式相同

### EU AI Act Article 14

第14条要求对欧盟的高风险人工智能系统进行有效的人力监督。“有效”不是装饰。监管语言明确排除了橡皮图章模式。在Microsoft Agent Governance Toolkit遵从性文档中的第14条审查中，“提出-然后提交”和“询问-响应”的形式经受住了考验。

## 使用它

Z0持久存储是一个JSON文件。幂等键是（thread_id, action_signature）的散列。驱动程序模拟三种情况：干净的审批流、短暂失败后的重试（不能重复执行），以及橡皮图章默认值与挑战-响应流的对比。

## 练习

1. 运行确认已批准提案的重试使用持久记录，而不重新执行。现在更改等幂键，使其包含时间戳，并显示重试双执行。

2. 扩展建议记录模拟验证步骤失败的执行。显示回滚自动触发。

3. 阅读微软代理框架确定玩具引擎缺少的API包含的一个元数据字段。添加它并解释它可以防止什么。

4. 为一个特定的行动设计一个挑战和回应清单（例如，“发布到公共Twitter账户”）。审稿人必须回答哪三个问题？为什么是这三个？

5. 选择一个同步的“Approve?”提示就足够了的情况（不需要持久存储）。解释原因，并说出你要接受的风险类别。

## 关键术语

| Term | What people say | What it actually means |
|---|---|---|
| Propose-then-commit | "Two-phase approval" | Persisted proposal + positive commit + verify |
| Idempotency key | "Retry-safe token" | Unique per proposal; second execution no-ops |
| Data lineage | "Where it came from" | The specific source content that led to the proposal |
| Blast radius | "Worst case" | Scope of effect if the action goes wrong |
| Rubber-stamp | "Fast approval" | "Approve" clicked without genuine review |
| Challenge-and-response | "Forcing checklist" | Reviewer must positively acknowledge specific questions |
| RequestInfoEvent | "MS Agent Framework primitive" | Durable HITL request with structured metadata |
| `interrupt()` / `waitForApproval()` | "Framework primitives" | LangGraph / Cloudflare equivalents of the same shape |
