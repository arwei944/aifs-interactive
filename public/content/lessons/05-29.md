# Dialogue status tracking

> I want to open a cheap restaurant in the north... In fact, it is moderate... And add Italian." Three rounds, three status updates. DST keeps the slot value dictionary synchronized for booking jobs.

**Type:** Build
**Languages:** Python
**Prerequisites:** Phase 5 · 17 (Chatbots), Phase 5 · 20 (Structured Outputs)
**Time:** ~75 minutes

## This question

In task-oriented dialogue systems, the user's goal is encoded as a set of slot value pairs: a slot can be added, changed or deleted in each user round. The system must read the entire conversation and correctly output the current state.

As long as one slot goes wrong, the system will book the wrong restaurant, arrange the wrong flight, or make the payment with the wrong credit card. DST serves as the hub between what the user says and what the backend executes.

Why the Master of Laws is still important in 2026:

- Compliance sensitive areas (banking, healthcare, air booking) require definite slot values rather than free generation.
- The tool still needs slot resolution before calling the api using a proxy.
- The multi-round correction is more difficult than it seems: "Actually, no. It's on Thursday."

Modern Pipeline: Classic DST concept + LLM extractor + structured output guardrail.

### Classic failure mode

- Cross-round co-references. "Let's continue to choose the first option." Which option needs to be addressed?
- "Coverage vs. add-on." The user said, "Add Italian." Are you a replacement dish or an addition dish?
- Implicit confirmation letter. "OK cool" - Is reservation accepted?
- "Corrected. "Let's set it at 7 p.m." The time must be updated without emptying other slots.
- Refer to the previous system discourse. "Yes, that's it." " ", "?

### Step 2: state update loop

```python
def update_state(state, utterance):
    new_state = dict(state)
    for slot, extractor in SLOT_EXTRACTORS.items():
        value = extractor(utterance)
        if value is not None:
            new_state[slot] = value
    for slot in NEGATION_CLEARS:
        if is_negated(utterance, slot):
            new_state[slot] = None
    return new_state
```

Three invariants:

- Never reset a slot that the user has not touched.
- A clear negation (" Don't worry about cooking ") must be clear.
- User correction (" Actually... ") It must be overwritten, not appended.

### Step 4: JGA evaluation

```python
def joint_goal_accuracy(predicted_states, gold_states):
    correct = sum(1 for p, g in zip(predicted_states, gold_states) if p == g)
    return correct / len(predicted_states)
```

Calibration: What is the correct rotation ratio for all slots obtained by the system? For MultiWOZ 2.4, the top 2026 systems: 80-83%. The systems within your field should exceed your narrow vocabulary; otherwise, the LLM baseline will beat you.

On a detected correction, overwrite the last-updated slot rather than appending. Hard to get right without LLM help. The modern pattern: always let the LLM regenerate the whole state from history rather than incrementally updating — this naturally handles corrections.

## Pitfalls

- **Full-history regeneration cost.** Letting the LLM regenerate state each turn costs O(n²) total tokens. Cap history or summarize older turns.
- **Schema drift.** Adding new slots post-hoc breaks old training data. Version your schema.
- **Case sensitivity.** "Italian" vs "italian" vs "ITALIAN" — normalize everywhere.
- **Implicit inheritance.** If the user has previously specified "for 4 people," a new request for a different time should not clear people. Always pass the full history.
- **Free-form vs closed-set.** Names, times, and addresses need free-form slots; cuisines and areas are closed. Mix both in the schema.

## Use It

The 2026 stack:

| Situation | Approach |
|-----------|----------|
| Narrow domain (one or two intents) | Rule-based + regex |
| Broad domain, labeled data available | LDST (LLaMA + LoRA on MultiWOZ-style data) |
| Broad domain, no labels, prod-ready | LLM + Instructor + Pydantic schema |
| Spoken / voice | ASR + normalizer + LLM-DST |
| Multi-domain booking flow | Schema-guided LLM with per-domain Pydantic models |
| Compliance-sensitive | Rule-based primary, LLM fallback with confirmation flow |

## Key terms

| Term | What people say | What it actually means |
|------|-----------------|-----------------------|
| DST | Dialogue state tracking | Maintain the slot-value dict across dialogue turns. |
| Slot | Unit of user intent | Named parameter the backend needs (cuisine, date). |
| Domain | The task area | Restaurant, hotel, taxi — sets of slots. |
| JGA | Joint Goal Accuracy | Fraction of turns where every slot is correct. All-or-nothing. |
| MultiWOZ | The benchmark | Multi-domain WOZ dataset; standard DST evaluation. |
| Ontology-free DST | No schema | Generate slot names and values directly, no fixed list. |
| Correction | "Actually..." | Turn that overwrites a previously-filled slot. |
