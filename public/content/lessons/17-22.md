# 负载测试LLM api -为什么k6和蝗虫存在

> 传统的负载测试器不是为流响应、可变输出长度、令牌级指标或GPU饱和度而设计的。大多数球队都有两个陷阱。GIL陷阱：Locust的令牌级测量在Python GIL下运行令牌化，在高并发性下与请求生成竞争；令牌化积压会增加报告的令牌间延迟——您的客户端才是瓶颈，而不是服务器。提示均匀性陷阱：相同的提示在一个循环中测试令牌分布上的一个点；真实流量具有可变长度和多种前缀匹配。LLMPerf用2026年的工具映射：用于标记级精度的LLM-specialized (GenAI-Perf, LLMPerf, LLM-Locust, guidellm)；**k6 v2026.1.0** + **k6 Operator 1.0 GA（2025年9月）** -流感知，Kubernetes-native通过testron /PrivateLoadZone CRDs分发，最适合CI/CD门；Go恒速饱和贝吉塔；Locust 2.43.3仅支持LLM-Locust流扩展。负载模式：稳态、斜坡、尖峰（自动缩放测试）、浸泡（内存泄漏）。

**Type:** Build
**Languages:** Python (stdlib, toy realistic-prompt generator + latency collector)
**Prerequisites:** Phase 17 · 08 (Inference Metrics), Phase 17 · 03 (GPU Autoscaling)
**Time:** ~75 minutes

## 学习目标

- 解释两种反模式（GIL陷阱、提示均匀性陷阱），它们使通用负载测试器适合LLM api。
- 为给定的目的选择一个工具：LLMPerf（基准测试运行），k6 +流扩展（CI门），guidellm（大规模合成），GenAI-Perf （NVIDIA参考）。
- 设计四种负载模式（稳定、斜坡、尖峰、浸泡）并命名每种捕获的故障模式。
- 使用输入令牌的mean + stddev构建一个真实的提示分布，而不是固定长度。

## 这个问题

您在500个并发用户下对LLM端点进行了k6测试。它举行。你发货。在200个实际用户的生产中，服务下降了- P99 TTFT爆炸了，gpu被钉住了。

发生了两件事。首先，k6发送了500个相同的提示—您的请求合并和前缀缓存使您看起来像是在处理500个并发解码，而实际上只处理一个。其次，k6不会像眼睛体验的那样跟踪流响应的令牌间延迟；它看到的是一个HTTP连接，而不是以不同的间隔到达的500个令牌。

llm的负载测试是它自己的学科。

## 这个概念

### GIL陷阱（蝗虫）

Locust使用Python并在GIL下运行令牌化客户端。在高并发性下，标记器排在请求生成之后。报告的令牌间延迟包括客户端令牌化积压。你觉得服务器太慢了；这是测试装置。

修复：LLM-Locust扩展将标记化移动到单独的进程，或使用编译语言工具（k6， llm - perf使用tokenizer .rs）。

### 即时一致性陷阱

所有已知的负载测试器都允许您配置一个提示符。在10,000次迭代的循环测试中，每次都发送完全相同的提示。服务器每次看到相同的前缀-前缀缓存命中率接近100%，吞吐量看起来很棒。

修复：样本从提示分发。LLMPerf使用

### 四种负载模式

1. **稳态** - RPS恒定30-60分钟。捕获：基线性能回归。
2. 斜坡-线性增加RPS从0到目标超过15分钟。捕获：容量断点、预热异常。
3. **脉冲** -突然3-10倍的RPS 2分钟，然后回来。捕获：自动缩放延迟，队列饱和，冷启动影响。
4. **浸泡** -稳定状态4-8小时捕获：内存泄漏、连接池漂移、可观察性溢出。

### 2026工具映射

**LLMPerf** (Anyscale) - Python但rust支持的标记化。意思是/ stddev提示。Streaming-aware。性能运行的最佳默认值。

**NVIDIA GenAI-Perf** - NVIDIA的参考。使用Triton客户端；全面的度量覆盖。注意它的ITL不包括TTFT；LLMPerf包含它。两个工具为同一台服务器生成不同的TPOT。

**LLM-Locust** (TrueFoundry) -修复GIL陷阱的蝗虫扩展。熟悉的蝗虫DSL +流参数。

**指南** -大规模合成基准测试。

**k6 v2026.1.0** + **k6 Operator 1.0 GA（2025年9月）**：
- k6本身（Go，已编译，无GIL）添加了流感知指标。
- k6运营商使用testron / PrivateLoadZone crd进行Kubernetes-native分布式测试。
- 最适合CI/CD门和SLA测试。

**贝吉塔** -走，比k6简单。恒定速率HTTP饱和。不支持llm，但适合网关/速率限制测试。

**蝗虫2.43.3股票** -有GIL陷阱LLM。只支持LLM-Locust扩展。

### 洛杉矶之门

在PR上运行k6：

- 在基准RPS上进行30-50次迭代。
- 栅极：P50/P95 TTFT， 5xx < 5%， TPOT低于阈值。
- 一有漏洞就破坏建筑。

### 现实的即时分配

从真实的流量样本（如果有的话）或从发布的发行版（例如，ShareGPT提示聊天，HumanEval提示代码）构建。将平均值+ stddev提供给LLMPerf。不惜一切代价避免一个提示符的循环。

### 你应该记住的数字

- k6运营商1.0 GA: 2025年9月。
- K6 v2026.1.0：流感知度量。
- 典型的LLMPerf运行：并发X的100-1000个请求。
- 典型的CI门：每个PR 30-50次迭代。
- 四种模式：平稳，坡道，尖峰，浸泡。

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| LLMPerf | "the LLM harness" | Anyscale benchmark tool, streaming-aware |
| GenAI-Perf | "NVIDIA tool" | NVIDIA reference harness |
| LLM-Locust | "Locust for LLMs" | Locust extension fixing GIL trap |
| guidellm | "synthetic benchmark" | Large-scale synthetic tool |
| k6 Operator | "K8s k6" | CRD-based distributed k6 |
| GIL trap | "Python client overhead" | Tokenization backlog inflates reported latency |
| Prompt-uniformity trap | "single-prompt lie" | Loop with same prompt hits cache, inflates throughput |
| Steady-state | "constant load" | Flat RPS for N minutes |
| Ramp | "linear up" | 0 to target over duration |
| Spike | "burst test" | Sudden multiplier then revert |
| Soak | "long test" | Hours for leak detection |
