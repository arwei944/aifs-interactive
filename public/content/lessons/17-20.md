# llm的影子流量、Canary Rollout和渐进式部署

> LLM的推出结合了软件部署中最难的部分：没有单元测试、分散的故障模式、延迟的信号。顺序是(1)影子模式——重复产品请求到候选模型，记录，与零用户影响比较；抓住明显的分销问题，但不能保证质量；(2)金丝雀式推出——流量递进变换10%→25%→50%→75%→100%，每一步设闸；跟踪延迟百分比、成本/请求、错误/拒绝率、输出长度分布、用户反馈率；(3)稳定性确认后，对不同方案进行A/B测试。非确定性是不可约的-由于GPU FP非关联性加上批大小方差，在具有相同输入的运行中高达15%的准确性变化。成本是可变的，而不是恒定的——一个好20%的模型每次通话可能要贵3倍。回滚速度是决定性的：如果回滚需要重新部署，那么您太慢了。策略保存在config/flags中；模型驻留在具有固定摘要的注册表中；回滚=翻转策略+恢复阈值+在秒内固定旧模型。

**Type:** Learn
**Languages:** Python (stdlib, toy canary-progression simulator)
**Prerequisites:** Phase 17 · 13 (Observability), Phase 17 · 21 (A/B Testing)
**Time:** ~60 minutes

## 学习目标

- 区分阴影模式（零影响比较）、金丝雀模式（实时流量渐进式）和A/B模式（稳定确认比较）。
- 列举五个llm特定的金丝雀指标（延迟、成本/请求、错误/拒绝、输出长度分布、用户反馈）。
- 解释为什么LLM不确定性（高达15%）改变了“稳定”在推出中的含义。
- 设计一个只需几秒钟（策略翻转）而不是几小时（重新部署）的回滚路径。

## 这个问题

你推出了一款新机型。离线评估显示3%的准确性提高。你在生产中打开它。在24小时内，成本上升了40%，用户表示反对的比例上升了8%，三个客户的投诉报告了“奇怪的答案”。你回滚。重新部署需要3个小时。你的周末被毁了。

这一切都是可以避免的。阴影模式会在任何用户看到之前抓住40%的成本峰值。当拇指向下移动时，金丝雀会停在10%的位置。策略标志回滚需要30秒。纪律填补了“线下评价看起来不错”和“真实用户很高兴”之间的空白。

## 这个概念

### 阴影模式

候选人收到与生产相同的请求；输出被记录下来，而不是返回给用户。零用户影响。日志:

- 输出内容（与生产不同）。
- 令牌计数（成本增量）。
- 延迟。
- 拒绝和错误。

捕获：成本膨胀，长度回归，明显的拒绝变化，硬错误。没有捕获：用户会感知到的质量delta。影子是烟雾测试，而不是质量测试。

### 金丝雀推出

有闸门的渐进式交通换挡。典型进度：1%→10%→25%→50%→75%→100%。每个步骤的5个指标：

1. **潜伏期百分位数** - P50， P95, P99。突破：金丝雀有P99 > 1.5倍基线。
2. **每个请求的成本** -混合$。违约：>高于基线20%。
3. 错误/拒绝率** - 5xx加上明确拒绝。突破：2倍基线。
4. **输出长度分布** -平均值+ P99。违反：分配转移。
5. **用户反馈率** -拇指向下/票据归档。违规：1.5倍基线。

### 不确定性是新的方差

相同的投入产生不相同的产出。原因:

- GPU FP非关联性（浮点约简顺序因批而异）。
- 批大小差异（在128批和16批中提示相同）。
- 采样（温度> 0）。

测量：在相同的eval集上运行到运行的准确度变化高达15%。“稳定”在一次发布中意味着度量标准在预期的变化范围内，而不是与基线相同。将门设置在噪声底之上。

### 成本是一个变量

一个好20%的型号每次通话可能要贵3倍。成本/请求是五大门之一。发布打破单位经济效益的“更好”模式是一个回滚案例。

### 回滚是武器

- 策略标志（特征标志系统）：配置中的翻转百分比；只需要几秒钟。
- 模型固定（注册表摘要）：固定的模型不会自动升级。
- 回滚=恢复标志+设置固定摘要到前一个。秒，不是小时。

如果您的堆栈需要重新部署以回滚，请在滚之前修复它。

### 工具

**Argo Rollouts** / **Flagger** - Kubernetes渐进式交付控制器。集成Istio/链路加权路由。

**Istio加权路由** -服务网格级流量分割。

**KServe / Seldon Core -内置金丝雀模式服务。

**功能标志** - LaunchDarkly， Flagsmith, Unleash。策略级翻转，无需重新部署。

### 度量节奏

金丝雀门根据交通流量每5-15分钟检查一次。1%的流量以10 req/min的速度提供每个窗口50-150个数据点——对于延迟来说足够了，但是对于用户反馈来说很嘈杂。10%给予~10倍以上。进程应该暂停足够长的时间，以便在每一步积累足够的样本。

### A/B步骤是可选的

如果新模式明显不同（不同的行为，不同的成本曲线，不同的基调），在金丝雀通过后进行50%的A/B测试。如果只是一个改进版本，当金丝雀门通过时跳到100%。

### 你应该记住的数字

- 金丝雀级数：1%→10%→25%→50%→75%→100%。
- 非确定性上限：在相同的输入上运行到运行的方差高达15%。
- 五个指标：延迟、成本、错误/拒绝、输出长度、用户反馈。
- 成本门槛：超过基线20%即为违约。
- 回滚：秒，而不是小时。

## 练习

1. 运行注入25%的成本回归。金丝雀在哪个阶段停止？
2. 你的新模型有3%的离线精度增益，但成本/请求是+18%。它是一艘船吗？取决于策略-写入两条路径。
3. 设计一个端到端不到60秒的回滚。列出所需的基础设施。
4. 不确定性在你的评估中显示为±7%。设置金丝雀门，这样你就不会误报。你用什么乘数？
5. 暗影模式在金丝雀模式之前消耗40%。编写在阴影中触发的警报规则。

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Shadow mode | "duplicate to new" | Zero-impact send-to-candidate for logging |
| Canary | "progressive traffic" | Gradual user-exposed rollout with gates |
| Gates | "rollout checks" | Metric thresholds that block progression |
| Non-determinism | "LLM variance" | Irreducible run-to-run differences |
| Policy flag | "flag flip rollback" | Config-level rollback, seconds not hours |
| Model pin | "registry digest" | Immutable reference to a model version |
| Argo Rollouts | "K8s progressive" | Kubernetes-native canary/rollback controller |
| KServe | "inference K8s" | Model serving with canary primitives |
| Istio weighted | "mesh split" | Service-mesh traffic splitter |
