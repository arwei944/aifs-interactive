# 前缀重工作负载的SGLang和RadixAttention

> SGLang将KV缓存视为存储在基数树中的一级可重用资源。在vLLM调度请求FCFS（先到先服务）的地方，SGLang的缓存感知调度程序优先处理具有较长共享前缀的请求——实际上是深度优先的基数遍历，因此热分支保留在HBM中。在具有类似sharept的1K提示的Llama 3.1 8B上，SGLang达到~16,200 tok/s，而vLLM达到~12,500 tok/s，优势约为29%。对于前缀较多的RAG工作负载，优势达到6.4倍。在语音克隆型工作负载下，缓存命中率清除了86%。2026年部署在xAI、LinkedIn、Cursor、Oracle、GCP、Azure、AWS等40多万个gpu上。问题在于，当前缀排序不一致时，6.4x的数字就会消失——排序是工程师的杠杆。

**Type:** Learn
**Languages:** Python (stdlib, toy radix-tree cache + cache-aware scheduler)
**Prerequisites:** Phase 17 · 04 (vLLM Serving Internals), Phase 14 (Agentic RAG)
**Time:** ~75 minutes

## 学习目标

- 图RadixAttention：前缀如何存储在基数树中，KV块如何在同一分支上的序列中共享。
- 解释缓存感知调度以及为什么FCFS对于前缀密集的流量是错误的。
- 计算给定前缀缓存命中率和提示长度分布的工作负载的预期加速。
- 说出让6.4倍的数字变得真实而不是失去上行空间的快速排序规则。

## 这个问题

经典服务将每个请求的提示视为不透明的。即使5,000个RAG请求都以相同的2,000个令牌系统提示符和相同的检索序言开始，vLLM也会将2,000个令牌前缀前缀添加5,000次。GPU一遍又一遍地做同样的工作。

观察结果：代理和RAG工作负载中的提示几乎总是共享长前缀。系统提示、工具模式、少量示例、检索头、会话历史记录——所有这些都在请求之间重复。如果您为该前缀存储了一次KV缓存并重用它，则不会再次预填充它。

RadixAttention就是这样做的。令牌在基数树中索引；每个节点拥有KV块，用于从根节点开始的路径上的令牌序列。一个新的请求遍历树：任何令牌匹配的节点都会重用该节点的KV块。预填充成本与“new”后缀成比例，而不是与完整提示符成比例。

挑战在于日程安排。如果两个请求共享2,000个令牌前缀，而第三个请求仅共享相同前缀的200个令牌，那么您希望将两个长共享请求一起提供服务，以便长前缀保留在HBM中。FCFS的做法正好相反——它为最先到达的人提供服务，可能会在下一个长前缀请求到达之前驱逐热分支。

## 这个概念

### 将基树作为KV索引

基数树（紧凑树）存储令牌序列。每个节点拥有一个令牌范围，并为该范围计算KV块。子序列扩展一个或多个标记。

```
root
 |- "You are a helpful assistant..."  (2,000 tokens, 124 KV blocks)
      |- "Context: <doc A>..."        (500 tokens, 31 blocks)
           |- "Question: Alice..."    (80 tokens, 5 blocks)
           |- "Question: Bob..."      (95 tokens, 6 blocks)
      |- "Context: <doc B>..."        (520 tokens, 33 blocks)
```

一个新的请求会伴随着系统提示+“Context: <doc A>”+“Question: Carol”。调度器遍历：系统前缀匹配（重用124个块），doc-A分支匹配（重用31个块），然后仅为“Question: Carol”（4个块）分配新的块。预填充成本：4块新令牌。没有树：160个街区。预填充节省约40倍。

### 支持缓存调度

如果缓存发生震荡，基于基数树的重用是没有意义的。两项关键政策：

1. * * * *深度优先调度。当从队列中选择下一个请求时，优先选择扎根于与当前运行集相同分支的请求。这使热树枝保持固定。
2. **LRU在分支级，而不是块级。清除整个分支（从使用时间最短的叶子开始）而不是单个块，因此缓存形状与基数形状匹配。

FCFS违反了这两者。共享2000个令牌的请求位于共享50个令牌的请求后面，然后2000个令牌的分支被驱逐，以接纳50个令牌的分支。

### 应该记住的基准数字

- Llama 3.1 8B, H100， ShareGPT 1K提示：SGLang ~16,200 tok/s vs vLLM ~12,500（~29%边缘）。
- 前缀重的RAG（相同的系统+相同的文档，不同的问题）：在SGLang上高达6.4x。
- 语音克隆工作负载：前缀缓存命中率86.4%。
- SGLang客户的生产命中率：50-99%，取决于及时的纪律。
- 2026年将部署在400,000+ gpu上。

### 顺序问题

6.4x的数字依赖于一致的提示模板排序。如果您的客户机构造提示为在人类看来是共享的前缀，在基数树中却是两个不同的序列。

工程师的杠杆：你的提示模板是一个缓存键。调整顺序。把所有不可变的东西（系统、工具、模式）放在第一位。接下来放入检索上下文。把用户问题放在最后。不要在前缀中穿插动态内容。

研究中的真实案例：将动态内容移出可缓存前缀使一次部署的缓存命中率从7%提高到74%。

### RadixAttention输赢在哪里

成功:
- 相同的检索序言，不同的问题。
- 代理（相同的工具模式，不同的查询）。
- 聊天与长系统提示。
- 具有重复序言的语音/视觉工作负载。

丢失（返回到vllm级别的吞吐量）：
- 具有独特提示的单次生成（代码完成，没有系统提示的开放式聊天）。
- 动态提示，其中每个请求将唯一内容穿插到前缀中。

### 为什么这是一个调度器问题，而不仅仅是一个内核问题

您可以将KV重用实现为一个内核技巧。SGLang的见解是，只有调度程序保持热分支驻留时，重用才有价值。天真的“可用时重用”策略会在混合负载下搅动缓存。基数树索引调度器将内核技巧转化为29%的生产优势。

### 与vLLM交互

这两个系统并不是严格的竞争对手。2026年vLLM添加了前缀缓存(差距缩小了，但没有完全消失——SGLang的整个堆栈是基数优先的；vLLM把它接了上去。对于前缀重用占主导地位的工作负载，SGLang仍然是默认值。对于没有强前缀模式的通用服务，vLLM仍然相同或更好。

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| RadixAttention | "the SGLang thing" | KV cache indexed as a radix tree so shared prefixes reuse blocks |
| Radix tree | "compact trie" | Tree where each node owns a token range and its KV blocks |
| Cache-aware scheduler | "hot-branch-first" | Scheduler that prefers requests sharing the resident branch |
| Prefix-cache hit rate | "how much of your prompt was free" | Fraction of prompt tokens served from reused KV blocks |
| FCFS | "first-come first-served" | Default scheduling that breaks prefix locality |
| Branch-level LRU | "evict the leaf" | Eviction policy matched to radix shape |
| Prompt template ordering | "the cache key" | The prompt's component order determines what the tree can share |
| System prompt pinning | "resident prefix" | Keep the immutable system portion pinned to avoid eviction thrash |
