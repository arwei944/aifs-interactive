# 分解预填充/解码- NVIDIA发电机和llm-d

> 预填充是计算绑定的；Decode是受内存限制的。在同一个GPU上运行这两个会浪费一个资源。分解将它们分离到单独的池中，并通过NIXL （RDMA/InfiniBand或TCP回退）在它们之间传输KV缓存。NVIDIA Dynamo （GTC 2025宣布，1.0 GA）位于vLLM/SGLang/TRT-LLM之上-其规划分析器+ SLA规划器自动匹配预填充：解码比率以满足slo。NVIDIA公布了这方面的吞吐量提升——developer.nvidia.com（2025-06）显示，在中等延迟状态下，DeepSeek-R1在GB200 NVL72 + Dynamo上的MoE提升了约6倍，而Dynamo产品页面（developer.nvidia.com，未标明日期）则宣传在GB300 NVL72 + Dynamo上的MoE吞吐量与Hopper相比提高了50倍。“30倍”的数字是由全栈Blackwell + Dynamo + DeepSeek-R1报告组成的社区总和；我们没有找到一个单一的主要来源，确切地说30倍，所以把它当作一个定向的主张。llm-d （Red Hat + AWS）是Kubernetes-native: prefill / decode / router作为独立的服务，具有每个角色的HPA。llm- d0.5增加了分层KV卸载，缓存感知LoRA路由，UCCL网络，缩放到零。经济学：对多个客户披露的内部汇总表明，当从托管服务切换到在恒定SLA下与Dynamo分解时，可以节省30-40%的200万美元级别的推断支出（即每年60 -80万美元）；200万美元→600-80万美元的具体数字是一个内部综合数据，而不是一个已发表的案例研究——把它作为一个数量级的锚点，而不是参考引用。短提示（<512个令牌，短输出）不能证明转移成本是合理的。

- 命名解聚合不起作用的条件（短提示，短输出）。
- 区分NVIDIA Dynamo （stack-above）和llm-d (Kubernetes-native)，并将它们与操作上下文相匹配。

## 这个问题

你用8台h100跑小羊驼3.3 70B。在混合工作负载下（长提示+短输出），gpu在解码期间空闲，因为大部分计算都花在预填充上。在不同的工作负载下（短提示+长输出），情况正好相反。并置的预填充+解码意味着两者都过度配置。

预算影响：20-40%的GPU时间浪费在错误的资源上。您正在购买H100计算来运行内存绑定解码，或者购买H100 HBM带宽来运行计算绑定预填充。两者都是昂贵的浪费。

分解将预填充和解码拆分到针对每个瓶颈大小的单独池中。KV高速缓存通过高带宽互连从预填充池传输到解码池。

## 这个概念

### 瓶颈为何不同

**预填充** -运行Transformer在一个向前的完整输入提示符。矩阵乘法占主导地位；的计算。H100 FP8提供~2000 TFLOPS的有效吞吐量。批处理效率很好——一个转发处理许多令牌。

**Decode** -每次生成一个令牌，每次迭代读取全部权重。Memory-bandwidth-bound。HBM3给出~ 3tb /s。批处理效率只有在高并发时才会很好——读取的权重会在批处理中分摊。

搭配它们：你买的gpu对两者都进行了优化。H100在这两方面都很好，但成本相同。在规模上，你想要H100 /计算量大的预填充池；解码池在H200 /内存繁重，或积极量化。

### 体系结构

```
            ┌──────────────┐
  Request → │    Router    │ ───────────────────────┐
            └──────┬───────┘                        │
                   │                                │
                   ▼ (prompt only)                  │
            ┌──────────────┐    KV cache    ┌───────▼──────┐
            │ Prefill pool │ ─── NIXL ────► │ Decode pool  │
            │  (compute)   │                │  (memory)    │
            └──────────────┘                └──────┬───────┘
                                                   │ tokens
                                                   ▼
                                                 Client
```

NIXL是NVIDIA的节点间传输。可用时使用RDMA/ ib，否则使用TCP回退。传输延迟是真实的——在70B FP8上，4k令牌提示的KV缓存通常为20- 80ms。这就是为什么简短的提示不能证明拆分是合理的：转让税超过了节省。

### Dynamo vs llm-d

**NVIDIA Dynamo** (GTC 2025宣布，1.0 GA)：
- 在vLLM， SGLang， TRT-LLM之上担任编导。
- Planner Profiler测量工作负载，SLA Planner自动配置预填充：解码比率。
- Rust核心，Python可扩展性。
- 吞吐量提升：NVIDIA报告称，在中延迟状态下，DeepSeek-R1 MoE在GB200 NVL72 + Dynamo上的性能提高了6倍（developer.nvidia.com, 2025-06）；关于Blackwell + Dynamo + DeepSeek-R1堆栈“高达30倍”的社区报告缺乏单一主源，应被视为定向。
- GB300 NVL72 + Dynamo：根据Dynamo产品页面（developer.nvidia.com，未注明日期），与Hopper相比，MoE吞吐量高达50倍。

**llm-d** (Red Hat + AWS, Kubernetes-native)：
- Prefill / decode / router作为独立的Kubernetes服务。
- 具有队列深度（预填充）/ KV利用率（解码）信号的每个角色HPA。
- 
- llm-d 0.5(2026)：分层KV卸载，缓存感知LoRA路由，UCCL网络，缩放到零。

如果你想要一个托管的堆栈之上的编排器，可以使用Dynamo。如果你想要kubernetes原生基元，并且致力于CNCF生态系统，请使用llm-d。

### 经济学

内部组合（不是单个已发表的案例研究-数量级锚）：

- $ 200万/年的推理花费在托管服务上。
- 切换到分解与发电机。
- 相同的请求卷，相同的P99延迟SLA。
- 报告节省：60万- 80万美元/年（减少30-40%）。
- 没有新的硬件。

我们从多个客户披露中综合了这个数字，而不是单一的可引用案例研究；最近公布的数据点是，使用Dynamo KV路由（Baseten）， Baseten的TTFT速度提高了2倍/吞吐量提高了61%。co, 2025-10)，以及VAST + CoreWeave的预测，在40-60% KV命中率下，代币/美元将增加60-130% （vastdata.com, 2025-12）。节省的资金来自对每个池的规模进行适当调整；前缀较多的工作负载（具有8K+前缀的RAG）比前缀均衡的工作负载受益更多。

### 什么时候不分解

- 提示< 512代币，输出< 200代币：转让税主导收益。
- 小集群（小于4个gpu）：池的多样性不够。
- 团队不能使用每个角色缩放操作两个GPU池：Dynamo有帮助，但不是微不足道。
- 没有RDMA结构：TCP传输税更重。

### 路由器与阶段17·11集成

分解路由器是kv缓存感知的（阶段17.11）。一个请求落在持有其前缀的解码池上——如果没有匹配，它的流是prefill→decode。命中率和分解复合——缓存感知路由器决定是否需要一个新的预填充。

### 对布莱克威尔的调查才是关键所在

GB300 NVL72 +发电机在Hopper基线上显示50倍的MoE吞吐量。MoE专家路由在预填充上计算量大，但在解码（专家缓存）上内存量大，因此反聚合是一种双赢。2026前沿模型服务以moe为主导（DeepSeek-V3，未来的GPT-5变体）。

### 你应该记住的数字

基准数据漂移- NVIDIA和推理堆栈每季度更新一次结果。报价前再检查。

- 在GB200 NVL72 + Dynamo上的DeepSeek-R1：在中等延迟状态下与基线相比，吞吐量约为6倍（developer.nvidia.com, 2025-06）；社区对完整的Blackwell + Dynamo堆栈的“高达30倍”的索赔是没有单一主要来源的定向聚合。
- GB300 NVL72 + Dynamo：与Hopper相比，MoE吞吐量高达50倍（developer.nvida.com，未注明日期）。
- 节省锚点（内部综合，不是单个案例研究）：在固定SLA下，每年200万美元的支出每年减少60 -80万美元。
- 分解阈值：提示>512个token +输出>200个token。
- 通过NIXL传输KV: 70B FP8上4k提示KV: 20-80 ms。

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Disaggregated serving | "split prefill/decode" | Separate GPU pools for each phase |
| NIXL | "NVIDIA transport" | Dynamo's inter-node KV transfer (RDMA/TCP) |
| NVIDIA Dynamo | "the orchestrator" | Stack-above coordinator for vLLM/SGLang/TRT-LLM |
| llm-d | "Kubernetes native" | Red Hat + AWS K8s disaggregated stack |
| Planner Profiler | "Dynamo auto-config" | Measures workload, configures pool ratios |
| SLA Planner | "Dynamo policy" | Auto-rate-matches prefill:decode to meet SLOs |
| `packDomain: rack` | "llm-d topology" | Pack prefill+decode on same rack for fast KV |
| UCCL | "unified collective" | llm-d 0.5 networking layer for scale-to-zero |
| MoE expert routing | "expert per token" | DeepSeek-V3 pattern; disaggregation helps |
