## 这个概念

### Langfuse(麻省理工学院)

- 600 + SDK安装/月，19k+ GitHub星级。
- 功能：跟踪，带有版本控制+游乐场的提示管理，评估（llm作为裁判，用户反馈，自定义），会话回放。
- 2025年6月：原商业模块（llm as-a-judge，注释队列，提示实验，Playground）在MIT下开源。
- 最强适用于：端到端可观察性与紧密的提示管理循环。

### Arize Phoenix（弹性许可证2.0）

- 更深层次的代理特定评估：跟踪聚类，异常检测，检索相关性的RAG。
- 本机OpenInference自动检测。
- 与管理的arisax配对用于生产。
- 没有及时的版本控制——定位为漂移/行为回归工具和更广泛的平台。
- 最适合：RAG相关性，行为漂移，异常检测。

### Comet Opik （Apache 2.0）

- 通过A/B实验自动优化提示。
- 护栏（PII修订，局部限制）。
- 法学硕士法官幻觉检测。
- Comet自己测量的基准：Opik日志+评估在23.44秒vs Langfuse 327.15秒（差距约14倍）-以供应商基准为导向。
- 最强优势：优化循环，自动实验，护栏强制执行。

### 行业数据

Per Maxim（2026年现场分析）：89%的组织具有代理可观察性；质量问题是最大的生产障碍（32%的受访者提到了这一点）。

### 选择一个

| Need | Pick |
|------|------|
| All-in-one with prompt management | Langfuse |
| Deep RAG evaluation + drift | Phoenix |
| Automated optimization + guardrails | Opik |
| Open licensing, no ELv2 | Langfuse (MIT) or Opik (Apache 2.0) |
| Datadog / New Relic integration | Any — they all export OTel |

### 这种模式哪里出错了

- **没有eval策略。**没有评估的跟踪只是昂贵的日志记录。
- **不接地的自卷式LLM-judge。**批评家模式（第05课）适用——法官需要外部工具来验证事实。
- **提示版本不绑定到跟踪。**当prod返回时，您不能分割到导致它的提示符。

## 练习

1. 将一周的OTel记录导出到Langfuse云（免费层）。哪些会话失败？为什么?
2. 为你的领域写一个法学硕士评判标准（事实正确性、语气、范围一致性）。测试50道痕迹。
3. 比较Langfuse的提示版本控制和Phoenix的跟踪集群。哪个能告诉你哪个破得更快？
4. 阅读Opik的护栏文档。将PII编校护栏连接到您的一个代理运行。
5. 在语料库中对这三个进行基准测试。忽略供应商公布的数字；衡量你自己。

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Tracing | "Spans collector" | Ingest OTel / SDK spans; index by session |
| Prompt management | "Prompt CMS" | Versioned prompts tied to traces |
| LLM-as-judge | "Automated eval" | Separate LLM scores agent output against a rubric |
| Session replay | "Trace playback" | Step through past runs for debugging |
| RAG relevancy | "Retrieval quality" | Does the retrieved context match the query |
| Trace clustering | "Behavioral grouping" | Cluster similar runs for drift detection |
| Guardrail enforcement | "Policy at log time" | PII/toxicity/scope checks on logged content |
