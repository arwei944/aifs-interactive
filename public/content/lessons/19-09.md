# 顶点09 -代码迁移代理（仓库级语言/运行时升级）

> 亚马逊的MigrationBench （Java 8到17）和b谷歌的App Engine py2到py3迁移器设定了2026年的标准。Moderne的OpenRewrite可以大规模地进行确定性AST重写。Grit针对的是编码风格DSL的相同问题。生产模式结合了这两者：用于安全重写的确定性基板加上用于模糊情况的代理层，用于每个分支构建的沙盒，以及在PR打开之前变为绿色的测试线具。最重要的是迁移50个真实的回购，并发布一个带有失败分类的通过率。

**Type:** Capstone
**Languages:** Python (agent), Java / Python (targets), TypeScript (dashboard)
**Prerequisites:** Phase 5 (NLP), Phase 7 (transformers), Phase 11 (LLM engineering), Phase 13 (tools), Phase 14 (agents), Phase 15 (autonomous), Phase 17 (infrastructure)
**运行阶段：** P5·P7·P11·P13·P14·P15·P17
**Time:** 30 hours

## 问题

大规模代码迁移是2026编码代理中最干净的生产应用程序之一。基本事实是显而易见的（迁移后测试套件通过了吗？），回报是真实的（Java-8舰队迁移是一个员工规模的项目），基准测试是公开的（MigrationBench 50-repo子集）。Moderne的OpenRewrite处理确定性方面的问题。代理层处理所有OpenRewrite食谱无法处理的事情：模棱两可的重写、构建系统漂移、长尾语法、传递依赖破坏。

您将构建一个代理，它接受一个Java 8仓库（或Python 2仓库）并生成一个绿色ci迁移的分支。您将度量通过率、测试覆盖率保存、每次回购的成本，并构建失败分类。与仅确定性基线的并排显示告诉您代理的值实际位于何处。

## 概念

管道有两层。确定性底层（Java的OpenRewrite， Python的libcst）可以安全地运行大量的机械重写：导入、方法签名、null安全编辑、使用资源尝试、废弃的API替换。它速度快，并产生可审计的差异。代理层（OpenAI Agents SDK或基于Claude Opus 4.7和GPT-5.4-Codex的LangGraph）处理食谱不能处理的情况：构建文件升级（Maven/Gradle/pyproject），传递依赖冲突，测试薄片，自定义注释。

每个repo获得一个Daytona沙盒，其中预安装了目标运行时。代理迭代：运行构建、对故障进行分类、应用修复、重新运行。硬性限制：每次回购30分钟，每次回购8美元，代理轮换20次。如果所有测试都通过了，并且覆盖率增量不为负，则分支打开PR。如果不是，则将回购归档到带有证据的失败类下。

失败分类是可交付的。在50个仓库中，什么坏了？传递deps吗?自定义注解?构建工具版本？与迁移无关的测试片？每个类都有一个计数和一个范例差异。未来的食谱作者可以针对前三名。

## 体系结构

```
target repo
      |
      v
OpenRewrite / libcst deterministic recipes
   (safe, fast, auditable, ~70-80% of fixes)
      |
      v
Daytona sandbox per branch
      |
      v
agent loop (Claude Opus 4.7 / GPT-5.4-Codex):
   - run build -> capture failures
   - classify failures (build, test, lint)
   - apply fix (patch or retry recipe)
   - rerun
   - budget: 30 min, $8, 20 turns
      |
      v
test + coverage delta gate
      |
      v (passed)
open PR
      |
      v (failed)
file under failure class + attach repro
```

## 堆栈

- 确定性底层：OpenRewrite （Java）或libcst （Python）
- Agent: OpenAI Agents SDK或LangGraph over Claude Opus 4.7 + GPT-5.4-Codex
- 沙盒：每个分支的Daytona devcontainers，预安装的目标运行时（Java 17 / Python 3.12）
- 构建系统：Maven， Gradle, uv （Python）
- 基准测试：Amazon MigrationBench 50-repo子集（Java 8到17），谷歌App Engine py2到py3 repos
- 测试工具：并行运行器，通过Jacoco （Java）或coverage.py （Python）进行覆盖
- 可观察性：Langfuse +跟踪每个不同块的每个repo包
- 仪表板：包含每个类计数和示例差异的故障分类仪表板

## 构建它

1. * *配方通过。**先运行OpenRewrite （Java）或libcst (Python) recipes。抓住70-80%的机械迁移。作为“配方”提交。

2. * *构建审判。Daytona沙盒：安装目标运行时，运行构建。如果是绿色，则跳到测试。如果是红色，就交给特工。

3. * *剂循环。* * LangGraph与工具:代理对故障（深度、语法、测试、构建工具）进行分类，并应用有针对性的修复。重新运行。

4. * *预算上限。**每次回购30分钟，8美元成本，20个代理回合。任何违约都将停止，并以当前的差异在“budget_exhausted”下存档。

5. **测试+覆盖门。**在构建变为绿色后，运行测试套件。将覆盖范围与基础回购进行比较。如果覆盖率下降超过2%，则在“coverage_regression”下进行归档。

6. * *公关开放。**成功后，推分支，打开PR，其中包含diff和应用的配方和代理撰写的提交的摘要。

7. * *故障分类。**对于每个失败的回购，用一个类标记：构建一个仪表板。

8. * * 50-repo运行。**跨MigrationBench子集执行。报告每个类的通过率、每次回购的成本、覆盖保留，以及仅比较与确定性的基线。

## 船这

Z0给定一个回购，它执行确定性配方，然后执行代理循环以生成绿色迁移分支，或者将该回购归档到一个分类法类下。

| Weight | Criterion | How it is measured |
|:-:|---|---|
| 25 | MigrationBench pass rate | 50-repo subset pass@1 |
| 20 | Test-coverage preservation | Mean coverage delta vs base |
| 20 | Cost per migrated repo | $/repo on passing runs |
| 20 | Agent / deterministic-tool integration | Fraction of fixes that OpenRewrite handled vs agent authored |
| 15 | Failure analysis write-up | Taxonomy completeness with exemplars |
| **100** | | |

## 练习

1. 只使用OpenRewrite运行迁移管道（没有代理）。将通过率与整个管道进行比较。确定哪些情况下单独使用代理是有区别的。

2. 实现“lint-clean”检查：迁移后，运行样式检查（Java为spottless， Python为ruff）。如果出现新的lint错误，则失败PR。测量覆盖保留但样式回归的比率。

3. 添加一个“最小差异”优化器：在代理的分支通过测试后，用第二次测试删除不必要的更改。报告diffi -size减少。

4. 扩展到第三个迁移：节点18到节点22。重用沙盒包装；将配方层替换为自定义代码模块。

5. 将首次绿色构建的时间（TTFGB）作为用户体验度量。目标：10分钟内达到50人。

## 关键术语

| Term | What people say | What it actually means |
|------|-----------------|------------------------|
| Deterministic substrate | "Recipe engine" | OpenRewrite / libcst: declarative AST rewrites with safety guarantees |
| Codemod | "Code-modifying program" | A rewrite rule that changes source code mechanically |
| Build drift | "Tool version skew" | Subtle Maven / Gradle / uv behavior changes between major versions |
| Failure class | "Taxonomy bucket" | A labeled reason a repo did not migrate: dep, syntax, test, build-tool, budget |
| Coverage delta | "Coverage preservation" | Change in test coverage % from base to migrated branch |
| Agent turn | "Tool-call round" | One plan -> act -> observe cycle in the agent loop |
| Budget exhaustion | "Hit the ceiling" | The repo consumed its 30-min / $8 / 20-turn limit without passing |
