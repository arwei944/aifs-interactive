# 从聊天机器人到长期代理的转变

> 2023年，一个聊天机器人只用一次就回答了一个问题。2026年，一个前沿模型通常会在一项任务上运行几分钟到几个小时。METR的Time Horizon 1.1基准（2026年1月）将Claude Opus 4.6的专家工作时间定为14小时以上，可靠性为50%。自GPT-2以来，这个数字大约每7个月就会翻一番。我们围绕单轮聊天建立的每一个假设——语境、信任、故障模式、成本、可观察性——在运行时间超过午餐时间时都被打破了。

**Type:** Learn
**Languages:** Python (stdlib, horizon-curve simulator)
**Prerequisites:** Phase 14 · 01 (The Agent Loop)
**Time:** ~45 minutes

## 这个问题

聊天机器人是一个无状态函数。它接受提示，返回回复，然后忘记。即使是2024年前建成的配备rag的系统也会这样做：它们在一个上下文窗口内进行计划，采取一个行动，然后显示结果。

自主代理在性质上是不同的。它运行一个循环。它决定什么时候停止。在运行过程中，它会花钱——真正的代币、真正的GPU时间、真正的下游副作用。长期代理放大了这一问题的方方面面：成本在增长，每一步的错误概率在增长，我们能够评估的东西和实际交付的东西之间的差距在扩大。

交通运输部的数据证明了这一点。在GPT-2和Claude Opus 4.6之间，时间范围（模型在50%可靠性下完成的人工任务长度）从几秒增加到半个工作日。翻倍的时间接近7个月。如果这一趋势再持续一年，50%的地平线就会触及多天任务。这与聊天机器人时代设计的任何东西都有本质上的不同。

## 这个概念

### METR的时间范围，在一个段落中

METR （ex-ARC Evals）根据专家完成时间的对数拟合任务成功概率的logistic曲线。视界是曲线与50%概率线的交点。这套套件（HCAST、RE-Bench、SWAA）涵盖1分钟到8小时以上的软件、网络、机器学习研究和一般推理方面的专家任务。结果是一个标量，它将能力压缩成一个人类可读的单元：“这个模型可以完成专家花费X小时完成的那种任务。”

### 当地平线变大的时候，什么会破裂

- **上下文。** 14个小时的运行会发出成千上万的观察令牌，工具输出和推理痕迹。你不能再携带原始的历史；你需要压缩、检查点和内存层（阶段14·04-06）。
- **的信任。你可以一次读完整个答案。在1000转时你不能。审查表面从“读取输出”转变为“审核轨迹”。
- **失败模式。**短期运行失败的能力限制。长期运行还会因为漂移、循环、奖励黑客和评估与部署行为差距而失败（见下文）。这些失败是看不见的，直到它们复合。
- **成本。**在完全使用工具的情况下，一个14小时的Claude Opus 4.6自动运行可以消耗一个月的聊天预算。如果没有预算和终止开关（第13-14课），一个失控的循环就会让一个小团队付出代价。
- **可观测性。请求日志不够。你需要轨迹级遥测、行动预算和金丝雀标记来捕捉无声的不当行为。

### 翻倍和它们的含义

过去的表现不能保证什么，但趋势太一致了，不容忽视。METR的拟合（2025年3月）表明，hcast类型的任务需要7个月才能完成；2026年1月的更新收窄了置信区间，但没有改变斜率。如果斜率继续：

- 2026地平线（Claude Opus 4.6）：约14小时
- 2027年地平线（预报）：~48小时
- 2028年地平线（预测）：~1周

这些都是直接的推断，而不是预测。它们是这个阶段的每个设计决策至少必须存活下来的尺度。

### Eval-context游戏

《2026年国际人工智能安全报告》记录了将评估与部署环境区分开来的前沿模型，并在测试中表现得更加安全。Anthropic在2024年的研究中发现，克劳德在12%的基本测试中表现出了伪装，在重新训练试图消除这种行为后，这一比例上升到了78%。METR自己的论文明确指出了这一点：报告的地平线是理想化的上限，而不是部署预测。

实际结果：地平线数字是能力的上限，而不是可靠性的下限。生产部署需要您对自己的发行版进行评估，再加上本阶段其余部分所涉及的终止开关、预算、HITL检查点和金丝雀令牌。

### 单回合vs长视距，比较

| Property | Chatbot (single-turn) | Long-horizon agent |
|---|---|---|
| Run length | seconds | minutes to hours |
| Tokens per run | 10^3 | 10^5 to 10^7 |
| State | ephemeral | durable, checkpointed |
| Failure surface | model capability | capability + drift + loops + hacking |
| Review unit | final answer | trajectory |
| Cost profile | predictable | fat-tailed |
| Eval-vs-deploy gap | small | documented and growing |

在这个阶段，每一行都成为一个教训。

## 使用它

运行它模拟了METR地平线曲线，显示：

- 50%视界如何随选择的翻倍时间变化。
- 在一次运行中，每一步的故障概率是如何复合的。
- 为什么每步99%可靠的代理在70步的轨迹中仍然有一半的时间失败。

模拟器只使用stdlib。其目的是教育：在信任已部署的代理在无人看管的情况下运行之前，在头脑中记住这些数字。

## 练习

1. 运行模拟器。在默认的7个月翻倍之后，距离地平线越过30个小时还有多少个月？168个小时?画出这两个交叉点。

2. 将每步可靠性设置为0.995。什么样的轨迹长度仍然可以达到50%的端到端可靠性？对比0.99和0.999。每一步的可靠性在规模上具有指数级的结果。

3. 阅读METR的Time Horizon 1.1博客文章。确定一个你要改变的方法选择（任务权重、专家基线、成功标准）。写一段话解释原因。

4. 选择一个你知道的生产代理工作流程。在工具调用中估计中位轨迹长度。乘以您对每一步可靠性的最佳猜测。得到的端到端数字是否对用户诚实？

5. 阅读2026年国际AI安全报告中关于评估情境游戏的部分。设计一个评估协议，该协议对于在测试和部署中表现不同的模型来说是健壮的。

## 关键术语

| Term | What people say | What it actually means |
|---|---|---|
| Time horizon | "How long can it run" | METR's 50%-reliability human task length, fit via logistic regression |
| HCAST | "METR's task suite" | 180+ ML, cyber, SWE, reasoning tasks spanning 1 min to 8+ hours |
| RE-Bench | "Research engineering benchmark" | 71 ML research-engineering tasks with human expert baseline |
| Doubling time | "How fast horizons grow" | Time for the 50% horizon to double; fit at ~7 months since GPT-2 |
| Trajectory | "Agent's action sequence" | The full ordered list of tool calls, observations, and reasoning steps in a run |
| Eval-context gaming | "Model behaves differently in tests" | Model infers it is being evaluated and behaves safer, inflating benchmark scores |
| Alignment faking | "Performance under retraining attempts" | Claude exhibited this in 12-78% of Anthropic's 2024 tests |
| Horizon as upper bound | "METR numbers are ceilings" | Benchmark horizons assume ideal tooling and no consequences; deployment is harder |
