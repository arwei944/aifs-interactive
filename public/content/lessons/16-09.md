# 并行/群/网络架构

> 与主管相反：没有中央决策者。代理读取共享事件总线，异步拾取工作，将结果写回来。LangGraph明确支持“群架构”，用于分散的动态环境。Matrix （arXiv:2511.21686）将控制流和数据流表示为通过分布式队列传递的序列化消息，以消除编排器瓶颈。权衡是明确的：可伸缩性的确定性和可追溯性。群拟合具有许多独立子问题的任务；它不适合需要单一连贯计划的任务。

**Type:** Learn + Build
**Languages:** Python (stdlib, `threading`, `queue`)
**Prerequisites:** Phase 16 · 05 (Supervisor Pattern), Phase 16 · 04 (Primitive Model)
**Time:** ~75 minutes

## 问题

主管扩大到几个工人。那几百呢？主管本身成为瓶颈：每个关于谁做什么的决定都要通过一个代理。一个缓慢的计划步骤会使整个系统停滞不前。

群体架构颠覆了设计。工人们从共享队列中挑选工作，而不是由中央计划器调度工作。“协调”被嵌入到事件总线语义中。没有协调器;系统会一直扩展，直到队列完成。

## 概念

### 的形状

```
                ┌──── shared queue ────┐
                │                      │
       ┌────────┼────────┐  ◄──────┬───┘
       ▼        ▼        ▼         │
     Worker  Worker  Worker   Worker
      A       B       C        D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
            results pool
```

没有协调器。每个worker重复：提取任务、处理、写入结果（以及可选的后续队列）。

### 当群体适应时

- **许多独立任务。**刮削、变换、分类。任务之间并不相互依赖。
- * * Variable-duration工作。**如果一些任务需要100毫秒，而另一些任务需要10秒，集群会自动平衡负载——快速的工人会拉下一个任务。主管必须预测持续时间。
- 吞吐量优于确定性。**你关心的是总完成时间，而不是严格的顺序。

### 当蜂群失败时

- * *下令工作流。**如果步骤3需要步骤2的输出，那么在步骤2完成之前，蜂群可能会发射步骤3。
- * *全球计划任务。**复杂的研究问题受益于计划者。一群研究人员产生独立的事实，而不是连贯的报告。
- * *调试。**由于没有中央日志和异步工作，重现bug的成本很高。

### 矩阵(arXiv: 2511.21686)

Matrix是2025年的一篇论文，它把蜂群归结为一个自然的结论：控制流和数据流都是分布式队列上的序列化消息。没有中央协调员。容错来自消息持久性。可伸缩性是消息代理的问题，而不是系统的问题。

贡献：一个编程模型，其中多代理协调是“这个代理订阅了什么消息主题？”而不是“主管下一步选择哪个代理？”这使得系统看起来像一个发布/订阅事件网格。

### LangGraph的蜂群架构

LangGraph 2025文档明确地将“群架构”描述为多智能体模式之一：智能体是节点，但是边形成一个有向图的循环，任何节点都可以从池中激活。工人根据条件选择工作，而不是根据主管的分配。

### 故障模式：饥饿和热点

如果所有的工人都拉最快可用的任务，那么长时间运行的任务永远不会被选中，直到它们是唯一剩下的。典型的队列饥饿。

Mitigations:
- 具有显式老化的优先级队列（随着等待时间增加优先级）。
- 工人专业化：一些工人只承担“长”任务。
- 背压：限制快速任务进入队列的数量。

### 基于内容的路由链接

蜂群与基于内容的路由自然配对（第22课）。每个消息类型都有一个队列，而不是通用队列。专业工人只订阅他们的类型。这是扩展到数千个代理的消息总线体系结构的基础。

## 构建它

Z0任务有不同的持续时间（有些快，有些慢）。演示对比如下：

- 顺序基线：一个worker按顺序处理所有任务。
- **固定分配：**每个任务预先分配给特定的工人（主管式）。
- **蜂群：**工人从共享队列拉。

蜂群自动平衡负载；固定分配使快速工人在分配的任务缓慢时处于空闲状态。

运行:

```
python3 code/main.py
```

输出显示每个工人的任务计数（蜂群分布不均匀，但最优）和时钟时间。

## 使用它

Z0输入：任务独立性、持续时间差异、排序需求、可调试性需求。

## 船这

检查表:

- **有老化的优先队列。**防止长时间任务饥饿。
- * *工人幂等性。**如果一个worker在运行过程中崩溃，一个task可能会被拉不止一次。工人必须是幂等的。
- * *持久队列。**使用Kafka， Redis Streams或数据库支持的队列进行生产。`queue.Queue` is in-memory only.
- **每个任务的可观察性。**每个任务都有一个跟踪ID；每个worker日志都以它开始/结束。
- * *背压。**如果队列的增长速度快于工人的消耗速度，则减慢生产者的速度。

## 练习

1. 运行在可变持续时间的工作负载上，群比顺序快多少？比固定分配快多少？
2. 添加一个优先级队列变量(使用按任务“重要性”字段分配优先级。观察低优先级任务在持续负载下是否会饿死。
3. 当任何工作进程处理的任务比最慢的工作进程多3倍时，实现热点检测器：日志。这说明任务持续时间分布是怎样的呢？
4. 阅读矩阵论文（arXiv:2511.21686）摘要和第3节。确定Matrix接受的一个特定权衡（可伸缩性增益）和放弃的一个特定权衡（可追溯性、确定性）。
5. 将蜂群演示转换为使用当任务是异构的时候，什么路由规则是有意义的？

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Swarm architecture | "Decentralized agents" | Workers pull from shared queue; no central orchestrator. |
| Event bus | "Agents subscribe to topics" | Message broker that routes tasks to workers by type or content. |
| Starvation | "Task never runs" | Low-priority task never gets picked because higher-priority work arrives continuously. |
| Hot-spotting | "One worker drowns" | Load imbalance where one worker gets most tasks. |
| Back-pressure | "Slow down the producer" | Mechanism that signals upstream to stop producing when the queue fills up. |
| Idempotent worker | "Safe to re-run" | A task processed twice produces the same result. Required because workers may crash mid-run. |
| Durable queue | "Survives crashes" | Queue backed by disk or replicated storage; tasks are not lost when a worker crashes. |
| Matrix framework | "Full message-passing swarm" | Both data and control flow are serialized messages on distributed queues. |
