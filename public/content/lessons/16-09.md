# Parallel/cluster/network architecture

> Contrary to the supervisor: There is no central decision-maker. The agent reads the shared event bus, picks up the work asynchronously, and writes the result back. LangGraph explicitly supports "group architecture" for decentralized dynamic environments. Matrix (arXiv:2511.21686) represents the control flow and data flow as serialized messages passed through a distributed queue to eliminate the orchestrator bottleneck. The trade-off is clear: the certainty of scalability and traceability. Group fitting is a task with many independent subproblems; It is not suitable for tasks that require a single coherent plan.

**Type:** Learn + Build
**Languages:** Python (stdlib, `threading`, `queue`)
**Prerequisites:** Phase 16 · 05 (Supervisor Pattern), Phase 16 · 04 (Primitive Model)
**Time:** ~75 minutes

## "Problem"

The supervisor was expanded to several workers. What about several hundred? The supervisor himself becomes a bottleneck: every decision about who does what has to go through an agent. A slow planning step will cause the entire system to come to a standstill.

Group architecture has revolutionized design. Workers select jobs from the shared queue instead of having them scheduled by the central planner. "Coordination" is embedded in the event bus semantics. There is no coordinator; The system will keep expanding until the queue is completed.

## Concept

### The shape

```
                ┌──── shared queue ────┐
                │                      │
       ┌────────┼────────┐  ◄──────┬───┘
       ▼        ▼        ▼         │
     Worker  Worker  Worker   Worker
      A       B       C        D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
            results pool
```

There is no coordinator. Each worker repeats: extracting tasks, processing, writing results (and an optional follow-up queue).

### When the group ADAPTS

- Many independent tasks. Scraping, transforming, classifying. Tasks are not interdependent with each other.
- ** Variable-duration works. If some tasks take 100 milliseconds while others take 10 seconds, the cluster will automatically balance the load - the faster worker will pull the next task. Supervisors must predict the duration.
- Throughput is superior to determinism. What you care about is the total completion time, not the strict sequence.

### When the bee colony fails

- Order the workflow. If step 3 requires the output of step 2, the bee colony may emit Step 3 before step 2 is completed.
- "Global Planning mission. Complex research problems benefit planners. A group of researchers produce independent facts rather than coherent reports.
- "Debugging. Due to the absence of a central log and asynchronous work, the cost of reproducing bugs is very high.

### Matrix (arXiv: 2511.21686)

Matrix is a paper published in 2025, which reduces bee colonies to a natural conclusion: both control flow and data flow are serialized messages on distributed queues. There is no central coordinator. Fault tolerance comes from message persistence. Scalability is a problem for the message broker, not for the system.

Contribution: A programming model in which multi-agent coordination is "What message topics does this agent subscribe to?" Rather than "Which agent will the supervisor choose next?" This makes the system look like a publish/subscribe event grid.

### The colony architecture of LangGraph

The LangGraph 2025 documentation explicitly describes the "group architecture" as one of the multi-agent patterns: agents are nodes, but edges form a loop of a directed graph, and any node can be activated from the pool. Workers choose their jobs based on conditions rather than on the allocation by their supervisors.

### Failure modes: Hunger and hotspots

If all the workers pull the fastest available tasks, then long-running tasks will never be selected until they are the only ones left. Typical queue hunger.

Mitigations:
- A priority queue with explicit aging (priority increases with waiting time).
- Worker specialization: Some workers only undertake "long" tasks.
- Back pressure: Limiting the number of fast tasks entering the queue.

### Content-based routing links

Bee colonies naturally pair with content-based Routing (Lesson 22). Each message type has a queue instead of a general queue. Professional workers only subscribe to their types. This is the foundation of a message bus architecture that extends to thousands of agents.

## Build it

 tasks have different durations (some are fast and some are slow). The demonstration comparison is as follows:

- Sequential baseline: A worker processes all tasks in sequence.
- ** Fixed allocation ** : Each task is pre-assigned to a specific worker (supervisor type).
- ** Swarm: ** Workers pull from the shared queue.

The bee colony automatically balances the load. Fixed allocation keeps quick workers idle when the assigned tasks are slow.

Run

```
python3 code/main.py
```

The output shows the task count of each worker (the bee colony distribution is uneven but optimal) and the clock time.

## This ship

Checklist

- There is an aging priority queue. Prevent hunger from long-term tasks.
- Workers' idempotence. If a worker crashes during its operation, a task may be pulled more than once. Workers must be idempotent.
- Persistent queue. Use Kafka, Redis Streams or databa-supported queues for production. `queue.Queue` is in-memory only.
- The observability of each task. Each task has a tracking ID; Each worker log starts/ends with it.
- Back pressure. If the growth rate of the queue is faster than the consumption rate of the workers, then slow down the rate of the producers.

## Practice

1. How much faster is a group than a sequence when running on a workload with variable durations? How much faster than the fixed distribution?
2. Add a priority queue variable (using the task "importance" field to assign priorities). Observe whether low-priority tasks will starve to death under continuous load.
3. When any worker process is handling three times more tasks than the slowest worker process, implement a hotspot detector: log. How does this indicate the distribution of task duration?
4. Read the abstract and Section 3 of the Matrix Paper (arXiv:2511.21686). Determine a specific trade-off that Matrix accepts (scalability gain) and a specific trade-off that it gives up (traceability, determinism).
5. When the task is heterogeneous, what routing rules make sense when converting the bee colony demonstration to use?

## Key terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Swarm architecture | "Decentralized agents" | Workers pull from shared queue; no central orchestrator. |
| Event bus | "Agents subscribe to topics" | Message broker that routes tasks to workers by type or content. |
| Starvation | "Task never runs" | Low-priority task never gets picked because higher-priority work arrives continuously. |
| Hot-spotting | "One worker drowns" | Load imbalance where one worker gets most tasks. |
| Back-pressure | "Slow down the producer" | Mechanism that signals upstream to stop producing when the queue fills up. |
| Idempotent worker | "Safe to re-run" | A task processed twice produces the same result. Required because workers may crash mid-run. |
| Durable queue | "Survives crashes" | Queue backed by disk or replicated storage; tasks are not lost when a worker crashes. |
| Matrix framework | "Full message-passing swarm" | Both data and control flow are serialized messages on distributed queues. |
