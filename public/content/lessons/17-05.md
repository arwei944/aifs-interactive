# EAGLE-3推测解码正在生产中

> 推测解码将快速草稿模型与目标模型配对。草案提出K个代币；目标在单次转发中验证；接受的代币是免费的。在2026年，EAGLE-3是生产级的变体-它根据目标模型的隐藏状态而不是原始令牌来训练草稿头部，将一般聊天的接受率alpha推至0.6-0.8区间。正确的问题不是“流速有多快”，而是“流量的alpha值是多少？”如果alpha低于~0.55，推测解码在高并发性下是净负的，因为每个被拒绝的草案都要花费第二次目标转发。这节课教你首先测量阿尔法，然后翻转旗帜。

**Type:** Learn
**Languages:** Python (stdlib, toy acceptance-rate simulator)
**Prerequisites:** Phase 17 · 04 (vLLM Serving Internals), Phase 10 · 18 (Multi-Token Prediction)

- 解释为什么推测解码在vLLM 2026中是可选的（而不是默认的），以及为什么在不测量alpha的情况下打开它是一个生产反模式。
- 编写一个度量计划：哪个基准测试，哪个提示分发，哪个并发点，哪个度量标准。

## 这个问题

Decode是受内存限制的。在运行Llama 3.3 70B FP8的H100上，每个解码的令牌读取~140 GB/s的权重并发出一个令牌。GPU计算在解码过程中几乎是空闲的-瓶颈是HBM带宽，而不是自然吞吐量。

推测性解码利用了这个缺口。使用便宜的草稿模型生成K个候选令牌，然后要求目标模型在单个向前传递中验证所有K个令牌。每个经过验证的令牌实际上都是免费的（无论如何，目标都必须向前平摊到一批k个令牌中）。

经典的草案-模型方法使用同一家族的较小模型（为Llama 3.3 70B起草Llama 3.2 1B）。它是有效的，但接受率一般——较小的模型分布偏离目标。EAGLE，然后EAGLE-2，然后EAGLE-3直接在目标模型的内部状态上训练一个轻的气流头，这样气流的分布就能更紧密地跟踪目标。这就是为什么alpha从draft-model的0.4到EAGLE-3的0.6-0.8。

问题是：EAGLE-3是vLLM 2026的选择。`speculative_config` must be set explicitly. 没有标志，没有加速。如果团队在没有测量实际流量的情况下启动了它，那么尾部延迟通常会变得更糟，而不是更好。

## 这个概念

### 投机解码到底买了什么

没有规范解码，每个令牌的成本是一个向前的目标。在草案长度为K的规范译码和接受alpha的情况下，每个目标转发的期望令牌为加速是当K=5, alpha=0.7时：现实世界的数字集中在2-3倍左右，因为alpha在生产流量上很少那么高，而epsilon在高批处理规模下增长。

### 为什么是唯一重要的指标

被拒绝的令牌不会消失——它们会强制为第一个被拒绝的令牌创建第二个目标。在alpha下降到0.4的工作负载上，您需要支付草稿开销、验证和重新滚动。在高并发性（比如256并发）下，解码批处理已经足够大，“单独目标”和“带有验证的目标”之间的内存带宽差距会缩小。在大多数2026硬件上低于alpha 0.55，规格解码为净负。

Alpha因工作负载而异。在ShareGPT风格的普通聊天中，经过ShareGPT训练的EAGLE-3达到了0.6-0.8。对于特定领域的流量（代码、医疗、法律），一般数据训练的草稿头部下降到0.4-0.6。训练特定领域的草稿头部恢复alpha -与目标微调相比，这是一项轻松，快速的训练工作。

### EAGLE一代一目了然

- **经典草稿模型**：同一家族的小模型。α0.3 - -0.5。基础设施简单-两个模型加载，草案运行K前锋每个目标前锋。
- **EAGLE-1(2024)**：在目标隐藏状态（最后一层）上训练的单草稿头部。α-0.6 ~ 0.5。目标顶部的小参数开销。
- **EAGLE-2(2025)**：自适应草案长度和基于树的草案（在一个目标通道中验证多个分支）。α-0.7 ~ 0.6。更复杂的草案调度程序。
- **EAGLE-3(2025-2026)**：在多个目标层（而不仅仅是最后）上训练草稿头部，更好的对齐。Alpha ~0.6-0.8上一般聊天。

### 2026年的生产配方

1. 船舶目标模型平原。测量基线TTFT、ITL和目标并发吞吐量。
2. 通过vLLM启用EAGLE-3草案重新运行基准测试。
3. 日志接受率alpha。vLLM V1将其报告为除以请求的草稿长度得到alpha。
4. 如果alpha在生产流量分布上< 0.55，禁用规范解码或训练特定于领域的EAGLE-3草案。
5. 在生产并发状态下，重新运行。确认P99 ITL没有恶化。

### 生产陷阱：P99尾

平均ITL随规格解码而下降。如果不进行调优，P99可能会变得更糟。被拒绝的草案触发一个两步序列（草案+验证-失败+重新投票）。在全批处理下，这两个传递序列化。看P99 ITL，不是P50。

### EAGLE-3已经部署在哪里

谷歌在2025年的AI Overviews中部署了推测解码（相同的质量，更快的响应）。vLLM V1船V1中的N-gram GPU推测解码是与块预填充兼容的变体。SGLang支持EAGLE-3作为前缀繁重工作负载的推荐草案路径。

### 一行就能算出收支平衡

预期加速：设置对于典型的verify_overhead ~0.15和K=5：但这是原始的解码数学。在高并发性下，验证开销会增加，而解码批处理已经平摊了跨序列的内存读取，因此在实践中，有效的alpha_breakeven会上升到~0.45-0.55。

### 不要使用推测解码

- 批1离线生成，其中延迟无关紧要。使用普通目标。
- 非常短的输出（少于50个令牌）。拟定经常性费用并确认费用占主导地位。
- 没有经过领域训练的草稿头的专门领域。太低了。
- vLLM v0.18.0加上草案模型规范解码加这个组合不能编译。记录的例外是V1中的N-gram GPU规范解码。

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Speculative decoding | "draft plus verify" | Propose K tokens with a cheap model, verify all K in one target forward |
| Acceptance rate alpha | "spec accept rate" | Fraction of draft tokens accepted by the target; the only metric that matters |
| Draft length K | "spec k" | How many tokens the draft proposes per target forward; typical 4-8 |
| Verify overhead epsilon | "spec overhead" | Extra cost to verify-and-reroll vs a plain target forward; grows with batch |
| EAGLE-3 | "latest EAGLE" | 2025-2026 variant; trains draft head on multiple target layers; alpha 0.6-0.8 on general chat |
| `speculative_config` | "vLLM spec config" | The explicit opt-in in vLLM V1; no default means no acceleration |
| N-gram spec decode | "N-gram draft" | GPU-side draft using N-gram lookups in the prompt; chunked-prefill-compatible |
| Break-even alpha | "no-op alpha" | Alpha at which spec decode gives zero speedup; watch this at production concurrency |
| Rejected-draft two-pass | "reroll cost" | Two target forwards when drafts reject; drives P99 tail |
