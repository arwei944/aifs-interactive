## 这个问题

上下文窗口看起来应该解决内存问题。他们没有。生产中出现的三种失效模式：

1. * *溢出。**多回合对话，长文件，或工具呼叫重轨迹穿过窗口。所有超过截止时间的东西都消失了。
2. * *稀释。**即使在窗口内，填充不相关的上下文也会稀释对重要内容的关注。前沿模型在长时间输入时仍然会退化。
3. * *持久性。**新会话以空窗口开始。没有外部记忆的代理不能跨会话说“记住你让我……的时候”。

更大的窗口有助于但不能解决这个问题。Mem0在2025年的论文中指出，128k窗口基线仍然错过了具有外部内存的4k窗口代理所能捕捉到的长期事实。

## 这个概念

### MemGPT: the OS analogy

Packer等人（arXiv:2310.08560, v2 Feb 2024）映射上下文管理到操作系统虚拟内存：

| OS concept | MemGPT concept | 2026 production analog |
|------------|---------------|------------------------|
| RAM | main context (prompt) | Anthropic/OpenAI context window |
| Disk | external context | vector DB, KV, graph store |
| Page fault | memory tool call | `memory.search`, `memory.read`, `memory.write` |
| OS kernel | agent control loop | ReAct loop with memory tools |

代理运行一个正常的ReAct循环。一个额外的工具类可以让它在主上下文内和主上下文外分页数据。

### Two tiers

- * *主要背景。**固定大小的提示符持有当前任务。始终对模型可见。
- * *外部环境。**无界，可通过工具搜索。相关的时候读，有事实的时候写。

原始论文在基本窗口之外的两个任务上评估了设计：超过10万个令牌的文档分析和使用持续内存的多会话聊天。

### 中断模式

MemGPT引入了内存即中断：在会话过程中，代理可以调用内存工具，运行时执行该工具，并将结果作为新的观察结果插入到下一个辅助回合中。在概念上与Unix相同

### MemGPT在哪里结束，Letta在哪里开始

2024年9月，MemGPT更名为Letta。研究报告(Letta扩展了设计：

- 三层而不是两层（核心、召回、存档——第08课）。
- 原生推理取代
- 运行异步内存工作的睡眠时间代理（第08课）。

即使生产系统运行Letta、Mem0或自定义两层存储，MemGPT论文也是2026的基础。

### 这种模式哪里出错了

- **内存腐烂。**写积累比读快；检索淹没在陈腐的事实中。修正：定期合并（Letta睡眠时间），显式无效（Mem0冲突检测器）。
- * *内存中毒。**外部存储器是检索文本。如果攻击者控制的内容出现在内存笔记中，代理将在下一个会话中重新摄取它。这是Greshake等人（第27课）的攻击。
- * *引用损失。**代理回忆“用户要求我运送X”，但无法说明是哪一个回合。在每次归档写入时存储源引用（会话ID，回合ID）。

## 使用它

今天的每个生产内存系统都是MemGPT的变体：

- **Letta**（第08课）-三层，原生推理，睡眠时间计算。
- **Mem0**（第09课）-矢量+ KV +图形与计分层融合。
- **OpenAI助手/响应** -通过线程和文件管理内存。
- **克劳德代理SDK** -通过技能和会话存储的长期记忆。

根据操作形式（自托管、托管、框架集成）选择一个，而不是根据核心模式—核心模式是MemGPT。

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Virtual context | "Unlimited memory" | Main (prompt) + external (searchable) tiers with page in/out |
| Main context | "Working memory" | The prompt — fixed-size, always visible |
| Archival memory | "Long-term store" | External searchable persistence, retrieved on demand |
| Core memory | "Persistent prompt section" | Named sections pinned inside the main context |
| Memory tool | "Memory API" | Tool call the agent issues to read/write external memory |
| Interrupt | "Memory page fault" | Agent pauses, runtime fetches, result splices into next turn |
| Memory rot | "Stale facts" | Old writes drown retrieval; fix with consolidation |
| Memory poisoning | "Injected persistent note" | Attacker content stored as memory, re-ingested on recall |
