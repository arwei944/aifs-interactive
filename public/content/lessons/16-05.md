# 主管/协调者-工作者模式

> 一个主要代理计划和委托；专门的工人在并行上下文中执行并报告。这就是Anthropic的研究系统背后的模式（克劳德作品4为主导，十四行诗4为次主体），在内部研究评估中，比单主体作品4高出90.2%。Anthropic的工程帖子报告说，BrowseComp上80%的差异是由令牌使用单独解释的——多代理获胜很大程度上是因为每个子代理都获得了一个新的上下文窗口。本课从原语构建主管模式，并涵盖了生产部署中的2026工程课程。

**Type:** Learn + Build
**Languages:** Python (stdlib, `threading`)
**Prerequisites:** Phase 16 · 04 (Primitive Model)
**Time:** ~75 minutes

## 问题

研究是单智能体系统失败的典型任务。你问“2023年到2026年间，多智能体系统有什么变化？”单个智能体按顺序阅读五篇论文，用它们的文本填充一半的上下文，然后必须一起对所有这些论文进行推理。到了第五篇的时候，它就会忘记第一篇了。它不能并行化。

主管模式解决了这个问题：一个领导代理计划搜索，将每个子问题委托给一个工作人员，然后进行综合。对于一个狭窄的问题，每个工作人员都有自己的20万令牌窗口。领导从来不看原稿，只看工人的总结。

Anthropic的生产研究系统报告+90.2%的内部研究评估与单一的Opus 4。同一篇文章指出，80%的BrowseComp差异是由“单独使用令牌”来解释的。每个子代理的新上下文是主要机制。

### 为什么它会赢

三个机制:

1. **每个子代理的新上下文。**探索“FIPA-ACL遗产”的工作人员不携带领导花费计划的40k令牌。它为一个问题获得了200k的窗口。
2. **通过提示专业化。**引子的提示是“分解和合成”，而不是“研究”。每个工人的提示都很狭窄：“找出x发生了什么变化。”重点提示产生重点输出。

### 工程课程（Anthropic 2025）

Anthropic的帖子列出了几个与2026年仍然相关的制作经验：

- **调整查询复杂度。**简单查询：一个座席，3-10个工具呼叫。复杂查询：10+代理。领导必须估计这个，而不是呼叫者。
- **先宽后窄。**首先分解为广泛的子问题，然后如果答案保证深度，则每个子问题产生更多的工人。
- * *彩虹部署。**代理是长时间运行且有状态的。传统的蓝绿色行不通。Anthropic使用彩虹：在旧版本耗尽的同时逐步推出新版本。
- **令牌使用占主导地位。**多代理是单代理令牌的15倍。只有当任务值与成本相符时才运行它。

### 失效模式

- Lead对计划产生了幻觉。**如果引子产生的子问题并没有分解真正的问题，那么工作人员对错误的目标进行了精确的研究。
- * *工人over-explore。**如果没有明确的范围边界，工作人员就会偏离指定的子问题并污染合成步骤。
- * *合成冲突。两个工人返回相互矛盾的事实。领导必须重新提出要求（增加一轮），或者明确指出分歧。沉默地选择一方是最糟糕的失败：用户永远不知道发生了分歧。

### 当主管犯错时

- * *顺序的任务。**如果步骤2确实需要步骤1的输出，并行性什么也买不到。使用流水线（CrewAI顺序，LangGraph线性图）。
- * *简单的查询。**单代理处理它们更快更便宜。在产卵工人之前，使用领导的“规模努力”检查。
- * *严格的决定论。**主管使用llm选择的委托。当审计/重放比适应性更重要时，静态图会更好。

## 船这

部署主管模式前的检查表：

- * *配对模式。**领导推理层模型（Opus类）；工人在更快，更便宜的模式(十四行诗，
- * *工人超时。**任何超过2倍中值运行时间的工作线程都会被杀死；铅要么以更窄的范围重新生成，要么没有它。
- **每个工人的代币上限。**硬限制（比如10倍的预期合成输入）可以防止失控的工人超支。
- * *可观测性。**跟踪领导的计划，每个工人的工具调用，和合成。这是任何事后调试的基础。
- * *彩虹推出。**有状态的长时间运行代理需要渐进的版本转换，而不是热插拔。

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Supervisor | "Lead agent" | An orchestrator agent that plans, delegates, and synthesizes. Does not do the work itself. |
| Worker | "Subagent" | A focused agent invoked by the supervisor with narrow scope and its own context window. |
| Orchestrator-worker | "Supervisor pattern" | Same thing, different name. The 2026 literature uses both. |
| Fresh context | "Clean window" | A worker's context starts from its system prompt and assigned question, not the lead's history. |
| Rainbow deployment | "Gradual rollout" | Long-running stateful agents need versioned drain-and-replace, not blue-green. |
| Token dominance | "Context is the variable" | 80% of research-eval variance comes from total tokens used, not model choice, per Anthropic. |
| Scale effort | "Match agent count to complexity" | Lead estimates query difficulty, spawns 1 vs 10+ workers accordingly. |
| Synthesis conflict | "Workers disagree" | Two workers return contradictory facts; the lead must surface disagreement, not silently pick one. |
