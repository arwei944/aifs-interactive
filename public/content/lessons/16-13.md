# Shared memory and blackboard mode

> Two methods coexist in multi-agent systems in 2026: message pools (where everyone sees everyone's messages, just like in AutoGen GroupChat or MetaGPT) and blackboards with subscriptions (where agents subscribe to related events, just like in context-aware MCP or matrix frameworks). They are all the only stateful parts in a multi-agent system - which means they are all interesting bugs. Reference failure mode is "memory poisoning" : one agent creates a "fact" illusion, while other agents treat it as verified, and its accuracy gradually declines. This is more difficult to debug than an immediate crash. This lesson builds these two structures from stdlib, injects poisoned attacks, and demonstrates three mitigation methods that actually work in production.

**Type:** Learn + Build
**Languages:** Python (stdlib, `threading`)
**Prerequisites:** Phase 16 · 04 (Primitive Model), Phase 16 · 09 (Parallel Swarm Networks)

## "Problem"

A multi-agent system requires a place for agents to share facts. A literal option is "pass everything in the message" - but this redefines the shared state through additional copying. Another approach is to "give everyone a global log" - but global logs can easily become unbounded and poisoned. The third one is "planning a view for each agent" - scalable but pattern-heavy.

When one of the agents generates an illusion and writes it to the shared state, each downstream agent reading that state takes the illusion as a fact. By the time humans noticed, the reasoning chain had already reached a depth of five steps, and the fundamental reason was the third piece of information in history. Debugging multi-agent precision decay is more difficult than debugging crashes.

This is memory poisoning. It is the second most recorded failure family in the MAST classification (Cemri et al., arXiv:2503.13657), and it is structural: any shared memory design without a source and non-writable validator will eventually exhibit it.

## Concept

### Two main topologies

*The message pool is full. Each agent reads each message. AutoGen GroupChat and MetaGPT use this. Simple, transparent and verifiable, but cannot be extended to more than 10 agents because the context of each agent is filled with the work of other agents.

```
agent-A ──write──▶ ┌────────────────┐ ◀──read── agent-D
                   │ message pool   │
agent-B ──write──▶ │                │ ◀──read── agent-E
                   │ (global log)   │
agent-C ──write──▶ └────────────────┘ ◀──read── agent-F
```

*Subscribe to Blackboard. The agent declares interest in the subject matter; The substrate only routes the relevant messages. CA-MCP (arXiv:2601.11595) and the Matrix decentralized framework (arXiv:2511.21686) employ this approach. It can be further expanded, but the model needs to be designed in advance to make the subscription meaningful.

```
                   ┌─ topic: prices ──┐
agent-A ──pub────▶ │                  │ ──▶ agent-D (subscribed)
                   ├─ topic: orders ──┤
agent-B ──pub────▶ │                  │ ──▶ agent-E (subscribed)
                   ├─ topic: alerts ──┤
agent-C ──pub────▶ │                  │ ──▶ agent-F (subscribed)
                   └──────────────────┘
```

### When everyone wins

- When there are few seats (< 10), heterogeneous, and short-sighted sessions, the entire pool wins. When everyone sees everything, it is insignificant to argue about who said what.
- When there are many agents, the roles are the same, but there are numerous instances (groups), and the session runs for a long time, Blackboard wins. Routing saves token costs and context pollution.

The production system is usually mixed: a small full pool at the top (planning level), and a blackboard at the bottom (worker level).

### Memory poisoning, in a scene

Three agents are conducting a research mission. Agent A is the retrieval agent. Agent B is a summarizer. Agent C is an analyst.

1. A retrieves the page and writes a message to the shared state: "The accuracy rate of the research report has increased by 42%."
2. The obtained page actually states "4.2% improvement". He had an illusion of a decimal.
3. B, who read the shared status, wrote: "The accuracy rate of the report has increased by 42% (Source: A)."
4. C, who read the shared status, wrote: "Recommended adoption - a 42% improvement is revolutionary."
5. The 42% figure mentioned in the final report simply does not exist.

No agent crash. There were no test failures. This system "works". Hallucinations span from the context of one subject to the reasoning of each downstream subject through shared states.

### Why is this structural

Without A shared state, agent A's illusion remains in the context of A. The downstream agent will re-acquire or re-derive and may catch errors. In the innocent state of sharing, the context of A became everyone's context, and illusions were washed into facts.

The problem itself is not a shared state - it is a shared state without a source or independent validator. There are three ways to alleviate this problem:

1. The source of each attribute written. Each entry in the shared state records who wrote it, when it was written, under what prompt it was written, and (if applicable) what source the proxy referenced. Downstream agents read with suspicion, with the source as the key.
2. "Version writing;" Treat them as additional only. It is more about replacing old entries with new ones, rather than updating them in place. Retain the audit trail.
3. At least one agent that cannot write to the shared state should be retained. The read-only validation agent samples the entries, retrieves the sources, and marks the inconsistencies. Because it cannot be written into the pool, it will not be poisoned by the pool.

### The Blackboard Precedent (Hayes-Roth, 1985)

The blackboard model is 40 years earlier than the Master of Laws agency. Hayes-Roth (1985, "Blackboard Architecture for Control") describes the sources of expertise for observing the global blackboard, provides partial solutions, and triggers other sources. The 2026 blackboard (CA-MCP, Matrix) follows the same pattern as LLM agents as knowledge bases and JSON blobs as partial solutions. Old literature documents solutions for the rediscovery of writing contention, opportunistic control and consistency in modern systems.

### Projection vs. Full view

A pure blackboard provides each subscriber with the same projection (subject range). A more radical design is each agent projection: each agent gets a view customized for its role. The state reducer of LangGraph is the standard 2026 implementation - the reducer function folds the global state into role-specific slices.

The projection of each agent can be further expanded, but a pattern is required. If not, you will rebuild the temporary projection in the prompt of each agent.

### Write to contention mode

Simultaneous writing by multiple agents is a concurrent issue, not merely an LLM problem. There are three working modes:

- Sequential writer (single producer). All write operations must go through a serialized coordinating agent. Simple, but it's a bottleneck.
- Optimistic concurrency with version control. Each entry has a version; The writer failed due to a version mismatch. Please try again. Classic database technology.
- "Theme zoning. Different agents have different themes. There is no debate on cross-topic. Partition boundaries need to be designed.

Most 2026 frameworks default to using sequential writers because LLM calls are slow enough, contention is minimal, and bottlenecks do not cause damage.

### The validator cannot be written

The most effective way to reduce the burden is the read-only validator. Implementation rules

- The validator shares the status with the team (reading the blackboard or pool).
- The validator has no write handles for the shared state - only write handles for individual validation channels.
- The validator independently retrieves the source referenced in the write. The divergence of flags.
- The validator's own output is routed to an individual or a separate decision agent and is never fed back to the pool.

Without such separation, the output of the validator would become a new entry in the pool, which means that a toxic pool would poison the validator and thereby poison its validation.

## This ship

For any shared memory design:

- Record the source of each write:
- Set the log to append only. It is precisely to guide the use of new entries that have replaced existing ones.
- Deploy at least one read-only validator agent with independent source access rights.
- Route the validator output to a separate channel instead of returning it to the shared pool.
- The proportion of suppressed writes recorded - an increase in the proportion is early evidence of the hallucination pattern.

## Key terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Message pool | "Shared chat history" | Append-only log that every agent reads. Full transparency, poor scaling. |
| Blackboard | "Shared workspace" | Topic-keyed pub/sub. Agents subscribe to relevant topics. Scales farther. |
| Provenance | "Who wrote what" | Metadata on each write: writer, timestamp, prompt, sources. |
| Memory poisoning | "Hallucinations spreading" | One agent's error enters shared state, downstream agents adopt it as fact. |
| Append-only | "No in-place updates" | Corrections are new entries that supersede. Preserves audit trail. |
| Unwritable verifier | "Independent auditor" | Read-only agent that re-fetches sources and flags inconsistencies. |
| Projection | "Scoped view" | Per-agent view computed from global state. LangGraph reducers are the canonical case. |
| Knowledge Source | "Specialist agent" | Hayes-Roth's 1985 term for a blackboard participant. |
