# 共享内存和黑板模式

> 两种方法在2026年的多智能体系统中共存：消息池（每个人都看到每个人的消息，就像在AutoGen GroupChat或MetaGPT中一样）和带有订阅的黑板（代理订阅相关事件，就像在上下文感知MCP或矩阵框架中一样）。它们都是多代理系统中唯一有状态的部分——这意味着它们都是有趣的bug所在。引用失败模式是“内存中毒”：一个代理产生“事实”幻觉，其他代理将其视为已验证，并且准确性逐渐衰减，这比立即崩溃更难调试。本课从stdlib构建这两个结构，注入中毒攻击，并展示在生产中实际工作的三种缓解方法。

**Type:** Learn + Build
**Languages:** Python (stdlib, `threading`)
**Prerequisites:** Phase 16 · 04 (Primitive Model), Phase 16 · 09 (Parallel Swarm Networks)
**Time:** ~75 minutes

## 问题

多智能体系统需要一个供智能体共享事实的地方。一个字面上的选项是“在消息中传递所有内容”——但这会通过额外的复制重新定义共享状态。另一种方法是“给每个人一个全局日志”——但是全局日志很容易变得无界和中毒。第三种是“为每个代理规划一个视图”——可伸缩但模式繁重。

当其中一个代理产生幻觉并将幻觉写入共享状态时，读取该状态的每个下游代理都将幻觉作为事实。当人类注意到的时候，推理链已经有五步深了，根本原因是有史以来第三条信息。调试多代理精度衰减比调试崩溃更难。

这是记忆中毒。它是MAST分类中第二多记录的故障族（Cemri等人，arXiv:2503.13657），并且它是结构性的：任何没有来源和不可写验证器的共享内存设计最终都会表现出它。

## 概念

### 两种主要拓扑

**满消息池。**每个代理读取每条消息。AutoGen GroupChat和MetaGPT使用这个。简单、透明、可检查，但不能扩展到超过10个代理，因为每个代理的上下文都充满了其他代理的工作。

```
agent-A ──write──▶ ┌────────────────┐ ◀──read── agent-D
                   │ message pool   │
agent-B ──write──▶ │                │ ◀──read── agent-E
                   │ (global log)   │
agent-C ──write──▶ └────────────────┘ ◀──read── agent-F
```

**订阅Blackboard。**代理声明对主题感兴趣；基板只路由相关的消息。CA-MCP （arXiv:2601.11595）和Matrix去中心化框架（arXiv:2511.21686）使用这种方法。可进一步扩展，但需要预先设计模式以使订阅有意义。

```
                   ┌─ topic: prices ──┐
agent-A ──pub────▶ │                  │ ──▶ agent-D (subscribed)
                   ├─ topic: orders ──┤
agent-B ──pub────▶ │                  │ ──▶ agent-E (subscribed)
                   ├─ topic: alerts ──┤
agent-C ──pub────▶ │                  │ ──▶ agent-F (subscribed)
                   └──────────────────┘
```

### 当每个人都赢了

- 当座席少（< 10）、异构、会话短视时，全池**获胜。当每个人都看到一切的时候，争论谁说了什么是微不足道的。
- 当代理数量多，角色相同，但实例（群）众多，并且会话长时间运行时，Blackboard**获胜。路由节省了令牌成本和上下文污染。

生产系统通常是混合的：一个小的全池在顶部（计划层），黑板在下面（工人层）。

### 记忆中毒，在一个场景中

三个特工正在进行一项研究任务。Agent A是检索代理。Agent B是一个总结者。Agent C是一名分析师。

1. A获取页面并向共享状态写入消息：“研究报告准确率提高了42%。”
2. 获取的页面实际上写着“4.2%改进”。他幻觉出了一个小数。
3. 阅读共享状态的B写道：“报告的准确率提高了42%（来源：A）。”
4. 阅读共享状态的C写道：“推荐采用——42%的提升是革命性的。”
5. 最终报告中提到的42%的数字根本不存在。

没有代理崩溃。没有测试失败。这个系统“起作用了”。幻觉通过共享状态从一个主体的情境跨越到每个下游主体的推理。

### 为什么这是结构性的

没有共享状态，agent A的幻觉停留在A的情境中。下游代理将重新获取或重新派生，并可能捕获错误。在天真的共享状态下，A的语境成为了每个人的语境，幻觉被洗成事实。

问题本身不是共享状态——它是没有来源和独立验证者的共享状态。有三种缓解办法可以解决这个问题：

1. **每次写的属性来源。**共享状态中的每个条目记录了谁写的，什么时候写的，在什么提示下写的，以及（如果适用的话）代理引用了什么来源。下游代理商以怀疑的态度阅读，以来源为关键。
2. * *版本写;将它们视为仅追加的。**更正是替换旧条目的新条目，而不是就地更新。保留审计跟踪。
3. **至少保留一个不能写共享状态的代理。**只读验证代理对条目进行采样，重新获取源，并标记不一致。因为它不能写入池，所以它不会被池毒害。

### 黑板先例（Hayes-Roth, 1985）

黑板模式比法学硕士代理早了40年。Hayes-Roth（1985，“用于控制的黑板架构”）描述了观察全局黑板的专业知识来源，提供部分解决方案，并触发其他来源。2026黑板（CA-MCP, Matrix）与LLM代理作为知识库和JSON blobs作为部分解决方案的模式相同。旧文献记录了现代系统重新发现的书写争用、机会主义控制和一致性的解决方案。

### 投影vs全视图

一个纯黑板为每个订阅者提供相同的投影（主题范围）。更激进的设计是每个代理投影：每个代理获得一个针对其角色定制的视图。LangGraph的状态reducer是规范的2026实现——reducer函数将全局状态折叠成特定于角色的片。

每个代理的投影可以进一步扩展，但需要一个模式。如果没有，您将在每个代理的提示符中重新构建临时投影。

### 写入争用模式

多个代理同时写入是一个并发问题，而不仅仅是LLM问题。有三种工作模式：

- **顺序作家（单一制片人）。**所有写操作都要经过一个序列化的协调代理。简单，但却是瓶颈。
- **带有版本控制的乐观并发性。**每个条目都有一个版本；编写器因版本不匹配而失败，请重试。经典的数据库技术。
- * *主题分区。**不同的代理拥有不同的主题。没有交叉话题的争论。需要设计分区边界。

大多数2026框架默认使用顺序写入器，因为LLM调用足够慢，争用很少，瓶颈也不会造成损害。

### 不可写验证器

最能减轻负担的是只读验证器。实现规则:

- 验证者与团队共享状态（读取黑板或池）。
- 验证器没有对共享状态的写句柄——只有对单独的验证通道的写句柄。
- 验证器独立地获取写入中引用的源。旗帜的分歧。
- 验证者自己的输出被路由到一个人或一个单独的决策代理，从来没有反馈到池中。

如果没有这种分离，验证者的输出将成为池中的新条目，这意味着一个有毒的池会毒害验证者，从而毒害它的验证。

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Message pool | "Shared chat history" | Append-only log that every agent reads. Full transparency, poor scaling. |
| Blackboard | "Shared workspace" | Topic-keyed pub/sub. Agents subscribe to relevant topics. Scales farther. |
| Provenance | "Who wrote what" | Metadata on each write: writer, timestamp, prompt, sources. |
| Memory poisoning | "Hallucinations spreading" | One agent's error enters shared state, downstream agents adopt it as fact. |
| Append-only | "No in-place updates" | Corrections are new entries that supersede. Preserves audit trail. |
| Unwritable verifier | "Independent auditor" | Read-only agent that re-fetches sources and flags inconsistencies. |
| Projection | "Scoped view" | Per-agent view computed from global state. LangGraph reducers are the canonical case. |
| Knowledge Source | "Specialist agent" | Hayes-Roth's 1985 term for a blackboard participant. |
