# MCP网关和注册表-企业控制平面

> 企业不能让每个开发人员随机安装MCP服务器。网关集中了身份验证、RBAC、审计、速率限制、缓存和工具中毒检测，然后将合并的工具表面作为单个MCP端点公开。官方MCP注册表（Anthropic + GitHub + PulseMCP + Microsoft，名称空间验证）是规范的上游。本节课列出了网关适合的位置，介绍了一个最小的实现，并调查了2026年的供应商情况。

**Type:** Learn
**Languages:** Python (stdlib, minimal gateway)
**Prerequisites:** Phase 13 · 15 (tool poisoning), Phase 13 · 16 (OAuth 2.1)
**Time:** ~45 minutes

## 这个问题

一家财富500强企业拥有30台经批准的MCP服务器、5000名开发人员、合规和审计需求，以及希望集中策略的安全团队。让每个开发人员在他们的ide中安装任意的服务器是不可能的。

网关模式：

1. 网关作为开发人员连接到的单个可流式HTTP端点运行。
2. 网关保存每个后端MCP服务器的凭据。
3. 每个开发人员请求都通过网关自己的OAuth进行身份验证和范围确定。
4. Gateway将调用路由到后端服务器，并应用策略。
5. 所有的电话都记录下来供审计。

Cloudflare MCP门户，Kong AI网关，IBM ContextForge, MintMCP, TrueFoundry， Envoy AI网关-所有在2025-2026年发布网关或网关功能。

与此同时，官方MCP注册表作为规范的上游启动：网关可以从经过管理、名称空间验证、反向dns命名的服务器中提取。元注册表(Glama, MCPMarket， MCP。因此，Smithery, LobeHub)跨多个源聚合服务器。

## 这个概念

### 五大网关职责

1. **身份验证。** OAuth 2.1识别开发人员；映射到用户角色。
2. ** RBAC。**每个用户策略：哪些服务器，哪些工具，哪些范围。
3. **审计。**每一通电话都记录了谁，什么，什么时候，结果。
4. **率限制。**每个用户/每个工具/每个服务器上限，以防止滥用。
5. **政策。**拒绝有毒描述，执行二原则，编辑PII。

### 网关作为单个端点

对于开发人员来说，网关看起来就像一个MCP服务器。在内部，它路由到N个后端。会话id（阶段13·09）在边界处被重写。

### 凭据跳跃

### 工具哈希固定在网关

网关持有批准的工具描述清单（SHA256哈希）。在发现时，它获取每个后端这是第13·15阶段的地毯拉式防御的集中应用。

### Policy-as-code

高级网关在OPA/Rego、Kyverno或Styra中表达策略。像“用户”这样的规则简单网关使用手工编码的Python。两种形状都是有效的。

### Session-aware路由

当用户会话包含多个服务器时，网关多路复用：开发人员的单个MCP会话包含N个后端会话，每个服务器一个。从任何后端路由通过网关发送到开发人员会话的通知。

### 名称空间合并

网关合并来自所有后端的工具名称空间，通常使用冲突前缀。`github.open_pr`, `notes.search`. 这使得路由没有歧义。

### 注册表

- **官方MCP注册表(**在Anthropic， GitHub, PulseMCP，微软管理下推出。名称空间验证（反向dns）：预过滤的基本质量。
- ** Glama。**以搜索为中心的元注册聚合了许多资源。
- ** MCPMarket。**带有供应商列表的商业倾斜目录。
- ** MCP.so。**社区目录；打开提交。
- **铁匠铺。**包管理器风格的安装流程。
- ** LobeHub。**在LobeChat应用程序中集成ui注册表。

默认情况下，企业网关从官方注册表中提取，允许从元注册表中添加由管理员管理的内容，并拒绝任何未固定的内容。

### 反向dns命名

官方注册管理机构要求公共服务器使用反向dns名称：名称空间可以防止占用，并使信任委托更清晰。

## 练习

1. 运行以允许的用户身份拨打电话；然后作为一个不被允许的用户；随后，一场超过利率上限的爆发。验证所有三个流。

2. 添加一个策略，在返回到客户端之前从结果中编辑PII。对ssn形状的字符串使用一个简单的正则表达式；注意差距（电子邮件，电话号码）。

3. 扩展审计日志以发出OpenTelemetry GenAI跨度。第13.20阶段涵盖了确切的属性。

4. 为一个拥有50名开发人员、5个后端（notes、github、postgres、jira、slack）的团队设计一个RBAC策略。谁的权限是只读的？谁来写？

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Gateway | "MCP proxy" | Centralizing server between clients and backends |
| Credential vaulting | "Backend tokens stay server-side" | Developers never see upstream tokens |
| Session-aware routing | "Multi-backend session" | Gateway multiplexes N backend sessions per developer session |
| Tool-hash pinning | "Approved manifest" | SHA256 of every approved tool description; blocks rug-pulls centrally |
| RBAC | "Per-user policy" | Role-based access control for tools and servers |
| Policy-as-code | "Declarative rules" | OPA/Rego, Kyverno, Styra policies enforced at gateway |
| Audit log | "Who, what, when" | Append-only event log for compliance |
| Rate limit | "Per-user token bucket" | Per-minute caps to prevent abuse |
| Official MCP Registry | "Canonical upstream" | `registry..io`, namespace-verified |
| Reverse-DNS naming | "Registry namespace" | `io.github.user/server` convention |
