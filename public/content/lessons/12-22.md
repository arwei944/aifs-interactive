# 文档和图表理解

> 文件不是照片。PDF、科学论文、发票或手写表单具有纯图像理解无法捕获的布局、表格、图表、脚注、标题和语义结构。vlm之前的堆栈是一个管道：Tesseract OCR + LayoutLMv3 +表提取启发式。VLM浪潮用无ocr模型取代了它——Donut (2022), Nougat (2023), doclm（2023）——直接发出结构化标记。到2026年，边界只是“将页面图像以2576px的原生格式提供给Claude Opus 4.7”，并且结构化标记输出是免费的。本课将阅读文档人工智能的三时代弧线。

**Type:** Build
**Languages:** Python (stdlib, layout-aware document parser skeleton)
**Prerequisites:** Phase 12 · 05 (LLaVA), Phase 5 (NLP)
**Time:** ~180 minutes

## 学习目标

- 解释文档人工智能的三个时代：OCR管道，无OCR， vlm原生。
- 描述LayoutLMv3的三个输入流：文本，布局（bbox），图像补丁，统一屏蔽。
- 比较Donut（无ocr，图像→标记），牛轧糖（科学论文→LaTeX）， DocLLM（布局感知生成），PaliGemma 2 （vlm原生）。
- 为新任务选择一个文档模型（发票、科学论文、手写表格、中文收据）。

## 这个问题

“理解这个PDF”看起来很难。信息位于：

- 文本内容（90%的信号）。
- 布局（标题、脚注、侧边栏、两栏格式）。
- 表（行、列、合并的单元格）。
- 数字和图表。
- 手写注释。
- 字体和排版（标题和正文）。

原始OCR转储文本并丢失其余部分。一个关心发票的系统需要知道“Total: $ 1245”来自右下角，而不是脚注。

## 这个概念

### 第1时代- OCR管道（2021年前）

经典的堆栈：

1. PDF→每页图片。
2. Tesseract（或商业OCR）使用每个单词的边界框提取文本。
3. 布局分析器识别块（页眉，表，段落）。
4. 表结构识别器解析表。
5. 域规则+正则表达式提取字段。

适用于干净的印刷文本。书写中断，扫描歪斜，表格复杂，非英语文字。每个故障模式都需要一个自def 的异常路径。

### TrOCR (2021)

TrOCR （Li et al., arXiv:2109.10282）用在合成+真实文本图像上训练的Transformer编码器-解码器取代了Tesseract的经典CNN-CTC。干净的手写和多语言文本的胜利。仍然是一个流水线（检测器然后TrOCR然后布局），但OCR步骤显著改进。

### 纪元2-无ocr （2022-2023）

第一个无ocr模型说：完全跳过检测，直接将图像像素映射到结构化输出。

Donut (Kim et al., ar14:2111.15664)：
- 编码器-解码器转换器，编码器为swing - b。
- 输出是用于表单理解的JSON，用于摘要的标记，或任何特定于任务的模式。
- 没有OCR，没有布局，没有检测。

牛轧糖（Blecher等人，arXiv:2308.13418）：
- 专门针对科学论文进行培训。
- 输出是LaTeX / markdown。
- 处理方程式，多列布局，图形。
- 每个arxiv解析器调用的模型。

他们是专家，不是通才。科学论文上的甜甜圈不及格；发票上的牛轧糖失败了。

### LayoutLMv3 (2022)

一条不同的轨道。LayoutLMv3 （Huang et al., arXiv:2204.08387）保留了OCR，但增加了布局理解：

- 三个输入流：OCR文本标记，每个标记的2D边界框，图像补丁。
- 蒙面训练目标跨越所有三种模式（蒙面文本，蒙面补丁，蒙面布局）。
- 下游：分类、实体提取、表QA。

LayoutLMv3是基于ocr的文档理解的顶峰。擅长表格和发票。需要OCR上游。在标准化文档基准上的最佳预vlm精度。

### DocLLM (2023)

doclm （Wang et al., arXiv:2401.00908）是LayoutLM的生成兄弟。根据布局令牌生成自由格式的答案。更适合QA文件；仍然取决于OCR输入。

### 时代3 - vlm原生（2024+）。

2024年vlm已经足够好，可以完全取代管道。将高分辨率的整页图像馈送到VLM，提出问题，得到答案。

- LLaVA-NeXT 336-tile AnyRes适用于小型文档。
- Qwen2.5-VL动态分辨率原生处理2048+像素。
- Claude Opus 4.7支持2576px文档。
- PaliGemma 2（2025年4月）专门针对文档和手写进行培训。

vlm原生和ocr管道之间的差距迅速缩小。到2026年，vlm native将赢得：

- 场景文本（手写+印刷，混合脚本）。
- 具有合并单元格的复杂表。
- 嵌入在文本中的数学方程。
- 带有文本注释的图形。

OCR管道仍然在以下方面获胜：

- 大规模的纯扫描工作负载，其中每个页面的延迟很重要。
- 管道可靠性（确定性故障vs VLM幻觉）。
- 需要可审计OCR输出的规范环境。

### 克劳德4.7 / GPT-5前沿

在2576像素的原生输入下，前沿vlm以接近人类的精度进行文档理解。从2026年初开始的基准数据：

- DocVQA: Claude 4.7 ~95.1, PaliGemma 2 ~88.4，牛轧糖~77.3，流水线LayoutLMv3 ~83。
- 图qa: Claude 4.7 ~92.2, GPT-4V ~78。
- VisualMRC: Claude 4.7 ~94.

封闭模式的差距主要是分辨率和基础llm尺度。7B的开放式模型落后几个点，但正在迎头赶上。

### 数学方程和LaTeX输出

科学论文需要精确的LaTeX输出方程。牛轧糖就是这样训练的。用LaTeX目标（Qwen2.5-VL-Math，牛轧糖导数）训练的vlm产生可用的LaTeX。如果没有明确的LaTeX训练，vlm会生成可读但不精确的转录。

对于2026年的科学论文管道：PDF上的牛轧糖链，然后是复杂页面上的VLM。

### 笔迹

仍然是最难的子任务。混合印刷+手写（医生笔记，填写表格）是OCR管道在成本上仍然优于vlm的地方。纯手写vlm正在改进（Claude 4.7, PaliGemma 2）。

### 2026年食谱

对于一个新的文档ai项目：

- 大规模纯打印发票：LayoutLMv3 +规则，成本效益高。
- 混合文档（科学+手写+表格）：vlm原生（PaliGemma 2或Qwen2.5-VL）。
- 完整的arXiv摄入：牛轧糖用于数学，VLM用于数字。
- 监管：OCR管道+ VLM验证器进行交叉检查。

## 使用它


- 一个玩具布局感知标记器：给定（text, bbox）对，生成layoutlmv3风格的输入。
- 一个donut样式的任务模式生成器：表单的JSON模板。
- 跨ocr管道、Donut、Nougat和vlm本地的每页令牌预算的比较。

## 船这

这一课产生了给定一个文档人工智能项目（领域、规模、质量、监管），在OCR管道、无OCR专家和vlm原生之间进行选择。

## 练习

1. 你的项目是每天1000万张发票。哪一种堆栈在不损失准确性的情况下使每页成本最小化？

2. 为什么LayoutLMv3在表单QA上优于纯clip - vlms，但在场景文本上表现不佳？bbox流放弃了什么？

3. 牛轧糖产生乳胶。提出一个测试用例，其中vlm本地输出在LaTeX保真度上胜过牛轧糖，以及一个牛轧糖获胜的用例。

4. 阅读PaliGemma 2论文（bb2010, 2024）。与PaliGemma 1相比，提高文档准确性的关键训练数据添加是什么？

5. 设计一个监管安全的混合：OCR管道为主要，VLM为次要交叉检查。你如何解决分歧？

## 关键术语

| Term | What people say | What it actually means |
|------|-----------------|------------------------|
| OCR pipeline | "Tesseract-style" | Stage-wise stack: detect -> OCR -> layout -> rules; deterministic, fragile |
| OCR-free | "Donut-style" | Image-to-output transformer that skips explicit OCR; single model |
| Layout-aware | "LayoutLM" | Input includes per-token bbox coordinates; unified masking across modalities |
| VLM-native | "Frontier VLM" | Feed page image directly to Claude/GPT/Qwen VLM at high resolution; no pipeline |
| DocVQA | "Doc benchmark" | Document VQA standard; most-cited score |
| Markup output | "LaTeX / MD" | Structured output format instead of free-form text; enables downstream automation |
