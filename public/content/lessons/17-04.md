## 这个问题

一个朴素的PyTorch服务循环一次运行一个请求：tokenize， prefill， decode直到EOS， return。对于一个用户，这是有效的。一百人的队伍里都是耐心的人。最明显的修复方法——静态批处理——将每个请求分配到窗口中最长的提示符，将每个解码分配到最长的预期输出，并在最慢的序列上暂停整个批处理。您为从未使用过的填充付费，快速请求等待慢速请求。

vLLM一次解决了三个问题。PagedAttention阻止KV缓存碎片吃60-80%的GPU内存的方式，经典的连续分配。连续批处理允许请求在每次解码迭代之间加入和离开批处理，因此批处理总是充满了实际的工作。块预填充将32k令牌提示分解为约512个令牌片，这些令牌片与解码交错，因此长提示不会冻结GPU上的每个解码令牌。

2026年的生产默认值是三个都打开。您需要了解每个模式的作用，因为故障模式都在调度器上，而不是模型上。

## 这个概念

### PagedAttention作为一个虚拟内存系统

千伏缓存是对于Llama 3.3 70B的8192个令牌，在BF16中每个序列大约有1.25 GB。如果为每个请求预先预留8192个插槽，但平均每个请求只使用1500个令牌，那么您就浪费了所预留HBM的82%。传统的批处理解决了这种浪费。

PagedAttention借鉴了操作系统虚拟内存的思想。KV缓存不是每个序列连续的。它被分配在固定大小的块中（默认16个令牌）。每个序列都有一个块表，将其逻辑标记位置映射到物理块id。当一个序列超过它分配的块时，就会再添加一个块。当它完成后，它的块返回到池中。

### 迭代级别的连续批处理

旧的“动态批处理”等待一个窗口（比如10毫秒）来填充一个批处理，然后运行prefill + decode + decode + decode，直到每个序列完成。当GPU完成慢序列时，快速序列会提前离开并处于空闲状态。

在每个解码步骤之间进行连续批处理操作。将运行序列集称为在每次迭代中：

1. 中的任意序列
2. 调度器查看等待队列。如果有空闲的KV块，它允许新的序列（预填充或恢复）。
3. 向前传球是在现在的位置上进行的

批大小永远不会填充到一个固定的数字。序列在其输出的不同位置共享一个融合向前。在2026 vLLM中，这被称为关键不变式：调度器在每次解码迭代时运行一次，而不是每次请求运行一次。

### 分块预填充保护TTFT尾部

预填充是计算绑定的。在Llama 3.3 70B上，一个32k令牌提示在一个H100上需要大约800毫秒的纯预填充时间。在预填充运行时，为批处理等待中的每个其他序列解码令牌。在服务循环中，一个长提示符的第一个令牌延迟（TTFT）会变成数十个其他用户的令牌间延迟（ITL）。

Chunked prefill将预填充分成固定大小的块（默认为512个令牌），并将每个块作为一个单元调度。在块之间，调度器可以按一个令牌推进解码序列。您可以用较小的绝对预填充延迟命中（每个块几毫秒）换取更低的解码时间抖动。在公布的基准测试中，混合负载下的P99 ITL从~50 ms降至~15 ms。

### 三个默认值相互作用

这三个特征相互假定。PagedAttention为调度器提供了一个细粒度的KV资源进行交易。连续批处理需要细粒度的资源，因此允许一个新序列不会强制全局重新洗牌。分块预填充是调度程序在相同的情况下做出的决定

### 2026 v0.18.0找到你了

在vLLM v0.18.0中不能合并记录的异常是V1调度器中的N-gram GPU推测解码。在没有阅读发行说明的情况下打开所有标志的团队会在启动时出现运行时错误，而不是软回归。如果您的投机收益值得启用分块预填充，请重新考虑选择- 2026年的正确答案通常是没有分块预填充的EAGLE-3，而不是没有编译的草案模型加上分块预填充。

### 你应该记住的数字

- Llama 3.3 70B FP8, H100 SXM5, 128并发，三开机：2200 - 2400 tok/s。
- 相同的模型，默认vLLM（没有块预填充）：~1,800 tok/s。
- 相同的模型，朴素PyTorch前向循环：~600 tok/s。
- 生产负荷下KV碎块浪费注意：<4%。
- 混合负载下P99 ITL：有块预填充时~15 ms，无块预填充时~50 ms。

### 调度程序是什么样子的

```
while True:
    finished = [s for s in RUNNING if s.is_done()]
    for s in finished: release_blocks(s); RUNNING.remove(s)

    while WAITING and have_free_blocks_for(WAITING[0]):
        s = WAITING.pop(0)
        allocate_initial_blocks(s)
        RUNNING.append(s)

    # schedule prefill chunks + decode in one batch
    batch = []
    for s in RUNNING:
        if s.in_prefill:
            batch.append(next_prefill_chunk(s))   # e.g. 512 tokens
        else:
            batch.append(decode_one_token(s))     # 1 token

    run_forward(batch)                            # one fused GPU call
```

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| PagedAttention | "the KV trick" | Fixed-size block allocator for KV cache; fragmentation <4% |
| Block table | "the page table" | Per-sequence map from logical token position to physical KV block |
| Continuous batching | "dynamic batching, but right" | Admit/release decisions made every decode iteration |
| Chunked prefill | "prefill splitting" | Break long prefill into 512-token slices interleaved with decode |
| TTFT | "first token time" | Prefill + queue + network; dominated by prefill at long prompts |
| ITL | "inter-token latency" | Time between consecutive decode tokens; dominated by batch size |
| Goodput | "throughput that meets SLO" | Tokens/sec where every request still hit TTFT and ITL targets |
| V1 scheduler | "the new scheduler" | vLLM's 2026 scheduler; N-gram spec decode is the chunked-prefill-compatible path |
| `--gpu-memory-utilization` | "the memory knob" | Fraction of HBM reserved for KV blocks after weights and activations |
