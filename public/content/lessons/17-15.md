# 批处理api - 50%折扣作为行业标准

> 每个主要提供商都提供了一个异步批处理API，折扣为50%，周转时间约为24小时。OpenAI、Anthropic、谷歌和大多数推理平台（Fireworks批处理层、Together批处理层）实现了相同的模式。使用即时缓存和隔夜管道的堆栈批处理降低到同步非缓存成本的10%左右。规则非常简单：如果它不是交互式的，它就属于批处理。内容生成管道、文档分类、数据提取、报告生成、批量标记、目录标记——任何能容忍24小时延迟的东西都是在批量处理之前留下的钱。2026年的生产模式是将每个新的LLM工作负载划分为三个通道：交互式（带缓存的同步）、半交互式（带回退的异步队列）、批处理（隔夜、缓存输入堆叠）。假装是交互式的，但容忍几分钟延迟的工作负载浪费最多。

**Type:** Learn
**Languages:** Python (stdlib, toy batch-vs-sync cost simulator)
**Prerequisites:** Phase 17 · 14 (Prompt & Semantic Caching)
**Time:** ~45 minutes

## 学习目标

- 说出三个提供商批处理api （OpenAI, Anthropic，谷歌）和常见的50%折扣+ 24小时周转保证。
- 计算在隔夜分类工作负载上堆叠批处理+缓存输入的成本，并与同步非缓存基线进行比较。
- 将工作负载分类为交互式/半交互式/批处理，并确定通道的合理性。
- 列出两个陷阱：部分交互性（用户期望超过24小时）和输出模式漂移（每个提供者的批处理文件格式不同）。

## 这个问题

您的团队发布了一个夜间报告生成管道。5万份文件，总结每一份，汇总总结，起草一份执行摘要。同步运行需要4小时，每晚2000美元。你听说过批处理api。

这批货打五折。您还可以在系统提示符上启用提示缓存（在所有50k调用中共享）。叠加后，账单降至每晚180美元——约为基准的9%。同样的管道，三个配置更改。

批处理是LLM成本工具包中最便宜的杠杆，没有人拉动。原因主要是组织上的：团队认为SLA是“实时的”，而实际上是“到早上”。这一课是关于不要把账单的90%留在桌子上。

## 这个概念

### 三个批量api

**OpenAI批处理API**: JSONL文件上传与请求列表。承诺24小时周转（实际上通常是2-8小时）。输入和输出令牌的50%折扣。`/v1/batches` endpoint. 符合缓存条件的输入也会在顶部获得缓存输入定价。

**Anthropic messages Batches**: JSONL上传。24小时的转机。50%的折扣。支持

**谷歌顶点AI批量预测**:BigQuery或GCS输入。双子座也有类似的五折优惠。与顶点管道集成。

### 语义：异步，而不是慢

Batch是“我保证在24小时内退货”，而不是“这需要24小时”。典型的P50是2-6小时。当GPU库存未充分利用时，提供商会在非高峰窗口安排批处理。

### 使用缓存进行堆栈

50k文档摘要，具有相同的4k令牌系统提示：

- 同步非缓存：50000 ×（$输入× 4000 + $输出× 200）全速率。
- 同步缓存：系统提示符在第一次写入后缓存；剩下的49999人得到了10倍便宜的输入。
- 批处理缓存：上述所有内容加上50%的读和写折扣。

栈：batch + cache =约10%的同步未缓存账单。任何夜间运行并具有共享系统提示符的工作负载都应该使用此功能。

### 工作负载分类

*交互式——用户等待响应。TTFT至关重要。带有提示缓存的同步调用。不能批量。

**半交互式** -用户提交任务，在几分钟内检查回来。如果批处理不可用，具有回退到同步的异步队列。考虑中等容量的RAG索引。

**批处理** -用户期望结果“在早上”或“下一个小时”。内容管道，大规模分类，离线分析。总是批处理，总是堆栈缓存。

常见错误：将所有内容归类为交互式，因为管道就是产品。生产不是延迟规范- SLA是。

### 部分交互性陷阱

有些功能看起来是交互式的，但需要5-10分钟。示例：带有“刷新”按钮的夜间客户运行状况报告。用户点击刷新；等10分钟就可以了。团队将其作为同步发布。50次并发刷新的成本是通过电子邮件进行批处理和交付的成本的10倍。

要问的问题是：“24小时对这个用户意味着什么？”如果答案是“他们不会注意到”，那就分批处理。

### 输出模式陷阱

批处理文件格式因提供程序而异：

- OpenAI: json，每行一个请求。
- Anthropic: JSONL，每行一条消息；嵌入响应格式。
- 顶点：带有TFRecord的BigQuery表或GCS前缀。

跨提供程序编写“一个批处理客户端”意味着每个提供程序编写适配器代码。发布多提供商批处理（Portkey， LiteLLM某些层）的网关仍然对原始格式进行薄封装。

### 你应该记住的数字

- 供应商之间的批量折扣：投入+产出50%。
- 周转SLA：保证24小时，典型P50为2-6小时。
- 堆叠批处理+缓存输入：约占同步非缓存成本的10%。
- 工作负载分类规则：如果可以接受24小时延迟，则总是批处理。

1. 运行对于100k-doc的管道，具有3g令牌系统提示和500令牌输出，计算全栈（批处理+缓存）与同步基线的节省。

4. 你们的批API返回SLA是24小时，但P99是20小时。您如何与用户沟通这一点-在边缘情况下下游系统的行为是什么？
5. 计算收支平衡：在什么共享前缀长度下，批处理+缓存比在您自己的预留GPU上过夜运行更便宜？

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Batch API | "async discount" | 50% off with 24h turnaround |
| JSONL | "batch format" | One JSON request per line; OpenAI/Anthropic standard |
| Message Batches | "Anthropic batch" | Anthropic's batch API product name |
| Batch prediction | "Vertex batch" | Vertex AI's batch API product |
| Turnaround SLA | "24h promise" | Guarantee, not typical; typical is 2-6h |
| Workload triage | "interactivity decision" | Interactive / semi / batch routing decision |
| Output schema | "response format" | Per-provider JSONL layout; not portable |
| Stacked discount | "batch + cache" | ~10% of uncached sync bill when both apply |
