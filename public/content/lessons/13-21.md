# 路由层- LiteLLM， OpenRouter, Portkey

> 提供者锁定是昂贵的。不同的工具调用工作负载适合不同的模型。路由网关提供一个API接口、重试、故障转移、成本跟踪和护栏。2026年主要有三个原型：LiteLLM（开源自托管），OpenRouter（托管SaaS）， Portkey（生产级，2026年3月开源）。本课命名决策标准并遍历标准库路由网关。

**Type:** Learn
**Languages:** Python (stdlib, routing + failover + cost tracker)
**Prerequisites:** Phase 13 · 02 (function calling), Phase 13 · 17 (gateways)
**Time:** ~45 minutes

## 学习目标

- 区分自托管、托管和生产级路由选项。
- 实现一个回退链，以def 的优先级顺序在提供者失败时重试。
- 跟踪每个请求的成本和跨提供者的令牌使用情况。
- 在给定的生产约束下选择LiteLLM、OpenRouter和Portkey。

## 这个问题

提供商路由很重要的场景：

1. **成本。**克劳德十四行诗的成本是俳句的三倍。对于分类任务，俳句就足够了；对于一个综合任务，十四行诗是值得的。每个请求。

2. **故障转移。** OpenAI正处于糟糕的时刻。每个请求都失败。你想要自动回退到Anthropic而不重新部署。

3. **延迟。**实时聊天UI需要快速到达第一个令牌。批汇总器则不需要。按时延SLA路由。

4. **遵从性。**欧盟用户必须留在欧盟地区。按区域路由。

5. **实验。** A/B两个模型在相同的工作负载上。按测试桶路由。

为每个集成手工编码是重复的。路由网关提供一个openai兼容的API，并处理其余的。

## 这个概念

### openai兼容的代理形状

每个人都说openai。路由网关公开了客户并不关心。

### 模型的别名

而不是网关将别名映射到真实模型。当Anthropic发布Claude 4时，你改变了服务器端的别名；您的代码没有触及任何东西。

### 后备链

```
primary: openai/gpt-4o
on 5xx: anthropic/claude-3-5-sonnet
on 5xx: google/gemini-1.5-pro
on 5xx: refuse
```

网关在配置中def 了这一点。重试算在预算中，因此回退级联不会爆炸成本。

### 语义缓存

相同或几乎相同的提示会命中缓存而不是提供程序。重复代理循环可以节省30%到60%。键是基于嵌入的；几乎相同的提示共享一个缓存槽。

### 护栏

Gateway-level:

- ** PII修订。**在发送提示之前通过Regex或ml。
- **政策违反。**拒绝含有禁止内容的提示。
- **输出过滤器。**清洗完井是否有泄漏。

Portkey和Kong都是船上固执己见的护栏。LiteLLM让它们是可选的。

### 每键速率限制

一个API密钥=一个团队。按键预算防止一个团队使用共享配额。大多数网关都支持这一点。

### 自托管与托管的权衡

| Factor | LiteLLM (self-hosted) | OpenRouter (managed) | Portkey (production) |
|--------|----------------------|----------------------|----------------------|
| Code | Open source, Python | Managed SaaS | Open source (Mar 2026) + managed |
| Setup | Deploy a proxy | Sign up | Either |
| Providers | 100+ | 300+ | 100+ |
| Billing | Your own keys | OpenRouter credits | Your own keys |
| Observability | OpenTelemetry | Dashboard | Full OTel + PII redaction |
| Best for | Teams that want full control | Rapid prototyping | Production with compliance |

当你有一个SRE团队并且想要数据主权时，LiteLLM会胜出。当你想要单一订阅而没有基础设施时，OpenRouter就胜出了。当您需要护栏和开箱即用的合规性时，Portkey获胜。

### 成本跟踪

每个请求都包含乘以每个型号每个代币的价格（从网关维护的价格表中提取）。每个用户/每个团队/每个项目聚合。

### MCP +路由

网关可以路由LLM调用和MCP采样请求。当采样请求的modelPreferences偏爱特定模型时，网关将转换为正确的后端。这就是阶段13·17 （MCP网关）和本课的路由网关有时合并为一个服务的地方。

### 路由策略

- **静态优先级。**第一名；退回到错误。
- **负载平衡。**循环或加权。
- ** Cost-aware。**选择最便宜的型号满足延迟/质量。
- ** Latency-aware。**选择最后N分钟内最快的型号。
- ** Task-aware。提示分类器将编码路由到一个模型，汇总到另一个模型。

## 使用它

Z0在三种情况下运行它：正常请求、主提供者中断触发回退、通过编校捕获的PII泄漏。

看点：

- 
- 在5xx时重试回退循环。
- 成本跟踪器将令牌使用率乘以每个模型的费率。
- PII编辑器在转发前擦洗ssn形状的图案。

## 船这

这一课产生了给定一个工作负载配置文件（延迟、成本、遵从性），该技能会选择LiteLLM / OpenRouter / Portkey并生成一个路由配置。

## 练习

1. 运行触发停机场景；确认备用降落在第二个供应商上，并且成本是正确的。

2. 添加语义缓存：SHA256的提示符是查找键；缓存立即返回。衡量重复呼叫节省的成本。

3. 添加一个提示分类器，将“code…”提示路由到支持智能的别名，并将“summary…”提示路由到支持速度的别名。

4. 设计每个团队的预算：每个团队都有每月的支出上限；一旦达到上限，网关将拒绝请求。选择执行粒度（每个请求或窗口）。

5. 并排阅读LiteLLM， OpenRouter和Portkey文档。说出每款游戏都具备而其他两款游戏没有的特点。

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Routing gateway | "LLM proxy" | One-API-surface layer in front of many providers |
| OpenAI-compatible | "Speaks the OpenAI schema" | Accepts `/v1/chat/completions` shape, translates to any backend |
| Model alias | "our_smart_model" | Name in your code that the gateway maps to a concrete model |
| Fallback chain | "Retry list" | Ordered list of providers attempted on failure |
| Semantic caching | "Prompt-embedding cache" | Key is embedding of the prompt; near-duplicates share a cache hit |
| Guardrails | "Input/output filters" | Redact PII, reject policy violations |
| Per-key rate limit | "Team budget" | Quota scoped to an API key |
| Cost tracking | "Per-request spend" | Aggregate token usage x price per model |
| LiteLLM | "The open proxy" | Self-hostable OSS routing gateway |
| OpenRouter | "The managed SaaS" | Hosted gateway with credit-based billing |
| Portkey | "The production option" | Open-source + managed with guardrails built in |
