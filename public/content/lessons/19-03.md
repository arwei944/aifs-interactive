# Capstone 03 -实时语音助手（从ASR到LLM到TTS）

> 感觉合适的语音代理端到端延迟低于800ms，知道您何时停止通话，处理入侵，并且可以在不拖延的情况下调用工具。Retell、Vapi、LiveKit Agents和Pipecat都将在2026年达到这一标准。它们采用相同的形状：一个流ASR、一个转弯检测器、一个流LLM和一个流TTS，所有这些都通过webbrtc连接，每一跳都有积极的延迟预算。构建一个，测量WER、MOS和误断率，并在丢包情况下运行。

**Type:** Capstone
**Languages:** Python (agent + pipeline), TypeScript (web client)
**Prerequisites:** Phase 6 (speech and audio), Phase 7 (transformers), Phase 11 (LLM engineering), Phase 13 (tools), Phase 14 (agents), Phase 17 (infrastructure)
**运行阶段：** P6·P7·P11·P13·P14·P17
**Time:** 30 hours

## 问题

语音是2025-2026年发展最快的AI UX类别。技术上限每个季度都在下降。OpenAI实时API， Gemini 2.5 Live, Cartesia Sonic-2, ElevenLabs Flash v3, LiveKit Agents 1.0和Pipecat 0.0.70都可以实现低于800ms的第一音频输出。这个条不仅仅是延迟。它是一种交互感觉：不会打断用户，不会被打断，从句子中间的中断中恢复过来，在对话中调用工具而不会中断音频，在紧张的移动网络中生存下来。

您不能通过拼接三个REST调用来实现这一点。该体系结构是端到端流水化的。构建它，故障模式就变得清晰可见了：VAD调成电话音频在背景电视上发射，转向检测器等待从未出现的标点符号，TTS在发射前缓冲400ms。最重要的是每次在负载下修复这些问题，并发布延迟和质量报告。

## 概念

该管道有五个流式传输阶段：**音频输入**（来自浏览器或PSTN的WebRTC）， **ASR**（从Deepgram Nova-3或更快的whisper流式传输部分转录本），**转弯检测** （VAD加上一个小型转弯检测器模型，读取部分转录本以获得完成提示），**LLM**（在判断回合完成后立即流式传输令牌），**TTS**（在第一个LLM令牌后约200毫秒内流式传输音频）。

三个交叉关注点。**插话**：座席在讲话时，用户开始讲话，TTS取消，ASR立即摘机。**工具使用**：在会话中调用功能（天气，日历）必须在一个侧通道上运行，而不会使音频中断；代理预填充确认令牌（“一秒钟……”）**背压**：在丢包情况下，保留部分抄本，VAD提高语音门阈值，代理避免对未确认的消息讲话。

测量条是定量的。在15 dB信噪比的Hamming VAD基准上，我们低于8%。在100次测量呼叫中，800毫秒下的首次音频输出p50。假截止率低于3%。TTS的MOS在4.2以上。在单个g5.xlarge上进行50个并发调用。这些数字是可交付的。

## 堆栈

- 传输：LiveKit Agents 1.0 (WebRTC) + Twilio PSTN网关；Pipecat 0.0.70作为替代框架
- ASR: Deepgram Nova-3（流式传输，第一部分低于300ms）或更快的低语低语-v3涡轮自托管
- VAD: Silero VAD v5加上LiveKit转弯检测器（读取部分转录本的小型变压器）
- LLM: OpenAI gpt - 40 -realtime紧密集成，Gemini 2.5 Flash Live，或级联Claude Haiku 4.5（流式完井，单独的音频路径）
- TTS: Cartesia Sonic-2（最低首字节）、ElevenLabs Flash v3或用于自主机的开源Orpheus
- 工具：用于天气/日历/预订的FastMCP侧通道；如果工具占用>300ms，代理会预发出填充
- 可观察性：OpenTelemetry语音跨度，Langfuse语音跟踪与音频回放
- 部署：单台g5。xlarge （24GB VRAM）用于自托管Whisper + Orpheus；托管api以实现最低延迟

## 构建它

1. * * WebRTC会话。**建立一个LiveKit房间和一个流麦克风音频的web客户端。在服务器上，附加一个加入房间的代理工作人员。

2. * * ASR流。**输入20ms PCM帧到Deepgram Nova-3（或GPU上更快的耳语）。订阅部分和最终成绩单。记录每个部分的延迟。

3. **VAD和转向检测器。**在帧流上运行Silero VAD v5。在演讲结束时，启动LiveKit转向检测器来检测最新的部分文本。只有当VAD表示沉默500ms并且转弯检测器的评分为> 0.6时，才承诺“转弯完成”。

4. * * LLM流。**在回合完成时，开始LLM呼叫与运行对话加上最终的成绩单。流出令牌。在第一个标记处，交给TTS。

5. * * TTS流。** Cartesia Sonic-2流音频块回来。第一个块必须在第一个LLM令牌的200ms内离开服务器。发送块到LiveKit房间；客户端通过WebRTC抖动缓冲播放。

6. * *闯入。**当VAD在播放TTS时检测到新的用户语音时，立即取消TTS流，丢弃剩余的LLM输出，并重新武装ASR。发布一个

7. **工具侧通道。**将天气和日历注册为函数调用工具。调用时，并发地触发调用；如果在300ms内没有解析，让LLM发出“一秒钟，让我检查一下”作为填充；工具返回后继续。

8. * * Eval利用。**记录100个电话。计算WER（针对保留的转录本），误断率（用户在句子中间取消TTS），首音频输出p50， TTS MOS（人类或NISQA）和抖动丢失测试（丢失3%的数据包）。

9. * *负载测试。**在单个g5上驱动50个并发呼叫。Xlarge与合成调用者。测量持续首音输出p95。

## 练习

1. 将Deepgram Nova-3换成g5.xlarge上更快的whisper v3涡轮增压。测量延迟和WER差距。确定cpu vs gpu决策的重要性。

2. 添加中断仲裁策略：当用户在工具调用期间闯入时，代理怎么办？比较三种策略（硬取消，完成-工具-然后停止，下一个回合排队）。

3. 做一个对抗性转向检测器测试：在句子中间给用户长时间的停顿。调整VAD沉默阈值和转弯检测器评分阈值，以获得最低的假截止，而不超过900ms。

4. 通过Twilio在PSTN上部署相同的代理。比较PSTN的first-audio-out和WebRTC。解释抖动缓冲器和编解码器的区别。

5. 添加非英语语言（日语，西班牙语）的语音活动检测。测量Silero VAD v5的误触发率与特定语言的微调。

## 关键术语

| Term | What people say | What it actually means |
|------|-----------------|------------------------|
| Turn detection | "End of utterance" | Classifier that, given VAD silence and a partial transcript, decides the user is done speaking |
| Barge-in | "Interruption handling" | Canceling TTS mid-playback when VAD detects new user speech |
| First-audio-out | "Latency" | Time from user stops speaking to the first audio packet leaving the server |
| VAD | "Speech gate" | Model classifying audio frames as speech vs silence; Silero VAD v5 is the 2026 default |
| Jitter buffer | "Audio smoothing" | Client-side buffer that holds packets briefly to absorb network variance |
| Filler | "Acknowledgment token" | Short phrase the agent emits to avoid silence when a tool is slow |
| MOS | "Mean opinion score" | Perceptual speech quality rating; NISQA is the automated proxy |
