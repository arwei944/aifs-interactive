# Capstone 16 - GitHub Issue-to-PR自治代理

> AWS远程SWE代理、光标后台代理、OpenAI Codex云和谷歌Jules都发布了相同的2026年产品形状：标记问题，获得PR。在云沙箱中运行代理，验证测试通过，并发布具有基本原理的审查就绪PR。困难的部分是自动再现回购的构建环境，防止凭证泄漏，执行每个回购预算，并确保代理不能强制推送。此顶点构建自托管版本，并将其与托管替代版本在成本和通过率上进行比较。

**Type:** Capstone
**Languages:** Python (agent), TypeScript (GitHub App), YAML (Actions)
**Prerequisites:** Phase 11 (LLM engineering), Phase 13 (tools), Phase 14 (agents), Phase 15 (autonomous), Phase 17 (infrastructure)
**运行阶段：** P11·P13·P14·P15·P17
**Time:** 30 hours

## 问题

异步云编码代理是一个独立于交互编码代理的产品类别（顶点01）。UX是一个GitHub标签。你给一个问题贴上标签没有交互回路，就没有终端。AWS远程SWE代理、光标后台代理、OpenAI Codex云、谷歌Jules和Factory Droids都汇聚于此。

工程上的挑战是具体的：环境再现（代理必须在没有缓存的开发映像的情况下从零开始构建repo）、不稳定的测试（必须重新运行或隔离）、凭证范围（具有最小细粒度权限的GitHub应用程序）、每天每个repo的预算执行以及非强制推送策略。顶标衡量的是相对于托管替代方案的通过率、成本和安全性。

## 概念

触发器是GitHub的webhook （issue标签或PR评论）。调度程序将工作排队到ECS Fargate或Lambda。worker将repo放入Daytona或E2B沙盒中，并从repo（语言，框架）推断出通用Dockerfile。代理运行一个针对Claude Opus 4.7或gpt -5.4 codex的迷你sweeagent或sweeagent v2循环。它迭代：读取代码，提出修复，应用补丁，运行测试。

验证是门控步骤。完整CI必须在PR打开之前通过沙箱。计算覆盖增量；如果负值超过阈值，PR打开但被标记代理将基本原理作为PR描述加上一个

安全性通过两个不同的GitHub界面进行作用域：应用程序提供一个带有的短期安装令牌分支保护（而不是应用程序权限）强制“不直接写入”的路径范围只读访问每天每个回购的预算上限由调度员执行（例如，每天每个回购最多5个PR，每个PR 20美元）。

## 体系结构

```
GitHub issue labeled `@agent fix` or PR comment
            |
            v
    GitHub App webhook -> AWS Lambda dispatcher
            |
            v
    ECS Fargate task (or GitHub Actions self-hosted runner)
       - pull repo
       - infer Dockerfile (language, package manager)
       - Daytona / E2B sandbox with target runtime
       - clone -> git worktree -> agent branch
            |
            v
    mini-swe-agent / SWE-agent v2 loop
       Claude Opus 4.7 or GPT-5.4-Codex
       tools: ripgrep, tree-sitter, read/edit, run_tests, git
            |
            v
    verify CI passes in-sandbox + coverage delta check
            |
            v (verified)
    git push + open PR via GitHub App
       PR body = rationale + diff summary + trace URL
       label: needs-review
            |
            v
    operator reviews; can @-mention agent for follow-ups
```

## 堆栈

- 触发器：GitHub应用程序与细粒度令牌；webhook接收器通过Lambda或Fly.io
- Worker: ECS Fargate任务（或GitHub Actions自托管运行器）
- 沙盒：Daytona devcontainer或E2B沙盒每个任务
- 药剂循环：迷你的SWE-agent基线或SWE-agent v2高于Claude Opus 4.7 / GPT-5.4-Codex
- 检索：tree-sitter repo-map + ripgrep
- 验证：全CI - in-sandbox +覆盖delta gate
- 可观察性：从PR主体链接到每个PR跟踪档案的Langfuse
- 预算：每次回购每日美元上限；每天每个回购的最高限额

## 构建它

1. **GitHub App.**细粒度安装令牌：问题读+写，pull_requests写，内容读+写，工作流读。分支保护（唯一可以做到这一点的表面）强制“不直接推到”该应用程序不在旁路列表中。工人强制执行“不写”

2. * * Webhook接收器。** Lambda函数接受问题标签/ PR评论webhook。按标签筛选排队到SQS。

3. * *调度员。**从SQS弹出任务。强制执行每天每个回购的预算。启动一个带有回购URL、问题主体和一个新的Daytona沙盒的ECS Fargate任务。

4. * *环境推理。**检测语言（Python, Node, Go, Rust）和包管理器（uv, pnpm, Go mod, cargo）。如果Dockerfile不存在，则动态生成Dockerfile。

5. * *剂循环。** mini-瑞典代理或瑞典代理v2与克劳德Opus 4.7。工具：ripgrep， tree-sitter repo-map, read_file, edit_file, run_tests, git。硬性限制：20美元成本，30分钟挂钟，30轮代理。

6. * *验证。**循环结束后，在沙箱中运行完整的测试套件。通过jacoco / coverage.py计算覆盖率delta。如果CI值为1 / 2，则不开启PR。如果覆盖率下降超过2%，则开启PR

7. * *公关发布。**推代理分支。通过GitHub API打开PR：标题，基本原理，diff摘要，跟踪URL，成本，转弯。

8. * *凭据卫生。** Worker使用一个短期的GitHub App安装令牌运行。日志在存档前要清除秘密。

9. * * Eval。** 30种不同难度的内部问题。衡量通过率、PR质量（差异大小、风格、覆盖率）、成本、延迟。在相同的问题上与游标后台代理和AWS远程SWE代理进行比较。

## 练习

1. 添加“修复片状测试”模式：标签

2. 在三个共同的问题上比较成本和光标后台代理。报告哪些工具在哪里获胜。

3. 实现预算仪表板：每个仓库每天的成本，每个用户的成本。异常警报。

4. 构建一个“试运行”模式，在不运行CI的情况下打开PR草案，这样审阅者就可以便宜地检查计划。

5. 添加保留策略：超过7天未合并的PR分支将被自动删除。

## 关键术语

| Term | What people say | What it actually means |
|------|-----------------|------------------------|
| GitHub App | "Scoped bot identity" | App with fine-grained permissions + short-lived installation token |
| Async cloud agent | "Background agent" | Non-interactive worker that runs in a cloud sandbox, not a terminal |
| Environment inference | "Dockerfile synthesis" | Detect language + package manager, generate a Dockerfile if absent |
| Verification | "CI-in-sandbox" | Run the full test suite inside the worker before opening a PR |
| Coverage delta | "Coverage preservation" | Change in test coverage % from base to agent branch |
| Per-repo budget | "Daily ceiling" | Dollar and PR-count cap enforced at the dispatcher |
| Rationale | "PR body explanation" | Agent's summary of what changed and why; required in the PR body |
