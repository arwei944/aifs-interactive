# 用于统一多模态模型的解耦编码器

> 统一的多模态模型具有不可避免的张力。理解需要语义特征——SigLIP或DINOv2输出向量富含概念级信息。Generation想要重建友好的代码- VQ令牌组成回清晰的像素。这两个目标在一个编码器中是不兼容的。Janus （DeepSeek， 2024年10月）和Janus- pro （DeepSeek， 2025年1月）认为解决办法是停止尝试：将两个编码器解耦。在任务之间共享Transformer体，但通过SigLIP进行路由理解，并通过VQ标记器生成。在7B时，Janus-Pro在GenEval上击败了dell - e3，而在MMMU上与LLaVA相匹配。这节课读到为什么两个编码器在一个失败的地方工作。

**Type:** Build
**Languages:** Python (stdlib, dual-encoder routing + shared-body signal)
**Prerequisites:** Phase 12 · 13 (Transfusion), Phase 12 · 14 (Show-o)
**Time:** ~120 minutes

## 学习目标

- 解释为什么单个共享编码器会影响理解或生成质量。
- 描述Janus-Pro的路由：用于理解输入端的SigLIP特性，用于生成输入和输出端的VQ令牌。
- 追踪使Janus- pro在Janus失败的地方取得成功的数据混合缩放。
- 比较解耦（Janus-Pro）、耦合连续（Transfusion）和耦合离散（Show-o）架构。

## 这个问题

统一模型在理解和生成方面共享一个Transformer体。之前的尝试（变色龙，Show-o，输血）都使用一个视觉标记器来表示两个方向。标记器是一种折衷：

- 针对重建（生成）进行了优化：VQ-VAE捕获细粒度的像素细节，但生成的标记语义一致性较弱。
- 针对语义（理解）进行了优化：SigLIP嵌入将“猫”图像分组在“猫”标记附近，但不允许良好的重建。

Show-o和Transfusion在一个方向上通过明显的质量税来支付这笔费用。Janus-Pro问：当任务有不同的需求时，为什么需要一个标记器？

## 这个概念

### 解耦视觉编码

Janus-Pro的架构将两个编码器分开：

- 理解的道路。输入图像→SigLIP-SO400m→2层MLP→Transformer本体。
- 生成的路径。输入图像（如果以现有图像为条件）→VQ标记器→令牌id→Transformer体。
- 输出的一代。由Transformer预测的图像符号→VQ解码器→像素。

Transformer本体是共用的。身体的上游和下游都是特定任务的。

输入通过提示格式消除歧义：a`<generate>` routes through VQ. 或者路由是从任务中隐式的。

### 为什么会这样？

理解损失获得SigLIP特征，clip风格的预训练已经针对语义相似性进行了调整。该模型的感知基准优于Show-o / Transfusion，因为输入特征更适合任务。

代损失获得VQ令牌，令牌器已为重建对其进行了调优。图像质量比Show-o有所提高，因为VQ代码清晰地组合回像素。

共享Transformer体看到两个输入分布（SigLIP和VQ），并学习如何使用这两个输入分布。声称：足够的数据+足够的参数，身体吸收开关。

### 数据扩展- Janus vs Janus- pro

Janus （original, arXiv 2410.13848）引入了解耦，但在小规模（13 b参数，有限的数据）。Janus-Pro （arXiv 2501.17811）缩放：

- 7B参数（vs 1.3B）。
- 第一阶段（对齐）的图像-文本对从72M增加到90M。
- 第二阶段（统一）从26M提高到72M。
- 为阶段3添加了200k图像生成指令样本。

结果：Janus-Pro-7B在MMMU上与LLaVA匹配（60.3 vs ~58），在GenEval上击败DALL-E 3 （0.80 vs 0.67）。一个开放的模式，在统一频谱的两边都有竞争力。

### JanusFlow -整流变体

JanusFlow （arXiv 2411.07975）将VQ生成路径交换为整流生成路径（连续）。这个分割变成了用于理解的siglip +用于生成的纠错流。质量天花板进一步提升。架构仍然是解耦-编码器-共享-主体。

### 共享机构的工作

Transformer本体处理一个统一的序列，但有两个输入分布。它的工作是：

- 为了便于理解：使用SigLIP特性+文本标记→自动回归地发出文本。
- 对于生成：使用文本标记+（可选的图像VQ标记）→自动回归地发出图像VQ标记。

身体没有每个块特定于模态的重量。它是文本风格的转换器，您可以在Qwen或Llama中找到，再加上两个输入适配器。

有趣的是，这意味着Janus-Pro的身体可以从预训练的LLM初始化。Janus-Pro确实是从DeepSeek-MoE-7B初始化的。这个选择很重要：LLM提供了纯粹从零开始的统一模型难以达到的推理能力。

### 与国际大学相比

internv -u（第12.10课）是2026年的后续课程。它结合了:

- 原生多模态预训练（InternVL3骨干）。
- 解耦编码器路由（SigLIP输入，VQ +扩散头输出）。
- 统一理解+生成+编辑。

InternVL-U将Janus-Pro的架构选择纳入一个更大的框架中。解耦编码器的想法现在是大规模统一模型的默认值。

### 限制

解耦编码器增加了架构的复杂性。两个标记器要训练，两个输入路径要维护，两组失效模式。对于不需要生成的产品，Janus-Pro是过度设计的-选择llava家族理解模型。

对于不需要理解的产品，Janus-Pro是合格的-选择一个稳定的扩散3 /通量模型。

对于两者都需要的产品，Janus-Pro现在是参考开放架构。

## 使用它


- 两个模拟编码器：类siglip（产生256个模糊语义向量）和类vq（产生整数代码）。
- 一个基于任务标签选择编码器的提示路由器。
- 一个共享主体（替身），它处理令牌序列，而不管由哪个编码器产生它们。
- 从阶段1（校准）切换到阶段3（指令调谐）加权样本调度。

打印3个示例的路由路径：图像QA， T2I，图像编辑。

## 船这

这一课产生了如果一个产品想要在前沿质量上统一生成+理解，它会选择Janus-Pro、JanusFlow或InternVL-U，并给出具体的数据规模推荐。

## 练习

1. Janus-Pro-7B在通用上击败了dell - e - 3。解释为什么7B开放模型可以在生成上与前沿专有模型相匹配，但在理解上却不行。

2. 实现一个路由器功能：给定提示文本，分类为你如何处理模棱两可的提示，比如“先描述后素描”？

3. JanusFlow将VQ路径替换为整流。Transformer体现在输出什么，损耗有什么变化？

4. 提出Janus-Pro架构可以处理的第四个任务，多一个解耦编码器。例如：图像分割（dino风格），深度（midas风格）。

5. 阅读Janus-Pro第4.2节关于数据缩放。哪个数据阶段对T2I与Janus的质量提升贡献最大？

## 关键术语

| Term | What people say | What it actually means |
|------|-----------------|------------------------|
| Decoupled encoding | "Two visual encoders" | Separate tokenizer or encoder per direction: semantic for understanding, reconstruction for generation |
| Shared body | "One transformer" | Single transformer processes either encoder's output; no modality-specific weights |
| SigLIP for understanding | "Semantic features" | CLIP-family vision tower providing rich conceptual features but poor reconstruction |
| VQ for generation | "Reconstruction codes" | Vector-quantized tokens that decode cleanly back to pixels |
| JanusFlow | "Rectified-flow variant" | Janus-Pro with a continuous flow-matching generation head instead of VQ |
| Routing tag | "Task tag" | Prompt marker (`<understand>` / `<generate>`) that picks the input encoder |
