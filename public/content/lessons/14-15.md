# 人员：基于角色的人员和流程

> CrewAI是2026年基于角色的多代理框架——代理、任务、团队、流程作为四个基本元素。文档中的生产指导：“对于任何生产就绪的应用程序，从Flow开始。”

**Type:** Learn + Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 14 · 12 (Workflow Patterns), Phase 14 · 14 (Actor Model)
**Time:** ~60 minutes

## 学习目标

- 命名CrewAI的四个原语——Agent、Task、Crew、Process——以及每个原语的角色。
- 区分团队（自主的基于角色的协作）和流（事件驱动的确定性工作流）。
- 解释为什么文档建议从生产流程开始，从勘探人员开始。
- 实现一个stdlib Crew runner和一个stdlib Flow runner；展示各自的闪光点。

## 这个问题

采用多代理框架的团队也遇到了同样的问题：“自主协作”听起来很棒，但是当客户提交错误时，您需要确定性的重放。CrewAI明确地划分了这一点——crew用于创造性协作，flow用于事件驱动的、可审计的、生产形状的工作流。

## 这个概念

### 的四种基本类型

- **代理。角色+目标+背景故事+工具。背景故事是承重的——它塑造了基调和判断。
- **的任务。** Description + expected_output +已分配代理。可重用的工作单元。
- **船员。**排序代理和任务的容器。拥有执行进程。
- **的过程。**顺序或分层（与管理代理）或共识。

### 人员vs流量

- **船员。**自主，LLM驱动。适用于开放式任务：研究、头脑风暴、初稿。框架在运行时选择形状。
- **流。事件驱动，代码所有的图。每个步骤触发一个触发器（函数装饰器，事件匹配）。有利于生产：可观察的、可测试的、确定的。

CrewAI 2026文档说：使用flow启动生产应用程序；当自动驾驶获得成本时，将crew作为子步骤加入。

### 记忆系统

CrewAI提供了四种开箱即用的内存类型：短期（运行内）、长期（跨运行）、实体（每个实体事实）、上下文（检索时汇编）。与矢量存储的集成是第一方的。

### AWS Bedrock集成

CrewAI已经记录了AWS Bedrock与CloudWatch、AgentOps和Langfuse可观察性挂钩的集成。AWS文档在他们的基准测试中引用了与LangGraph相比，在QA任务上的速度提高了5.76倍——将特定框架的数字作为方向，而不是绝对的。

### 依赖形状

独立于LangChain。Python 3.10 - -3.13。用途30k+ GitHub将于2026年初启用。

### 这种模式哪里出错了

- ** Crew-as-prod。**在prod中使用自由形式的Crew而不使用Flow包装器。输出变异性高；调试是痛苦的。
- **基本信息膨胀。2000字的背景故事超出了上下文预算。保持紧绷。
- **过程混乱。**分层进程增加了一个管理代理，用于路由；只有当你有4+专家时才使用。

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Agent | "Persona" | Role + goal + backstory + tools |
| Task | "Unit of work" | Description + expected output + assignee |
| Crew | "Agent team" | Container for Agents + Tasks + Process |
| Process | "Execution strategy" | Sequential / Hierarchical / Consensual |
| Flow | "Deterministic workflow" | Event-driven, code-owned, testable |
| Backstory | "Persona prompt" | Tone and judgment shaper for the Agent |
| Entity memory | "Per-entity facts" | Memory scoped to a customer/account/issue |
