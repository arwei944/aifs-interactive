# 为什么多代理?

> 一个探员碰壁了。明智的做法不是建立更大的代理商，而是增加更多的代理商。

**Type:** Learn
**Languages:** TypeScript
**Prerequisites:** Phase 14 (Agent Engineering)
**Time:** ~60 minutes

## 学习目标

- 确定单代理上限（上下文溢出、混合专业知识、顺序瓶颈），并解释何时拆分为多个代理是正确的做法
- 比较编排模式（管道模式、并行扇出模式、主管模式、分层模式），并为给定的任务结构选择正确的编排模式
- 设计一个具有明确角色边界、共享状态和通信契约的多代理系统
- 分析多代理复杂性（延迟、成本、调试难度）与单代理简单性之间的权衡

## 这个问题

你在第14阶段造了一个特工。它的工作原理。它可以读取文件、运行命令、调用api并对结果进行推理。然后将其指向一个真实的代码库：200个文件、三种语言、依赖于基础设施的测试，以及在编写代码之前研究外部api的需求。

代理人窒息了。不是因为LLM笨，而是因为任务超出了一个代理循环所能处理的范围。上下文窗口充满了文件内容。代理忘记了它在40次工具调用前读取的内容。它试图同时成为研究人员、编码员和审稿人，但这三者都做得很差。

这是单一代理的上限。每次任务需要：

- **更多的上下文比适合在一个窗口** -读取50个文件吹超过200k令牌
- **不同的专业知识在不同的阶段** -研究需要不同的提示比代码生成
- **工作可以并行发生** -为什么读取三个文件顺序当你可以同时读取它们？

## 这个概念

### 单代理上限

单个代理是一个循环、一个上下文窗口、一个系统提示符。图片:

```
┌─────────────────────────────────────────┐
│            SINGLE AGENT                 │
│                                         │
│  ┌───────────────────────────────────┐  │
│  │         Context Window            │  │
│  │                                   │  │
│  │  research notes                   │  │
│  │  + code files                     │  │
│  │  + test output                    │  │
│  │  + review feedback                │  │
│  │  + API docs                       │  │
│  │  + ...                            │  │
│  │                                   │  │
│  │  ██████████████████████ FULL ███  │  │
│  └───────────────────────────────────┘  │
│                                         │
│  One system prompt tries to cover       │
│  research + coding + review + testing   │
│                                         │
│  Result: mediocre at everything         │
└─────────────────────────────────────────┘
```

三件事被打破了：

1. **上下文饱和度** -工具结果堆积。到第30轮时，代理已经消耗了文件内容、命令输出和先前推理的150k令牌。第5回合的关键细节丢失了。

2. 角色混淆——系统提示“您是研究员、编码员、审稿人和测试人员”会导致代理一半研究一半编码，永远不会完成审查。

3. **顺序瓶颈-代理读取文件A，然后文件B，然后文件c。三个串行LLM调用。三个串行工具执行。没有并行性。

### 多代理解决方案

把工作分开。给每个代理一个作业、一个上下文窗口和一个针对该作业调优的系统提示符：

```
┌──────────────────────────────────────────────────────────┐
│                    ORCHESTRATOR                          │
│                                                          │
│  "Build a REST API for user management"                  │
│                                                          │
│         ┌──────────┬──────────┬──────────┐               │
│         │          │          │          │               │
│         ▼          ▼          ▼          ▼               │
│   ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐  │
│   │RESEARCHER│ │  CODER   │ │ REVIEWER │ │  TESTER  │  │
│   │          │ │          │ │          │ │          │  │
│   │ Reads    │ │ Writes   │ │ Checks   │ │ Runs     │  │
│   │ docs,    │ │ code     │ │ code     │ │ tests,   │  │
│   │ finds    │ │ based on │ │ quality, │ │ reports  │  │
│   │ patterns │ │ research │ │ finds    │ │ results  │  │
│   │          │ │ + spec   │ │ bugs     │ │          │  │
│   └─────┬────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘  │
│         │           │            │             │         │
│         └───────────┴────────────┴─────────────┘         │
│                          │                               │
│                     Merge results                        │
└──────────────────────────────────────────────────────────┘
```

每个代理有：
- 集中的系统提示(“您是代码审阅者。你唯一的工作就是找bug。”)
- 它自己的上下文窗口（不受其他代理工作的污染）
- 明确的输入/输出合同（接收研究笔记，输出代码）

### 真正的系统是这样做的

**Claude Code子代理** -当Claude Code生成子代理时父类保持其上下文干净。子进程执行重点工作并返回摘要。

**Devin** -运行一个规划代理，一个编码器代理，和一个浏览器代理。计划者把工作分成几个步骤。编码员编写代码。浏览器研究文档。每个都有单独的上下文。

**多代理编码团队(sw -bench)** -在sw -bench上表现最好的系统使用读取代码库的研究人员，设计修复的计划者和实现它的编码员。单智能体系统得分较低。

**ChatGPT深度研究** -并行生成多个搜索代理，每个代理探索不同的角度，然后综合结果。

### 频谱

多代理不是二进制的。它是一个光谱：

```
SIMPLE ──────────────────────────────────────────── COMPLEX

 Single        Sub-         Pipeline      Team         Swarm
 Agent         agents

 ┌───┐       ┌───┐        ┌───┐───┐    ┌───┐───┐    ┌─┐┌─┐┌─┐
 │ A │       │ A │        │ A │ B │    │ A │ B │    │ ││ ││ │
 └───┘       └─┬─┘        └───┘─┬─┘    └─┬─┘─┬─┘    └┬┘└┬┘└┬┘
               │                │        │   │       ┌┴──┴──┴┐
             ┌─┴─┐          ┌───┘───┐    │   │       │shared │
             │ a │          │ C │ D │  ┌─┴───┴─┐    │ state │
             └───┘          └───┘───┘  │  msg   │    └───────┘
                                       │  bus   │
 1 loop      Parent +      Stage by    │       │    N peers,
 1 context   child tasks   stage       └───────┘    emergent
                                       Explicit      behavior
                                       roles
```

**单代理** -一个循环，一个提示。适用于简单的任务。

**Subagents** -父任务生成子任务。父母维护该计划。孩子们回来了。这就是Claude Code所做的。

**流水线** -代理按顺序运行。Agent A的输出变成了Agent B的输入。适用于分阶段工作流程：研究->代码->审查->测试。

**团队** -代理与共享消息总线并行运行。每个人都有一个角色。协调者坐标。当同时需要不同的技能时很有用。

**群** -许多相同或接近相同的代理共享状态。没有固定的协调者。代理从队列中获取工作。适用于高吞吐量并行任务。

### 四种多智能体模式

#### 模式一：管道

```
Input ──▶ Agent A ──▶ Agent B ──▶ Agent C ──▶ Output
          (research)  (code)      (review)
```

每个代理转换数据并将其传递下去。原因很简单。一个阶段的失败阻碍了其他阶段的发展。

#### 模式2：扇出/扇入

```
                ┌──▶ Agent A ──┐
                │              │
Input ──▶ Split ├──▶ Agent B ──├──▶ Merge ──▶ Output
                │              │
                └──▶ Agent C ──┘
```

在并行代理之间分割工作，然后合并结果。适用于分解为独立子任务的任务。

#### 模式3：协调者-工作者

```
                    ┌──────────┐
                    │  Orch.   │
                    └──┬───┬───┘
                  task │   │ task
                 ┌─────┘   └─────┐
                 ▼               ▼
           ┌──────────┐   ┌──────────┐
           │ Worker A │   │ Worker B │
           └──────────┘   └──────────┘
```

聪明的编排者决定要做什么，把任务委派给工作人员，然后综合结果。编排器本身就是一个代理，拥有产卵工人的工具。

#### 模式4：同伴群

```
         ┌───┐ ◄──── msg ────▶ ┌───┐
         │ A │                  │ B │
         └─┬─┘                  └─┬─┘
           │                      │
      msg  │    ┌───────────┐     │ msg
           └───▶│  Shared   │◄────┘
                │  State    │
           ┌───▶│  / Queue  │◄────┐
           │    └───────────┘     │
      msg  │                      │ msg
         ┌─┴─┐                  ┌─┴─┐
         │ C │ ◄──── msg ────▶ │ D │
         └───┘                  └───┘
```

没有中央指挥。代理进行点对点通信。决策来自于互动。更难调试，但可以扩展到许多代理。

### 何时不使用多代理

多代理增加了复杂性。代理之间的每条消息都是潜在的故障点。调试从“读取一个对话”到“跨五个代理跟踪消息”。

**在以下情况下保持单一代理
- 该任务适合一个上下文窗口（在大约100k个工作数据令牌下）
- 您不需要为不同的阶段提供不同的系统提示
- 顺序执行足够快
- 这个任务非常简单，拆分它增加的开销大于价值

**复杂性成本：**
- 每个代理边界都是一个有损压缩步骤：代理a的完整上下文被总结为代理B的消息
- 协调逻辑（谁在什么时候、以什么顺序做什么）本身就是bug的来源
- 延迟增加：N个代理意味着N个串行LLM调用最少，如果它们需要来回通信则更多
- 成本倍增：每个代理独立地燃烧令牌

经验法则：如果一个任务需要少于20个工具调用，并且适合10万个令牌，那么就让它保持单一代理。

### Step 2: Specialist Agents

Now split it. Each agent gets one job:

```typescript
type SpecialistAgent = {
  name: string;
  systemPrompt: string;
  run: (input: string) => Promise<AgentResult>;
};

function createSpecialist(name: string, systemPrompt: string): SpecialistAgent {
  return {
    name,
    systemPrompt,
    run: async (input: string) => {
      const result = await fakeLLMCall(systemPrompt, input);
      return {
        content: result.output,
        tokensUsed: result.tokens,
        toolCalls: result.calls,
      };
    },
  };
}

const researcher = createSpecialist(
  "researcher",
  "You are a technical researcher. Read documentation, find patterns, and summarize findings. Output only the facts needed for implementation."
);

const coder = createSpecialist(
  "coder",
  "You are a senior TypeScript developer. Given requirements and research notes, write clean, tested code. Nothing else."
);

const reviewer = createSpecialist(
  "reviewer",
  "You are a code reviewer. Find bugs, security issues, and logic errors. Be specific. Cite line numbers."
);
```

每个专家都有一个重点提示。每个都获得一个干净的上下文窗口，其中只包含所需的输入。

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|----------------------|
| Swarm | "A hive mind of AI agents" | A set of peer agents with shared state and no fixed leader. Behavior emerges from local interactions. |
| Orchestrator | "The boss agent" | An agent whose tools include spawning and managing other agents. It plans and delegates but may not do the actual work. |
| Coordinator | "The traffic cop" | A non-agent component (often just code, not an LLM) that routes messages between agents based on rules. |
| Consensus | "The agents agree" | A protocol where multiple agents must reach agreement before proceeding. Used when conflicting outputs need resolution. |
| Emergent behavior | "The agents figured it out themselves" | System-level patterns that arise from agent interactions but were not explicitly programmed. Can be useful or harmful. |
| Fan-out / fan-in | "Map-reduce for agents" | Splitting a task across parallel agents (fan-out), then combining their results (fan-in). |
| Message passing | "Agents talk to each other" | The communication mechanism between agents: structured data sent from one agent to another, replacing shared context windows. |
