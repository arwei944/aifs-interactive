# Why multiple agents?

> An agent hit a wall. The wise approach is not to establish larger agents, but to increase more agents.

**Type:** Learn
**Languages:** TypeScript
**Prerequisites:** Phase 14 (Agent Engineering)
**Time:** ~60 minutes

## Learning objectives

- Determine the upper limit of a single agent (context overflow, mixed expertise, sequential bottleneck), and explain when it is the right approach to split into multiple agents
- Compare the orchestration patterns (pipeline pattern, parallel fan-out pattern, supervisor pattern, hierarchical pattern), and select the correct orchestration pattern for the given task structure
- Design a multi-agent system with clear role boundaries, shared states and communication contracts
- Analyze the trade-off between the complexity of multi-agent (latency, cost, debugging difficulty) and the simplicity of single-agent

## This question

You created an agent in stage 14. Its working principle. It can read files, run commands, call apis and reason about the results. Then point it to a real code base: 200 files, three languages, infrastructure-dependent tests, and the need to study external apis before writing the code.

The agent suffocated. It's not because the LLM is stupid, but because the task is beyond the capacity of a proxy loop to handle. The context window is filled with file content. The agent forgot what it had read before 40 tool calls. It attempts to be a researcher, a coder and a reviewer at the same time, but performs poorly in all three aspects.

This is the upper limit of a single agent. Each task requires:

- ** More context than suitable in one window ** - Reading 50 files blow over 200k tokens
- ** Different professional knowledge at different stages ** - Research requires different prompts than code generation
- ** Work can occur in parallel ** - Why read three files in sequence when you can read them simultaneously?

## This concept

### Single-agent upper limit

A single agent is a loop, a context window, and a system prompt. Picture

```
┌─────────────────────────────────────────┐
│            SINGLE AGENT                 │
│                                         │
│  ┌───────────────────────────────────┐  │
│  │         Context Window            │  │
│  │                                   │  │
│  │  research notes                   │  │
│  │  + code files                     │  │
│  │  + test output                    │  │
│  │  + review feedback                │  │
│  │  + API docs                       │  │
│  │  + ...                            │  │
│  │                                   │  │
│  │  ██████████████████████ FULL ███  │  │
│  └───────────────────────────────────┘  │
│                                         │
│  One system prompt tries to cover       │
│  research + coding + review + testing   │
│                                         │
│  Result: mediocre at everything         │
└─────────────────────────────────────────┘
```

Three things were broken:

1. ** Context saturation ** - Tool result accumulation. By the 30th round, the agent had consumed 150k tokens for file content, command output, and previous reasoning. The key details of the fifth round were lost.

2. Role confusion - When the system prompts "You are a researcher, coder, reviewer and tester", it will cause the agent to research half and code half, and the review will never be completed.

3. Sequential bottleneck - The agent reads file A, then file B, and then file c. Three serial LLM calls. Three serial tools are executed. There is no parallelism.

### Multi-agent solution

Separate the work. Give each agent a job, a context window, and a system prompt tuned for that job:

```
┌──────────────────────────────────────────────────────────┐
│                    ORCHESTRATOR                          │
│                                                          │
│  "Build a REST API for user management"                  │
│                                                          │
│         ┌──────────┬──────────┬──────────┐               │
│         │          │          │          │               │
│         ▼          ▼          ▼          ▼               │
│   ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐  │
│   │RESEARCHER│ │  CODER   │ │ REVIEWER │ │  TESTER  │  │
│   │          │ │          │ │          │ │          │  │
│   │ Reads    │ │ Writes   │ │ Checks   │ │ Runs     │  │
│   │ docs,    │ │ code     │ │ code     │ │ tests,   │  │
│   │ finds    │ │ based on │ │ quality, │ │ reports  │  │
│   │ patterns │ │ research │ │ finds    │ │ results  │  │
│   │          │ │ + spec   │ │ bugs     │ │          │  │
│   └─────┬────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘  │
│         │           │            │             │         │
│         └───────────┴────────────┴─────────────┘         │
│                          │                               │
│                     Merge results                        │
└──────────────────────────────────────────────────────────┘
```

Each agent has:
- Centralized system prompt (" You are a code reviewer." Your only job is to look for bugs. )
- Its own context window (not contaminated by the work of other agents)
- Clear input/output contract (receive research notes, output code)

### This is how a real system works

**Claude Code Sub-agent ** - When Claude Code generates a sub-agent, the parent class keeps its context clean. The child process performs key tasks and returns summaries.

**Devin** - Run a planning agent, an encoder agent, and a browser agent. The planner divided the work into several steps. Coders write code. Browser research the document. Each one has its own context.

** Multi-Agent Coding Team (sw-bench)** - The systems that perform best on sw-bench use researchers who read the code base, planners who designed the fixes, and coders who implemented it. Single-agent systems score relatively low.

**ChatGPT In-depth Research ** - Generate multiple search agents in parallel, each exploring different perspectives, and then synthesize the results.

### Spectrum

Multi-agent is not binary. It is a spectrum:

```
SIMPLE ──────────────────────────────────────────── COMPLEX

             │ a │          │ C │ D │  ┌─┴───┴─┐    │ state │
             └───┘          └───┘───┘  │  msg   │    └───────┘
                                       │  bus   │
 1 loop      Parent +      Stage by    │       │    N peers,
 1 context   child tasks   stage       └───────┘    emergent
                                       Explicit      behavior
                                       roles
```

*"Single agent" - one loop, one prompt. Suitable for simple tasks.

**Subagents** - Parent tasks generate sub-tasks. The parents defended the plan. The children are back. This is what Claude Code does.

*"Assembly line" - The agent operates in sequence. The output of Agent A becomes the input of Agent B. Applicable to phased workflows: Research -> Code -> Review -> testing.

** Team ** - The agent runs in parallel with the shared message bus. Everyone has a role. Coordinator coordinates. It is very useful when different skills are needed simultaneously.

** Group ** - Many identical or nearly identical agents share a state. There is no fixed coordinator. The agent retrieves work from the queue. Suitable for high-throughput parallel tasks.

### Four multi-agent modes

#### Mode One: Pipeline

```
Input ──▶ Agent A ──▶ Agent B ──▶ Agent C ──▶ Output
          (research)  (code)      (review)
```

Each agent converts the data and passes it down. The reason is very simple. The failure of one stage hinders the development of other stages.

#### Mode 2: Fan-out/Fan-in

```
                ┌──▶ Agent A ──┐
                │              │
Input ──▶ Split ├──▶ Agent B ──├──▶ Merge ──▶ Output
                │              │
                └──▶ Agent C ──┘
```

Split the work among parallel agents and then merge the results. Tasks applicable to decomposition into independent sub-tasks.

#### Mode 3: Coordinator - Worker

```
                    ┌──────────┐
                    │  Orch.   │
                    └──┬───┬───┘
                  task │   │ task
                 ┌─────┘   └─────┐
                 ▼               ▼
           ┌──────────┐   ┌──────────┐
           │ Worker A │   │ Worker B │
           └──────────┘   └──────────┘
```

Smart schedulers decide what to do, delegate tasks to the staff, and then synthesize the results. The orchestrator itself is a proxy with tools for egg-laying workers.

#### Mode 4: Peer Group

```
         ┌───┐ ◄──── msg ────▶ ┌───┐
         │ A │                  │ B │
         └─┬─┘                  └─┬─┘
           │                      │
      msg  │    ┌───────────┐     │ msg
           └───▶│  Shared   │◄────┘
                │  State    │
           ┌───▶│  / Queue  │◄────┐
           │    └───────────┘     │
      msg  │                      │ msg
         ┌─┴─┐                  ┌─┴─┐
         │ C │ ◄──── msg ────▶ │ D │
         └───┘                  └───┘
```

There is no central command. The agent conducts point-to-point communication. Decisions come from interaction. It is more difficult to debug, but it can be extended to many agents.

### When not to use multiple agents

Multi-agent increases complexity. Every message between agents is a potential point of failure. Debug from "reading a conversation" to "tracking messages across five agents".

*Maintain a single agent in the following circumstances
- This task is suitable for a context window (under approximately 100k working data tokens).
- You don't need to provide different system prompts for different stages
- Sequential execution is fast enough
- This task is very simple. The additional cost of splitting it is greater than the value

*"Complexity cost:
- Each agent boundary is a lossy compression step: the complete context of agent A is summarized as the message of agent B
- Is the coordination logic (who does what, when, and in what order) itself a source of bugs
- Increased latency: N agents mean that N serial LLM calls are the least, and more if they need to communicate back and forth
- Cost doubling: Each agent burns tokens independently

Rule of thumb: If a task requires less than 20 tool calls and is suitable for 100,000 tokens, then keep it as a single agent.

### Step 2: Specialist Agents

Now split it. Each agent gets one job:

```typescript
type SpecialistAgent = {
  name: string;
  systemPrompt: string;
  run: (input: string) => Promise<AgentResult>;
};

function createSpecialist(name: string, systemPrompt: string): SpecialistAgent {
  return {
    name,
    systemPrompt,

const researcher = createSpecialist(
  "researcher",
  "You are a technical researcher. Read documentation, find patterns, and summarize findings. Output only the facts needed for implementation."
);

const coder = createSpecialist(
  "coder",
  "You are a senior TypeScript developer. Given requirements and research notes, write clean, tested code. Nothing else."

Each expert has a key tip. Each one gets a clean context window that only contains the required input.

The multi-agent version uses more master tokens (three agents, three independent LLM calls), but the context of each agent remains clean. As the system prompts are specialized, the quality of each stage has been improved.

## Key terms

| Term | What people say | What it actually means |
|------|----------------|----------------------|
| Swarm | "A hive mind of AI agents" | A set of peer agents with shared state and no fixed leader. Behavior emerges from local interactions. |
| Orchestrator | "The boss agent" | An agent whose tools include spawning and managing other agents. It plans and delegates but may not do the actual work. |
| Coordinator | "The traffic cop" | A non-agent component (often just code, not an LLM) that routes messages between agents based on rules. |
| Consensus | "The agents agree" | A protocol where multiple agents must reach agreement before proceeding. Used when conflicting outputs need resolution. |
| Emergent behavior | "The agents figured it out themselves" | System-level patterns that arise from agent interactions but were not explicitly programmed. Can be useful or harmful. |
| Fan-out / fan-in | "Map-reduce for agents" | Splitting a task across parallel agents (fan-out), then combining their results (fan-in). |
| Message passing | "Agents talk to each other" | The communication mechanism between agents: structured data sent from one agent to another, replacing shared context windows. |
