# A2A - Agent-to-Agent协议

> 谷歌于2025年4月宣布A2A；到2026年4月，该规范在https://a2a-protocol.org/latest/specification/上发布，有150多个组织支持它。A2A是MCP的水平补充（第13课）：其中MCP是垂直的（agent↔工具），A2A是对等的（agent↔agent）。它定义了Agent card（发现）、带有工件（文本、结构化数据、视频）的任务、不透明的任务生命周期和授权。生产系统越来越多地将MCP与A2A配对。谷歌Cloud在2025-2026年期间将A2A支持纳入Vertex AI Agent Builder。

**Type:** Learn + Build
**Languages:** Python (stdlib, `http.server`, `json`)
**Prerequisites:** Phase 16 · 04 (Primitive Model)
**Time:** ~75 minutes

## 问题

您的代理需要调用另一个系统上的另一个代理。如何?您可以公开HTTP端点，定义定制的JSON模式，并希望另一方使用它。每一对代理都成为自定义集成。

A2A是该呼叫的通用有线协议。标准发现，标准任务模型，标准传输，标准工件。类似于HTTP+REST，但作为一等公民的代理。

## 概念

### 四大要素

**代理卡。** JSON文档通过读卡片就能发现。

```
GET https://agent.example.com/.well-known/agent.json
→ {
    "name": "code-review-agent",
    "skills": ["review-python", "review-typescript"],
    "endpoints": {
      "tasks": "https://agent.example.com/tasks"
    },
    "auth": {"type": "bearer"},
    "modalities": ["text", "structured"]
  }
```

**任务。**工作单位。一个具有生命周期的异步、有状态对象：客户端发送任务、投票或订阅更新。

**工件。**任务产生的结果类型。文本，结构化JSON，图像，视频，音频。工件是类型化的，所以不同的模态是一级的。

**不透明的生命周期。A2A没有规定远程代理如何解决任务。客户端看到状态转换和工件；实现可以自由地使用任何框架。

### MCP/A2A分裂

- **MCP**（第13课）：代理↔工具。代理通过JSON-RPC向工具服务器读/写。默认为无状态。
- **A2A**: agent↔agent。对等协议;双方都是代理人，都有自己的推理。

生产多代理系统使用这两种方法。A2A对等体调用它这边的MCP工具。这种分离保持了两家公司的清白。

### 发现流

```
Client                     Agent server
  ├──GET /.well-known/agent.json──>
  <──Agent Card JSON─────────────
  ├──POST /tasks {skill, input}──>
  <──201 task_id, state=submitted
  ├──GET /tasks/{id}──────────────>
  <──state=working, 42% done──────
  ├──GET /tasks/{id}──────────────>
  <──state=completed, artifacts──
```

或者用流媒体：SSE订阅

### 身份验证

A2A支持三种常见模式：

- **承载令牌** - OAuth2或不透明。
- **mTLS**—互TLS；组织之间相互证明身份。
- **签名请求** - HMAC的有效载荷。

授权在代理卡中声明；客户发现并遵从。

### 到2026年4月，将有150多个组织

企业采用推动了A2A规模。标题：A2A成为企业代理系统跨越信任边界的方式。谷歌云交付顶点AI Agent Builder A2A支持；Microsoft Agent Framework支持；大多数主要框架（LangGraph、CrewAI、AutoGen）都提供A2A适配器。

### A2A获胜

- * *跨组织的电话。** A公司的代理人打电话给b公司的代理人。没有A2A，每一对都是定制合同。
- * *异构框架。** LangGraph代理调用CrewAI代理调用自定义Python代理。负责规范化。
- * *类型的工件。**视频结果，结构化JSON，音频-所有一流。
- * *长时间运行的任务。**不透明的生命周期+轮询使长达数小时的任务变得简单。

### A2A的挣扎之处

- * *对延迟敏感micro-calls。** A2A的生命周期是异步的。亚毫秒代理到代理不匹配；使用直接RPC。
- **紧密耦合的进程内代理。**如果两个代理运行在同一个Python进程中，A2A的HTTP往返是多余的。
- * *小团队。**规格开销是真实的；内部代理可能不需要手续。

### A2A vs ACP, ANP, NLIP

2024-2026年出现了几个相关的规范：

- **ACP** （IBM/Linux基金会）- A2A的前身，范围更窄。
- **ANP**（代理网络协议）-对等发现重，分散优先。
- **NLIP** （Ecma自然语言交互协议，2025年12月标准化）-自然语言内容类型。

截至2026年4月，A2A是采用最多的对等协议。参见arXiv:2505.02279 （Liu et al.，“A Survey of Agent Interoperability Protocols”）进行比较。

## 船这

检查表:

- **固定规格版本。** A2A仍在发展中；代理卡应声明协议版本。
- **创建幂等任务。**重复提交（网络重试）应该产生一个任务。
- * *工件模式。**声明代理返回的形状；消费者应该验证。
- **速率限制+授权。** A2A面向公众；应用标准的web安全。
- **失败任务的死信。**随着时间的推移检查模式以查找重复出现的故障类型。

## 练习

1. 运行确认客户端发现了服务器并接收到正确的工件。
2. 向服务器添加第二个技能（例如，“总结”）。更新Agent Card。编写一个基于任务类型选择技能的客户端。
3. 实现一个SSE流端点：客户需要做什么不同的事情？
4. 阅读A2A规范（https://a2a-protocol.org/latest/specification/）。确定规范规定的三件事是本演示没有实现的。
5. 比较A2A（代理卡发现）和MCP（服务器端功能列表）自我描述代理和能力探测之间的权衡是什么？

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| A2A | "Agent-to-agent" | Peer protocol for agents to call other agents across systems. Google 2025. |
| Agent Card | "The agent's business card" | JSON at `/.well-known/agent.json` describing skills, endpoints, auth. |
| Task | "The unit of work" | Async stateful object with a lifecycle; artifacts produced on completion. |
| Artifact | "The result" | Typed output: text, structured JSON, image, video, audio. First-class media. |
| Opaque lifecycle | "How it's solved is the agent's business" | Client sees state transitions; server is free to choose framework/tools. |
| Discovery | "Finding the agent" | `GET /.well-known/agent.json` returns the card. |
| MCP vs A2A | "Tools vs peers" | MCP: vertical agent ↔ tool. A2A: horizontal agent ↔ agent. |
| ACP / ANP / NLIP | "Sibling protocols" | Adjacent specs; A2A is the most-adopted 2026. |
