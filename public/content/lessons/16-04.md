# Multi-agent primitive model

> Every multi-agent framework released in 2026 - AutoGen, LangGraph, CrewAI, OpenAI Agent SDK, Microsoft Agent Framework - is a point in the four-dimensional design space. There are four basic elements, nothing more: proxy, switching, shared state, and orchestrator. This lesson builds them from scratch, runs a toy system on all four frames, and then maps each major frame to the same axis, so that you can read any new version in one paragraph.

**Type:** Learn
**Languages:** Python (stdlib)
**Prerequisites:** Phase 14 (Agent Engineering), Phase 16 · 01 (Why Multi-Agent)
**Time:** ~60 minutes

## "Problem"

A new multi-agent framework is released every six months. AutoGen in 2023 In 2024. LangGraph and OpenAI Swarm in 2024. By April 2025. The Microsoft proxy framework RC was released in February 2026. Every press release claims to be a "correct abstraction".

If you try to learn one at a time, you will be exhausted. The api looks different. Doctors have different opinions on what an "agent" is. One framework refers to its shared memory as a "blackboard", another as a "message pool", and the third as a "state graph". You start to suspect that the magnetic field is just stirring.

That's not the case. Under marketing, these four fundamental elements are stable. Study once and read each new framework in one paragraph.

## Concept

### Four basic elements

1. "Agent" - A system prompt plus a list of tools. Stateless; Each run starts from its system prompt and the current message history.
2. Transfer - Transferring control from one agent to another. Mechanically speaking, it is a tool call that returns a new agent or a graph edge that meets the conditions.
3. Shared state - a data structure that any more than one agent can read (and sometimes write to). Message pool, blackboard, key-value storage, vector memory.
4. "Command" - The person who decides the next speaker. Options: Explicit graph (deterministic), LLM speaker selector (soft), handover call for the last speaker (OpenAI Swarm), or scheduler on the queue (cluster architecture).

This is the entire design space. Each frame selects the default value for each axis; The rest is superficial grammar.

### How is each 2026 framework mapped to it

| Framework | Agent | Handoff | Shared state | Orchestrator |
|-----------|-------|---------|--------------|--------------|
| OpenAI Swarm / Agents SDK | `Agent(instructions, tools)` | tool returns Agent | caller's problem | the LLM's next handoff call |
| AutoGen v0.4 / AG2 | `ConversableAgent` | speaker-selector on GroupChat | message pool | selector function (LLM or round-robin) |
| CrewAI | `Agent(role, goal, backstory)` | `Process.Sequential / Hierarchical` | Task outputs chained | manager LLM or static order |
| LangGraph | node function | graph edge + condition | `StateGraph` reducer | the graph, deterministic |
| Microsoft Agent Framework | agent + orchestration patterns | pattern-specific | thread / context | pattern-specific |
| Google ADK | agent + A2A card | A2A task | A2A artifacts | host decides |

The surface differences seem quite significant. Below: The same four knobs.

### Why is this important?

Once you see these primitives, the frame comparison becomes a short list:

- Does the orchestrator trust LLM routes (Swarm) or fix routes in the code (LangGraph)?
- Is it the complete history of the shared state (GroupChat) or projection (statgraph reducer)?
- Can agents modify each other's prompts (CrewAI Manager) or just hand them over (Swarm)?

These three questions answer that 80% of the framework is suitable for the given question. You no longer seek out the "best multi-agent framework", but start designing for the axes that you truly care about.

### Stateless insight

All primitives are stateless except for the shared state. An agent is the function of a (prompt, tool). Switching is a function call. Orchestrator is a scheduler. The only stateful thing in the system is the shared state. All the interesting bugs exist here: memory poisoning (Lesson 15), message sorting, version control, and write contention.

The framework of hidden shared State (Swarm) pushes the problem onto the caller. Concentrate its framework (LangGraph checkpoints, AutoGen pools) to make it inspectable, but shift the coordination cost to the shared state implementation.

### The anatomy of a single primitive person

#### Agent

```
Agent = (system_prompt, tools, model, optional_name)
```

No memory. I'm not in a state. Two agents with the same system prompt and tools are interchangeable. Everything that looks like each agent state is actually in a shared state or in a switching protocol.

#### Switch

```
Handoff = (from_agent, to_agent, reason, payload)
```

There are mainly three implementations:

- ** Function Return ** - The tool returns the next agent. This is the OpenAI Swarm mode. The agent carries routes in its tool mode.
- ** Graph Edge ** -LangGraph. The edges are declarative. The LLM generates a value; Select the next node based on the condition.
- "Speaker Selection" - AutoGen Group Chat. The selector function (sometimes an LLM call itself) reads the pool and selects the next speaker.

#### Shared state

```
SharedState = { messages: [], artifacts: {}, context: {} }
```

There should be at least one message list. Usually more: structured components (CrewAI task output), typed context (LangGraph reducer), external memory (MCP, vector DB).

Two topologies: ** Full pool ** (each agent sees each message) and ** projection ** (the agent sees a role-range view). The full pool is very simple and has poor scalability. It is expected that the pool can be expanded, but pattern design needs to be carried out in advance.

#### Coordinator

```
Orchestrator = ({state, last_speaker}) -> next_agent
```

Four flavors

- ** Static ** - The graph is fixed when constructed (LangGraph deterministic, CrewAI sequential).
- LLM-selected** - LLM reads the pool and selects the next speaker (AutoGen, CrewAI Hierarchical).
- Switching drivers - The current agent is determined by calling the switching tool (Swarm).
- ** Queue-driven ** - Staff extract from the shared queue; There is no definite next speaker (group architecture, matrix).

### What changes are there between the frameworks

Once these primitives are fixed, the remaining design decisions are:

- ** Memory Strategy ** - Transient and persistent checkpoints (LangGraph Checkpoints).
- ** Safety Boundary ** - Who can approve the handover (in the ring).
- ** Cost Accounting ** - Budget per agent token.
- ** Observability ** - Tracking switching, persistent state replay.

All of these can be achieved on top of the source language. None of them are new source languages.

## This ship

Before adopting the new framework, write the primitive mapping for it. If not, it indicates that the documentation is incomplete or the framework is inventing a fifth primitive (rare - check for shared state types you haven't seen before).

## Key terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Agent | "An LLM with tools" | A `(system_prompt, tools, model)` triple. Stateless. |
| Handoff | "Transfer of control" | A structured call that names the next agent and optional payload. Three implementations: function return, graph edge, speaker selection. |
| Shared state | "Memory" / "context" | The only stateful part of a multi-agent system. Message pool or blackboard. |
| Orchestrator | "Coordinator" | Whoever decides who runs next. Static graph, LLM selector, handoff-driven, or queue-driven. |
| Primitive | "Abstraction" | One of the four axes every framework parameterizes. Not a framework feature. |
| Message pool | "Shared chat history" | Full-history shared state. Easy to reason about, scales badly. |
| Projected state | "Scoped view" | Role-specific view into shared state. Scales, requires schema design. |
| Speaker selection | "Who talks next" | Orchestrator pattern where a function (often an LLM) picks the next agent from a group. |
