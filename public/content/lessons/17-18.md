# vLLM生产堆栈与LMCache KV卸载

> vLLM的生产栈是参考Kubernetes部署——路由器、引擎和可观察性连接在一起。LMCache是KV卸载层，它从GPU内存中提取KV缓存，并在查询和引擎（CPU DRAM，然后是磁盘/Ceph）中重用它。vLLM 0.11.0 KV卸载连接器（2026年1月）通过连接器API （v0.9.0+）实现异步和可插拔。卸载延迟不是面向用户的。即使没有共享前缀，LMCache也很有价值——当GPU耗尽KV插槽时，可以从CPU恢复抢占的请求，而不是重新计算预填充。在16倍H100 （80GB HBM）上发布的4 a3-highgpu-4g基准测试：当KV缓存超过HBM时，本机CPU卸载和lmccache都大大提高了吞吐量；在低KV占用时，所有配置都符合基线，开销小。

## 这个问题

当并发性上升时，您的vLLM服务显示gpu在100% HBM时具有抢占事件。请求被驱逐、排队，并且您在一分钟内重新预填充相同的2K-token提示四次。GPU计算花费在冗余的前置文件上；Goodput远低于原始吞吐量。

增加更多gpu的成本是线性的。添加更多HBM是不可能的。但是CPU DRAM很便宜——一个插槽有512 GB以上的延迟，比HBM差几个数量级，但对于“暂时温暖”KV缓存来说很好。

LMCache将KV缓存提取到CPU DRAM中，因此被抢占的请求可以快速恢复，并且跨引擎的重复前缀共享缓存而无需每个引擎重新预填充。

### KV卸载连接器API （v0.9.0+）

vLLM 0.9.0为可插拔的KV缓存后端引入了Connector API。你的引擎将积木卸到连接器上；连接器存储它们（RAM、磁盘、对象存储、LMCache）。请求需要一个块，连接器将它加载回来。

vLLM 0.11.0（2026年1月）增加了一个异步卸载路径——卸载可以在后台发生，所以引擎在通常情况下不会阻塞它。端到端延迟和吞吐量仍然取决于工作负载形状、KV缓存命中率和系统压力；vLLM自己的笔记指出，自定义内核卸载会在低命中率下降低吞吐量，并且异步调度在推测解码方面存在已知的交互问题。

### 本机CPU卸载vs LMCache

**本机vLLM CPU卸载**:engine-local。在主机RAM中存储KV块。快速实现，零网络跳。不会穿过引擎。

**LMCache连接器**：集群级。在共享LMCache服务器（CPU DRAM + Ceph/S3层）中存储块。任何引擎都可以访问块。发布了16x H100基准测试。

当单个引擎有HBM压力时，选择本机。当多个引擎共享前缀（具有公共系统提示的RAG、具有共享模板的多租户）时，选择LMCache。

### 基准行为

16 × H100 （80 GB HBM）横跨4 a3-highgpu-4g测试：

- 低KV占用（短提示，低并发性）：所有配置匹配基线，LMCache增加了~3-5%的开销。
- 适度的占用：LMCache开始帮助跨引擎的前缀重用。
- KV超过HBM：本机CPU卸载和LMCache都大大提高了吞吐量；由于跨引擎共享，LMCache的收益更大。

### 当麦迪是决定性的

- 多租户服务，其中系统提示在租户之间共享。
- 文档块在查询中重复的RAG。
- 基于相同基础的微调变体（LoRA），其中基础模型KV重用减少了冗余工作。
- 重抢占的工作负载：从CPU恢复比重新预填充便宜。

### 何时不启用

- HBM压力小——你付出了额外的开销，却没有任何好处。
- 短上下文（<1K令牌）-传输时间>重新预填充。
- 单租户单提示工作负载—无需重用以捕获。

### 集成分解服务

第17阶段·17个分解的服务+ LMCache化合物：KV从预填充池转移到LMCache中未使用的解码池土地；后续查询从LMCache提取。阶段17·11缓存感知路由器可以路由到本地或lmcache共享缓存匹配的引擎。

### 你应该记住的数字

- vLLM 0.9.0：已发布连接器API。
- vLLM 0.11.0(1月2026)：异步卸载路径；端到端延迟影响取决于工作负载、KV命中率和系统压力（不是绝对保证）。
- 16倍H100基准测试：当KV占用超过HBM时，LMCache会有所帮助。
- HBM压力小：开销3-5%，无效益。

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Production-stack | "the reference deployment" | vLLM's Kubernetes Helm chart + operator |
| Connector API | "KV backend interface" | vLLM 0.9.0+ pluggable KV store interface |
| Native CPU offload | "engine-local spill" | Store KV in host RAM of same engine |
| LMCache | "cluster KV cache" | Cross-engine KV cache server on CPU DRAM + disk |
| 0.11.0 async | "non-blocking offload" | Offload hidden behind engine stream |
| Preemption | "evict to make room" | KV cache shuffle when HBM full |
| Prefix reuse | "same system prompt" | Multiple queries share beginning; cache hit |
| Ceph tier | "disk tier" | Durable storage below DRAM in the cache hierarchy |
