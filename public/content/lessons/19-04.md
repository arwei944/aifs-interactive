# Capstone 04 -多模态文档质量保证（视觉优先PDF，表格，图表）

> 2026年文档- qa的前沿将从ocr -然后文本转向视觉优先的后期交互。ColPali、ColQwen2.5和ColQwen3-omni将每个PDF页面视为图像，嵌入多向量后期交互，让查询直接关注补丁。在财务报表、科学论文和手写笔记上，这种模式大大优于ocr。在10k个页面上端到端构建管道，并根据ocr -然后文本并排发布。

**Type:** Capstone
**Languages:** Python (pipeline), TypeScript (viewer UI)
**Prerequisites:** Phase 4 (computer vision), Phase 5 (NLP), Phase 7 (transformers), Phase 11 (LLM engineering), Phase 12 (multimodal), Phase 17 (infrastructure)
**运行阶段：** P4·P5·P7·P11·P12·P17
**Time:** 30 hours

## 问题

企业坐在OCR管道混乱的pdf文件上：带旋转表格的扫描10- k，密密地写着方程式的科学论文，只有图像才有意义的图表，手写的注释。把这些当作文本优先意味着失去一半的信号。2026年的答案是对原始页面图像进行后期交互多向量检索。ColPali （Illuin Tech）介绍了它；ColQwen2.5-v0.2和ColQwen3-omni推送精度。在ViDoRe v3上，视觉优先检索的得分比OCR-then-text高很多，而且在图表、表格和手写方面差距更大。

这种权衡是存储和延迟。ColQwen嵌入是每页2048个补丁向量，而不是单个1024个暗淡向量。原始的储存气球。DocPruner（2026）带来50%的修剪，没有可测量的精度损失。您将索引10k个页面，测量ViDoRe v3 nDCG@5，提供低于2s的答案，并直接与OCR-then-text基线进行比较。

## 概念

延迟交互意味着每个查询令牌对每个补丁令牌得分，并且每个查询令牌的最大得分被求和。您可以获得细粒度匹配，而不需要单个池化向量。多向量索引（Vespa， Qdrant多向量，或AstraDB）存储每个补丁嵌入，并在检索时运行MaxSim。

回答器是一个视觉语言模型，它将查询和前k个检索到的页面作为图像，并使用证据区域（边界框或页面引用）编写答案。qwen3 - v1 - 30b、Gemini 2.5 Pro和InternVL3是2026年的前沿选择。对于方程式和科学符号，OCR后退（牛轧糖，点）。将Ocr)拼接为可选的文本通道。

求值是一个二维矩阵。一个轴：内容类型（纯文本段落、密集表格、条形图/折线图、手写笔记、方程）。其他轴：检索方法（视觉优先的后期交互vs ocr -后文本vs混合）。每个单元都得到nDCG@5和答案的准确性。报告是可交付的。

## 体系结构

```
PDFs -> page renderer (PyMuPDF, 180 DPI)
           |
           v
  ColQwen2.5-v0.2 embed (multi-vector per page, ~2048 patches)
           |
           +------> DocPruner 50% compression
           |
           v
   multi-vector index (Vespa or Qdrant multi-vector)
           |
query ----+----> retrieve top-k pages (MaxSim)
           |
           v
  VLM answerer: Qwen3-VL-30B | Gemini 2.5 Pro | InternVL3
    inputs: query + top-k page images + optional OCR text
           |
           v
  answer with cited page numbers + evidence regions
           |
           v
  Streamlit / Next.js viewer: highlighted boxes on source page
```

## 堆栈

- 页面渲染：PyMuPDF （fitz）在180 DPI，肖像标准化
- 后期交互模型：ColQwen2.5-v0.2或ColQwen3-omni（拥抱脸视频团队）
- 索引：Vespa与多向量场，或Qdrant多向量，或AstraDB与MaxSim
- 修剪：DocPruner 2026策略（保持高方差补丁，50%压缩，精度损失< 0.5%）
- OCR后退（方程式/密集表）：点。或者牛轧糖
- VLM答机：Qwen3-VL-30B自托管或Gemini 2.5 Pro托管；InternVL3作为回退
- 评测：ViDoRe v3基准，M3DocVQA用于多页推理
- 查看器UI: Next.js 15与画布覆盖的证据区域

## 构建它

1. * *摄取。**浏览10- k PDF页面的语料库，科学论文和扫描文档。将每个页面渲染为1536x2048的PNG格式。坚持

2. * *嵌入。**在每个页面图像上运行ColQwen2.5-v0.2。输出形状~2048个贴片，嵌入暗淡的128个。应用DocPruner来保留信号最高的那一半。写Vespa多向量场或Qdrant多向量。

3. * *查询。**对于每个传入查询，嵌入查询塔（令牌级嵌入）。对索引运行MaxSim：对于每个查询标记，取页面补丁嵌入的最大点积sum。返回前k页。

4. * *合成。**调用qwen3 - v1 - 30b查询和前5页图像。提示：“仅使用提供的页面回答。引用每个声明（doc_id, page），并命名区域（图，表，段）。

5. * *地区的证据。**对答案进行后处理以提取引用区域。如果VLM发出边界框（Qwen3-VL会这样做），那么在查看器中将它们呈现为覆盖层。

6. * * OCR撤退。**对于识别为方程密集的页面（对图像方差的启发式），运行牛轧糖或圆点。并将ocr文本作为图像旁边的额外通道传递。

7. * * Eval。**运行ViDoRe v3（检索nDCG@5）和M3DocVQA（多页QA精度）。还可以使用相同的合成器在相同的语料库上运行OCR-then-text管道。生成内容类型x方法矩阵。

8. * * UI。**首先是流光原型；js 15生产查看器逐页证据区域覆盖。


## 练习

1. 在同一语料库上测量ColQwen2.5-v0.2与ColQwen3-omni。哪一页写对了，哪一页写错了？在按类型路由的索引中添加一个“content class”标签。

2. 积极修剪嵌入（75%,90%）。找到压缩悬崖：ViDoRe nDCG@5下降到OCR基线以下的点。

3. 构建一个混合：并行运行OCR-then-text和ColQwen，与RRF融合，使用交叉编码器重新排序。混合动力车能单独打败任何一个吗？它在哪里帮助最大？

4. 将Qwen3-VL-30B换成较小的VLM （Qwen2.5-VL-7B）。测量每美元的精确度曲线。

5. 添加手写笔记支持。呈现手写语料库，嵌入ColQwen，测量检索。与手写OCR管道比较。

## 关键术语

| Term | What people say | What it actually means |
|------|-----------------|------------------------|
| Late interaction | "ColPali-style retrieval" | Query tokens score against page patches independently; MaxSim aggregates |
| Multi-vector | "Per-patch embedding" | Each document has many vectors, not one pooled vector |
| MaxSim | "Late-interaction scoring" | For every query token, take max similarity over document vectors; sum |
| DocPruner | "Patch compression" | 2026 pruning that keeps 50% of patches with negligible accuracy loss |
| ViDoRe v3 | "Document-retrieval benchmark" | The 2026 standard for measuring visual-document retrieval |
| Evidence region | "Cited bounding box" | A bbox on the source page that localizes the answer span |
| OCR fallback | "Equation channel" | Text pipeline used alongside vision for equation- or table-heavy pages |
