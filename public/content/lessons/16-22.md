# 生产缩放-队列，检查点，持久性

> 将多代理系统扩展到数千个并发运行需要持久执行。LangGraph的运行时在每个超级步骤之后写入一个检查点Worker崩溃，释放一个租约，另一个Worker恢复。代理可以无限期休眠，等待人工输入。**MegaAgent** (arXiv:2408.09955)运行一个具有三种状态（Idle / Processing / Response）和两层协调（组内聊天+组间管理员聊天）的每个代理的生产者-消费者队列。**对于LLM流来说，光纤/异步优于每个任务一个线程：线程在99%的时间里处于空闲状态，等待令牌，光纤协同产生I/O。反驳：Ashpreet Bedi的“伸缩代理软件”主张FastAPI + Postgres +其他什么都不要，除非负载证明不是这样——简单的架构比预期的走得更远。本课构建了一个持久的检查点日志、一个带有状态转换的每个代理工作队列、一个async-vs-thread演示，并实现了实用的“简单开始”规则。

**Type:** Learn + Build
**Languages:** Python (stdlib, `asyncio`, `sqlite3`)
**Prerequisites:** Phase 16 · 09 (Parallel Swarm Networks), Phase 16 · 13 (Shared Memory)
**Time:** ~75 minutes

## 问题

一个原型多代理系统在一台笔记本电脑上工作，在内存事件循环中有三个代理。你转向生产：

- 代理有时会运行几个小时（长时间的研究，人在循环中的等待）。
- 工作进程崩溃。重启会丢失状态。
- 峰值负荷为平均值的10倍；你需要水平扩展。
- 用户按代理运行付费；收费需要一次语义。

内存中的事件循环不做这些。下面需要一个持久的执行层。2026年的规范选项是：

1. 带有检查点的工作流引擎（Temporal, LangGraph runtime）。
2. 一个带有状态存储的消息队列（Postgres + SQS/RabbitMQ）。
3. 参与者-模型框架（MegaAgent的每个代理的生产者-消费者）。
4. 手滚FastAPI + Postgres （Bedi的论点）。

本节课构建了每个模型的微缩模型。

## 概念

### 持久执行，模式

持久执行引擎在每个“步骤”（用LangGraph的语言来说就是超级步骤）之后保存完整的程序状态。崩溃:

```
worker crashes mid-step
  -> lease timeout
  -> another worker picks up the thread_id
  -> resumes from last checkpoint
  -> no duplicate side effects
```

工作要求：

- * *可串行化的状态。**所有代理状态必须是可持久的。具有实时数据库连接的函数闭包不存在。
- * *确定性的简历。**给定相同的状态和相同的输入，代理产生相同的动作（或服从外部确定性oracle的LLM调用）。
- **幂等副作用。**外部调用（工具调用，付款）必须是幂等的或使用重复数据删除键。

LangGraph在每个超级步骤之后编写一个检查点；每个活动之后的临时写；Restate使用事件源日志。这三个都实现了相同的模式。

### LangGraph的运行时

每个代理都有一个State是一个类型化字典；每个超级步骤将一行写入检查点表。在恢复时，运行时从最后一个检查点重播，而不是从头开始。代理可以运行时持久化并释放工作线程。当输入到达时，任何工作人员都可以继续。

这是2026年4月的参考生产设计。

### MegaAgent的每个代理队列

arXiv:2408.09955描述了一个规模实验：一个集群中有数千个并发代理。架构:

```
agent i:
  state ∈ {Idle, Processing, Response}
  in_queue   <- messages addressed to agent i
  out_queue  -> replies + side effects

coordinators:
  intra-group chat  (agents in the same group)
  inter-group admin chat  (high-level routing)
```

两层协调使组内对话发生密集，而组间对话保持稀疏——这种模式用于在数千个代理中保持成本线性。

### 异步vs线程/任务

LLM调用是I/ o绑定的。等待下一个令牌的线程99%的时间是空闲的。每个线程消耗约1MB的RAM；在10,000个并发调用时，仅用于堆栈就有10GB。

光纤（Python）同样的10,000个调用可以轻松地处理。在llm代理规模上，异步不是优化——它是架构。

异常：cpu绑定的后处理（嵌入，标记器技巧）仍然需要线程或进程。将I/O层与CPU层分开。

### 贝蒂的对位

“伸缩代理软件”（Ashpreet Bedi, 2026）认为，大多数团队在测量负载之前就过度设计了。实际默认值：

- FastAPI + Postgres.
- 每个代理运行是一行；使用乐观并发性就地更新状态。
- 后台作业
- 应用程序代码中的重试策略。

对于在可管理任务上运行的~100个并发代理以下的负载，这通常是您所需要的。当你检测到失败时升级。

规则是：当遇到简单架构无法解决的具体问题时，采用持久执行框架。过早收养会在没有回报的仪式上浪费时间。

### 只有一次语义

对于付费代理运行，您需要“正好一次有效”（至少一次交付+幂等消费者）。工程移动：

- **每次运行删除键。**包括在每一个副作用呼叫。
- * *发件箱模式。**副作用首先写入表，然后由单独的进程执行。两个步骤都是幂等的。
- * *补偿事务。当一个副作用成功，但它的跟踪写失败时，调度一个补偿。

这些都是数据库工程模式，而不是llm特有的。LLM税只是LLM电话太慢；其他的都是标准的分布式系统。

### 彩虹部署

Anthropic的多代理研究系统使用“彩虹部署”：多个版本的代理运行时并发运行，因此长时间运行的代理不必在每次代码部署时被终止。在一小段流量上检测新版本；当代理完成时，退出旧版本。

这是长时间运行的有状态系统的标准；2026年的适应是代理可以存活数小时，因此部署周期必须适应。

### 规范的生产清单

- 持久状态（检查点、快照或发件箱+可重放日志）。
- 幂等副作用。
- 用于LLM调用的异步I/O层。
- 至少一次用dedup交付。
- 有状态工作负载的彩虹/金丝雀部署。
- 可观察性：每个代理跟踪，超级步骤审计，重试计数器。

## 船这

规范生产硬化：

- **从简单开始（Bedi的规则）。** FastAPI + Postgres，直到你测量它失败。
- **在优化之前进行所有测试。**每次运行延迟直方图，每步时间，重试计数，失败分类。
- **发件箱模式的副作用。**特别是支付和外部API调用。
- * *彩虹部署。**永远不要在部署期间杀死飞行中的代理运行。
- **当您遇到特定问题时，采用持久执行引擎（Temporal / LangGraph / Restate）：长达一小时的人工循环等待、跨区域协调、复杂的重试/补偿策略。
- **异步I/O层。**线程仅用于cpu绑定的后处理。

## 练习

1. 运行确认检查点恢复工作；测量异步与线程并发性的差异。
2. 实现一个发件箱表：每个工具调用首先写入发件箱，然后执行一个单独的程序/任务。通过两次运行工具调用来验证幂等性。
3. 模拟**彩虹部署**：两个并发运行时版本；将新thread_ids的一半路由给每个线程；确认旧版本上正在运行的线程没有中断。
4. 阅读LangGraph的运行时文档（链接如下）。确定在手工制作的FastAPI + Postgres版本中复制运行时的哪些特性需要花费最长的时间。这是收养孩子的理由吗，还是可以推迟？
5. 读取MegaAgent （arXiv:2408.09955）章节3。两层协调（组内+组间管理聊天）是明确的。简述如何将其映射到具有两个队列族的消息队列。

## 关键术语

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| Durable execution | "Persist the program state" | Engine writes state after each super-step; crash recovery is deterministic. |
| Super-step | "Transactional boundary" | Unit of work between checkpoints. LangGraph term. |
| thread_id | "Agent run identifier" | Key that binds checkpoints and resume logic. |
| Idempotency | "Safe to retry" | Repeating a side effect produces the same result as one attempt. |
| Outbox pattern | "Decouple side effects" | Write intent to a table; a separate executor performs and marks done. |
| At-least-once delivery | "Possible duplicates" | Message queue semantics; dedup key makes consumer effective-once. |
| Rainbow deploy | "Overlapping versions" | Multiple runtime versions concurrent during long-running workloads. |
| Async fiber | "Cooperative yielding" | User-mode concurrency; cheap compared to threads for I/O-bound loads. |
| Checkpoint | "State snapshot" | Serialized state at a super-step boundary; key for resume. |
